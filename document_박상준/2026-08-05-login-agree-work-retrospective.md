## 1. 회원가입 약관/개인정보처리방침 강제 동의

### 문제
- 초기 구현에서는 이용약관 동의 체크박스 값을 개인정보처리방침 동의(`privacyAgreed`)에도 그대로 매핑해서, 사실상 한 번의 동의로 두 가지에 다 동의 처리되는 상태였음
- 약관을 끝까지 읽지 않아도 체크박스를 켤 수 있어 "동의"가 형식적이었음
- 회원가입 API가 `termsAgreed` 여부를 서버에서 검증하지 않아, 클라이언트에서 값을 조작하면 동의 없이도 가입이 가능한 구조였음

### 해결
- 약관/개인정보처리방침을 완전히 독립된 상태(`termsAgreed`, `privacyAgreed`)와 체크박스로 분리
- 두 화면 모두 스크롤이 끝(`scrolledToEnd`)에 닿아야만 동의 버튼이 활성화되도록 게이팅 추가
- 서버 쪽에도 `termsAgreedAt`/`privacyAgreedAt`을 각각 별도 컬럼으로 기록하고, 값이 없으면 예외 없이 가입을 거부하도록 필수 검증 추가 — "클라이언트가 우회하면 서버가 못 막는다"는 리뷰 지적을 반영한 것
- 회원가입 폼 임시 저장(sessionStorage)에서 비밀번호 필드는 아예 제외 — 평문으로 로컬에 남는 걸 방지

### 느낀 점
- 프론트에서만 막아둔 검증은 "UX 힌트"일 뿐 실제 보안 경계가 아니라는 걸 코드리뷰를 통해 다시 확인함. 서버 검증 없이 프론트 검증만으로 끝냈다면 눈에는 안 보이지만 실제로는 뚫려 있는 기능이 됐을 것
- 두 개의 동의 항목처럼 "겉보기엔 비슷해 보이는 상태값"을 하나로 퉁쳐서 재사용하면 나중에 반드시 분리해야 하는 순간이 오고, 그때 비용이 더 커진다는 걸 체감함

## 2. 프로필 설정 & 아바타 업로드

### 문제
- 마이페이지에 개인정보(이름/소속/분야/GitHub) 수정 기능과 프로필 사진 업로드 기능이 아예 없었음
- 아바타 업로드를 붙이면서, 작은 용량 파일이 비정상적으로 큰 해상도로 압축된 "압축 폭탄" 이미지를 그대로 `ImageIO.read()`로 전체 디코딩하면 서버 메모리가 고갈될 수 있는 위험이 있었음
- 아바타를 Storage에는 올렸는데 DB 저장이 실패하는 경우, Storage에 고아 파일이 남는 문제
- GitHub 아이디에 형식 검증이 없어 임의 문자열이 그대로 저장됨

### 해결
- PNG/JPG, 10MB, 2000×2000 제한과 함께, 전체 픽셀을 읽기 전에 `ImageReader`로 헤더(메타데이터)만 먼저 읽어 해상도를 검증하도록 순서를 바꿔 압축 폭탄을 사전 차단
- DB 저장 실패 시 방금 올린 Storage 객체를 정리하는 롤백 로직 추가
- GitHub 아이디에 실제 계정 형식 정규식을 프론트/백엔드 양쪽에 추가
- 분야 태그도 서버에서 null/공백/중복 값을 필터링하고 개수(10개)·글자수(30자) 제한을 양쪽에 추가

### 느낀 점
- "파일 업로드"라는 흔한 기능도 검증 순서 하나(헤더 먼저 vs 전체 디코딩 먼저)로 보안 리스크가 달라진다는 걸 배움. 기능이 동작하는지만 볼 게 아니라 "악의적인 입력이 오면 어떻게 되는가"를 항상 같이 물어야 한다는 걸 체감
- Storage와 DB처럼 서로 다른 저장소에 걸친 작업은 한쪽만 성공하는 부분 실패 상태를 항상 염두에 둬야 한다는 걸 롤백 로직을 짜면서 새삼 느낌

## 3. 마이페이지 실데이터 연동 (하드코딩 제거)

### 문제
- 이름 옆 직함 배지가 실제 역할과 상관없이 항상 "팀원"으로 고정
- 참여 프로젝트명도 실제 데이터와 무관하게 항상 "스마트 주차 관리 시스템"으로 고정되어 있었음 — 목업 단계 하드코딩이 실제 연동 이후에도 남아있었던 것
- 프로젝트 시작일/최종 마감일/중간 점검일 사이의 순서가 어긋나도 저장이 되었고, 저장 직후 화면이 최신 값을 바로 안 보여주는 문제(읽기 전용 뷰가 갱신 안 되는 project 상태를 참조)도 있었음

### 해결
- `currentProject.role`/`projectTitle`을 실제로 참조하도록 수정하고, 사이드바/헤더와 동일한 `ROLE_COLORS` 배색을 재사용해 UI 언어를 통일
- 날짜 3종의 선후관계 검증 추가
- 저장 후 즉시 반영되도록 읽기 전용 project 상태 대신 폼 상태를 참조하도록 데이터 흐름 수정
- 근거 없는 "AI 추천 업무" 카드도 함께 제거

### 느낀 점
- 목업 데이터로 화면을 먼저 만들고 나중에 실데이터로 바꾸는 순서에서, "다 바꿨다고 생각했는데 한두 군데는 남아있는" 케이스가 실제로 발생한다는 걸 직접 겪음. 하드코딩을 넣을 때 검색하기 쉬운 표식(주석 등)을 남기는 습관이 필요하다고 느낌
- "저장은 됐는데 화면이 최신 상태를 안 보여준다"는 류의 버그는 사용자 입장에서 특히 신뢰를 깎는 문제라, 단순 기능 구현보다 이런 상태 동기화 디테일에 더 신경 써야겠다고 생각함

## 4. 팀원 초대(링크/코드) 기능 통합

### 문제
- 초대 방식이 두 가지(이메일 토큰 기반 `/invite/:token` vs 프로젝트 고정 코드)로 나뉘어 있었는데, 화면마다 처리 로직이 따로 구현되어 있어 한쪽만 고쳐지고 한쪽은 안 고쳐지는 드리프트가 반복적으로 발생
  - "링크 복사"가 초대 코드 없이 `/projects`만 복사하던 문제
  - 링크(토큰)를 "초대 URL 또는 코드 입력" 박스에 붙여넣으면 코드 전용 로직이 토큰 형식을 못 알아봐서 실패하던 문제
  - 초대 수락 실패 시 원인 구분 없이 무조건 코드 참여로 폴백해서, 진짜 에러(권한 없음, 5xx 등)가 사용자에게 안 보이고 묻히던 문제
- 코드리뷰에서 폴백 로직이 실패 원인을 가리지 말아야 한다는 지적을 받음

### 해결
- 링크 복사가 `/invite/{코드}` 형태로 실제 코드를 담도록 수정
- "토큰 수락 먼저 시도 → `INVITE_NOT_FOUND`일 때만 코드 참여로 폴백"하는 계약을 `InviteAcceptScreen`과 `ProjectEntryScreen` 양쪽에 동일하게 적용해 두 화면의 로직을 통일
- 백엔드도 실패 원인을 `404/INVITE_NOT_FOUND`, `409/INVITE_ALREADY_PROCESSED`처럼 구분된 코드로 응답하도록 수정, 프론트는 이 코드가 정확히 일치할 때만 폴백하고 나머지는 실제 에러를 그대로 노출
- 참여 성공 메시지/실패 메시지가 겹쳐 뜨지 않도록 알림 로직도 정리
- 다른 실제 계정으로 브라우저에서 링크를 붙여넣어 참여되는 것까지 end-to-end로 직접 검증

### 느낀 점
- 비슷한 로직이 두 화면에 중복되면 반드시 한쪽만 고쳐지는 순간이 온다는 걸 이번에 직접 겪음 — 다음엔 공통 훅으로 뽑아내는 걸 먼저 고려해야겠다고 생각함(실제로 향후 개선 항목으로 남겨둠)
- "실패하면 일단 다른 방법으로 재시도"라는 폴백은 편해 보이지만, 어떤 실패에 대해서만 폴백해야 하는지(코드로 명확히 구분)를 정하지 않으면 진짜 에러를 숨기는 부작용이 있다는 걸 코드리뷰 피드백을 통해 배움

## 짧은 정리

- **문제**: 프론트 검증만 있고 서버 검증이 없던 약관 동의, 하드코딩된 마이페이지 데이터, 초대 링크/코드 로직 중복으로 인한 반쪽 수정, 파일 업로드의 잠재적 보안 취약점(압축 폭탄)이 반복적으로 드러남
- **해결**: 클라이언트-서버 이중 검증 원칙 적용, 목업→실데이터 전환 시 누락 지점 재점검, 초대 처리 로직을 한 계약으로 통일, 업로드 검증 순서 개선(헤더 우선 검사) 및 부분 실패 롤백 추가
- **느낀 점**: "프론트에서 막았다"는 실제 보안 경계가 아니며, 비슷한 로직의 중복은 반드시 드리프트를 낳고, 부분 실패(Storage/DB, 링크/코드 등 두 시스템에 걸친 작업) 상황을 항상 설계 단계에서 염두에 둬야 한다는 걸 이번 작업들을 통해 반복적으로 확인함
