# UI 위계 재설계 — 설계 문서

- 작성일: 2026-08-11
- 대상: WorkFlow AI 프론트엔드 (`App/frontend`)
- 인원/기간: 2인 · 3주 (전체 고도화 1~4주 중 1단계)
- 상태: 설계 확정 대기 (사용자 검토 중)

---

## 1. 배경

개발은 2026-08-06 커밋을 마지막으로 사실상 종료된 상태다. P0 전 기능과 P1 대부분이 구현돼 있고, 남은 것은 완성도다.
사용자가 밝힌 목적은 세 가지 — ①포트폴리오 완성도 ②실제 서비스화 ③기술 깊이 증명.

전체 고도화를 세 덩어리로 나누고, 이 문서는 그중 **A: UI 일관성·위계**만 다룬다.

| 덩어리 | 내용 | 이 문서 |
|---|---|---|
| **A** | UI 위계 재설계 + 디자인 토큰 회수 | ✅ 대상 |
| B | AI 품질 수치화 (RAG 정확도 측정·개선) | 별도 스펙 |
| C | 서비스 안정성 (지연·비용·관측) | 별도 스펙 |
| ~~D~~ | ~~P2 신규 기능~~ | **제외** — 기능을 더 붙이면 A와 C가 같이 나빠진다 |

A와 B는 파일이 겹치지 않아(`App/frontend` vs `App/backend_fastapi`+노트북) 2인이 병렬로 진행한다. C는 A·B 결과가 나와야 대상이 정해지므로 3~4주차로 미룬다.

## 3. 설계 원칙

"기깔나게"를 사람마다 다르게 해석하면 2인 작업이 어긋난다. 판단 기준을 규칙으로 고정한다.

| # | 규칙 | 정의 |
|---|---|---|
| **R1** | 한 화면에 주인공은 하나 | 시각적 1순위를 딱 하나 정하고 나머지는 크기·색·여백에서 확실히 내린다. 대시보드=진행률, 보드=칸반 컬럼, 회의록AI=분석 결과, 어시스턴트=대화 |
| **R2** | 행동할 것이 읽을 것보다 위 | 블로커·마감임박처럼 조치가 필요한 정보가 위·크게. 전체업무 166 같은 참고 수치는 아래·작게 |
| **R3** | 숫자는 혼자 두지 않는다 | 모든 수치에 분모나 추이를 붙인다. `8` ✕ → `블로커 8 / 전체 166 · 어제보다 +2` ○ |
| **R4** | 색은 상태에만, 장식 금지 | 보라=브랜드·현재위치 / 빨강=블로커 / 주황=마감임박 / 초록=완료. **이 4개 외 전부 무채색.** 카테고리 뱃지는 색 대신 아이콘+회색으로 내린다 |
| **R5** | 밀도는 3등급만 | `요약`(대시보드) / `작업`(보드·회의록) / `목록`(활동로그·설정). 화면마다 하나 골라 그 안에서만 간격을 쓴다 |

R4가 가장 큰 변화다. 지금은 카테고리 뱃지 6종이 각자 색을 가져서 **정작 중요한 블로커 빨강이 묻힌다.** 색을 줄여야 눈에 띈다.

### 시각 방향 (확정)

밝은 배경 + **기존 보라 `#6D5EF8` 유지**. 다크·에디토리얼·네오브루탈은 검토 후 기각(사용자 피드백: "너무 어둡고, 업무툴 같지 않고, 보라색은 유지").

전체 13개 영역을 다 다시 짜면 3주에 못 끝낸다.

| 등급 | 화면 | 작업 |
|---|---|---|
| **깊게** (5) | 대시보드 · 업무 보드 · 회의록 AI · AI 어시스턴트 · 랜딩/로그인 | 레이아웃 재설계 + R1~R5 전면 적용 |

## 5. 대시보드 확정 설계

깊게 하는 5개 중 대시보드만 이번에 시안까지 확정했다. 나머지 4개는 이 설계를 기준 삼아 후속 진행.

### 5.1 상단 — 액션바 (R2)

기존 "빠른 액션" 버튼 4줄을 **제거**하고(우상단 아이콘으로 축소), 그 자리에 조치가 필요한 정보를 놓는다.

```
⚠  막힌 업무 8건 · 오늘 마감 3건            [오늘 마감]  [블로커 풀기]
   블로커 5건은 3일 넘게 그대로입니다
```

- 읽고 마는 배너가 아니라 **버튼이 붙은 액션바**
- 부제에 심각도 근거를 한 줄 붙임

### 5.2 진행률 — 도넛 게이지 + 판정 (R1, R3)

화면의 주인공. 게이지 처리는 **③ 상태 세그먼트 + 계획선**을 기본으로 삼는다.

- **세그먼트**: 완료(보라) / 진행중(주황) / 막힘(빨강) / 할일(회색) — 원 하나로 팀 상태 전체가 읽힘
- **계획선**: 검은 눈금으로 *오늘 있어야 할 위치*를 표시. 눈금보다 앞서면 순항, 뒤면 지연
- **판정 배지**: `✓ 예정보다 3일 앞섬` + 근거 한 줄 (`남은 42건을 지금 속도(주 18건)로 하면 마감 3일 전 완료`)
- **누를 수 있는 숫자**: 남은 42 / 막힘 8 / 오늘 3 → 클릭 시 필터된 목록으로 이동

**계획선 데이터 (확인 완료)** — `Project` 엔티티에 `startDate`(41행), `deadline`(35행), `midCheckDate`(44행)가 모두 있다.
계획선 위치는 `(오늘 − startDate) / (deadline − startDate)`로 바로 산출된다. 스키마 변경 불필요.
`midCheckDate`가 있으므로 **중간 점검일 눈금도 함께** 긋는다 — 중간 점검까지 남은 여유가 한 번에 보인다.

### 5.3 막힌 업무 — 시간 타임라인 (확정: N안)

블로커를 숫자로 요약하지 않고 **얼마나 오래 정체됐는지**를 막대 길이로 보여준다.

```
● ERD 수정본 공유        ████████████████ 5일 · 위험      (유)
● LLM 회의 분석 구조화    ████████████ 4일 · 위험          (허)
● 학습·평가 노트북 정리   █████████ 3일 · 주의             (이)
● /ai/score/workload     ██████ 2일                       (고)
● 대시보드 테스트4        ███ 1일                          (박)
  0일        2일        3일(주의선)        5일
```

- 막대 길이 = 막힌 기간. 길수록 심각 → 눈이 자동으로 제일 긴 막대로 감
- **등급 기준**: 2일까지 `보통`, **3일부터 `주의`, 4일 이상 `위험`** (운영하며 조정 가능)
- 막대 안에 기간·등급을 **텍스트로 직접 표기** — 색 대비만으로 판단하지 않게

**기각한 대안**
- J(배너 숫자 확대) / K(진행률과 동급 패널) — "8건 막혔다"를 크게 말할 뿐, 왜 지금 풀어야 하는지를 못 보여줌
- L(연쇄 영향: "8건이 다른 17건을 세우고 있음") / O(사람 중심: "3명이 막고 있고 5명 대기") — 설득력은 가장 크나 **업무 간 선후 관계 데이터가 없어** 구현 불가
- M(카드로 직접 노출) — 카드 4장이 상단 자리를 너무 많이 먹음

### 5.4 하단

- **팀원별 업무량**: 과부하 표시 추가 (예: 21/23 → 빨강 + `과부하` 라벨)
- **마감 임박**: 담당자 아바타 + D-day 뱃지

## 5-2. 업무 보드 확정 설계

진단 #5(카드 과밀)와 #6(밀도 불일치)을 푸는 절. 대시보드 다음으로 확정했다.

### 카드 — P안 (제목 우선)

제목만 키우고 나머지 5종(카테고리·상태·우선순위·기간·담당자)을 **회색 한 줄로 내린다.**

- 제목 `14px / 650` — 카드에서 실제로 찾는 정보는 "무슨 일인가" 하나다
- 메타 `11.5px` 회색 한 줄 — 눈이 제목만 따라 내려가고, 필요할 때만 아래를 본다
- 카테고리 뱃지는 **색을 걷어내고** 회색 아이콘+텍스트로 (R4)
- 컬럼 헤더에 맥락 추가 — `할 일 28 · 미배정 6` (R3)
- 블로커 카드에는 `4일째 막힘` 표기 (대시보드 N안과 같은 기준)

**기각한 대안**: Q(좌측 색띠) — 카드는 가장 작아지나 상태를 색만으로 전달해 §6 접근성 요구 2번과 충돌. R(메타바 분리) — 경계는 가장 뚜렷하나 카드가 높아져 표시 수가 줄어든다.

### 상태색 매핑 — S2 (확정)

보드 컬럼과 대시보드 게이지가 **같은 규칙**을 쓴다. 한쪽만 바꾸면 두 화면이 어긋난다.

| 상태 | 색 | 표시 |
|---|---|---|
| 할 일 | `#E4E3ED` (회색) | **빈 원** — 테두리만. 색 없이 모양으로도 "아직 시작 안 함"이 읽힌다 |
| 진행 중 | `#2A7FE0` (파랑) | 채운 원 |
| 보류·블로커 | `#E5484D` (빨강) | 채운 원 |
| 완료 | `#6D5EF8` (보라, 브랜드색) | 채운 원 |
| *마감 임박* | `#F59E0B` (주황) | 상태가 아닌 **별개 축**. 위 4개와 무관하게 유지 |

상태색이 4개 → 5개로 늘어 R4를 완화한다. 근거: 카테고리 뱃지 색 6종을 걷어냈으므로 **화면 전체 색 수는 오히려 줄어든다.**
완료를 브랜드 보라로 두어 게이지 대부분이 보라로 차고, 제품 인상이 유지된다.

**기각한 대안**: S1(진행중=보라, 완료=초록) — 브랜드색을 상태색으로 소비해 현재 메뉴 표시 등에 보라를 쓰기 애매해진다. S3(보라 명도 3단계) — 색을 안 늘리나 대비가 가장 약해 "확실히 구분" 요구에 못 미친다.

### 카드 호버

카드에 마우스를 올리면 **그 컬럼 상태색의 연한 단계(약 40% 톤)**로 테두리가 바뀐다.

| 상태 | 기본 테두리 | 호버 테두리 |
|---|---|---|
| 할 일 | `#E8E8F0` | `#B9B7C8` |
| 진행 중 | `#E8E8F0` | `#9DC5F0` |
| 보류·블로커 | `#F3C9CA` | `#F0AFB1` |
| 완료 | `#E8E8F0` | `#C0B8FB` |

- 진한 원색을 쓰지 않는다 — 블로커 빨강과 경쟁해 "지금 급한 게 뭔지"가 흐려진다. 호버는 "누를 수 있다"는 신호일 뿐 상태 표시보다 약해야 한다
- 테두리 1px 색 변화만으로는 대비가 약한 모니터에서 안 보이므로, **같은 색 계열 옅은 그림자 + `translateY(-1px)`**를 같이 준다
- **`:focus-visible`에도 동일 스타일** 적용 — 호버는 마우스 전용이라 키보드 탐색에서 같은 피드백이 없으면 안 된다
- `prefers-reduced-motion`일 때는 **`transform`만 끄고** 테두리·그림자는 유지한다

## 5-3. 회의록 AI 확정 설계

### 레이아웃 — T안 (To-Do 우선)

이 화면에 오는 이유는 회의록을 읽으려는 게 아니라 **회의에서 나온 일을 보드로 넘기려는 것**이다(R2).
지금은 To-Do가 맨 아래라 스크롤해야 보이고, 핵심 행동인 `업무로 등록`이 우측 상단 작은 텍스트로 묻혀 있다.

- **To-Do를 맨 위 주인공으로.** `업무 후보 7건이 나왔습니다` + `7건 모두 등록` 버튼을 크게
- **담당자를 그 자리에서 지정** — 인라인 `담당자 지정 ▾`. 미배정 문제를 화면을 옮기지 않고 푼다
- **요약·결정사항은 아래 2열로** 내린다. 세 카드가 같은 무게로 경쟁하던 문제(R1) 해소
- **To-Do 제목에서 `미배정:` 접두사 제거** — 미배정은 담당자 칸의 상태이지 제목의 일부가 아니다
- **좌측 목록의 `AI 분석 완료` 뱃지 제거** — 전 항목에 붙어 정보량이 0이다. 대신 `미배정 5` / `등록 완료`처럼 **처리가 남았는지**를 표시한다 (V안에서 가져옴)

**기각한 대안**: U(단계형 진행바) — 방치 방지에는 좋으나 진행바가 자리를 먹고 이미 등록을 끝낸 회의록에는 군더더기. V(탭 분리) — 카드 경쟁은 없어지나 요약과 To-Do를 동시에 볼 수 없어 맥락 보며 담당자 정하기가 불편.

### 담당자 표시 — W안 (연한 배경 칩) + 사람색

이니셜 1자(`박`, `유`) 대신 **전체 이름**(`박지수`, `유소은`)을 띄우고, 사람마다 색을 다르게 준다.

**두 색 축을 분리한다.** 사람색이 상태색을 이기면 블로커 빨강이 묻히므로, 역할과 채도를 갈라 놓는다.

| 축 | 역할 | 채도 |
|---|---|---|
| 상태색 (5) | **의미 전달** — 완료·진행중·블로커·마감임박·할일 | 높음 |
| 사람색 (6) | **식별만** — 누구인지 구분 | 낮음(무딘 톤) |

사람색 팔레트 — 상태색 5개와 색조가 겹치지 않게 고른 6색:

| 색 이름 | 글씨 | 배경 |
|---|---|---|
| 청록 | `#0F6B63` | `#E6F2F1` |
| 자주 | `#A6376A` | `#FBEAF1` |
| 황토 | `#7A5B2E` | `#F2EDE4` |
| 올리브 | `#5B6B33` | `#EEF0E3` |
| 회보라 | `#5A5470` | `#EDEBF3` |
| 청회색 | `#3E6076` | `#E7EFF4` |

- 팀원이 6명을 넘으면 **사용자 ID 해시로 6색을 순환**한다. 같은 사람은 어느 화면에서든 항상 같은 색
- 색이 겹쳐도 **이름이 항상 함께 나오므로** 혼동이 생기지 않는다. 색은 이름의 보조 수단일 뿐이다

**공간에 따른 표기 규칙** — 사람색은 어디서나 적용하되 이름 길이만 다르게 한다.

| 위치 | 표기 |
|---|---|
| 회의록 AI · 마감 임박 · 팀원별 업무량 (넓음) | **전체 이름 칩** (사람색 배경 + 진한 글씨) |
| 보드 카드 (236px, 좁음) | **이니셜 아바타**에 같은 사람색 배경. 전체 이름은 툴팁·상세에서 |

**기각한 대안**: X(점 + 무채색 이름) — R4와는 가장 잘 맞으나 점이 작아 "색을 다르게" 요구의 효과가 약하다. Y(글씨색만) — 정렬이 깔끔하나 W보다 사람 식별이 느리다.

> 사람색 도입은 R4("색은 상태에만, 장식 금지")를 완화한다. 근거: 식별은 장식이 아니라 기능이고,
> 채도를 낮춰 상태색과 경쟁하지 않게 했으며, 카테고리 뱃지 색 6종을 걷어낸 자리를 쓰는 것이다.

## 5-4. AI 어시스턴트 확정 설계

### Z안 (구조화 답변) — 1순위

지금 답변은 DB 레코드를 문장에 섞어 그대로 나열한다:

```
- 프로젝트 CRUD 및 초대 API 구현 (홍길동) 마감 2025-12-28 우선순위 high 사유: [...] WF-207
```

대시보드·보드에서 세운 위계가 여기서 무너진다.

- **업무를 텍스트가 아니라 카드로 렌더한다.** 보드와 같은 컴포넌트를 재사용
- 카드에 **같은 상태색·사람색·"5일째" 표기**를 그대로 쓴다 → 네 화면이 하나의 제품으로 보인다
- 항목을 누르면 **해당 업무로 바로 이동**
- `- 외 5건`으로 끊지 않고 **`나머지 5건 모두 보기 →`** 링크를 둔다
- 출처 칩을 `출처: 액션아이템 #680` 대신 **`업무 보드 · 보류/블로커`** 처럼 무엇인지 알 수 있게 쓴다

### 후속 순위

| 순위 | 안 | 내용 |
|---|---|---|
| 1 | **Z** | 구조화 답변 (위) |
| 2 | AB | 실행형 확인 — `"내일까지로 바꿔줘"` → **이전값 → 새값** 미리보기 후 반영. README에 적힌 "실행형은 확인(interrupt) 후에만 반영"이 지금 화면에 전혀 안 보인다. 시연에서 가장 강한 장면 |
| 3 | AA | 근거 확장 — 출처를 제목 + 인용문까지 펼침 |

2·3순위는 3주 안에 못 하면 다음 사이클로 넘긴다.

> **범위 밖 발견** — 어시스턴트 답변에 `사유: [Jira01 재검증 테스트 삽입]` 같은 **테스트 데이터가 그대로 실려 나온다.**
> UI가 아니라 데이터 문제라 이 스펙 범위 밖이지만, 시연·포트폴리오에 노출되므로 별도 처리가 필요하다.

## 7. 데이터 전제와 리스크

### 7.1 `tasks.status_changed_at` 부재 — **차단 요인**

N안(막힌 기간 막대)의 전제. 실측 결과:

- `Task` 엔티티에 `status`(String), `updatedAt`만 존재. **`statusChangedAt` 없음**
- `updatedAt`은 제목 수정 등 아무 변경에나 갱신되므로, 막힌 기간이 **실제보다 짧게** 계산됨
- `activities` 테이블에 `STATUS_CHANGED` 타입 + `targetId` + `createdAt`이 있어 역산은 가능하나, **바뀐 상태값이 `message` 문자열 안에** 있어 파싱이 취약

**결정: `tasks.status_changed_at TIMESTAMP` 컬럼을 새 Flyway `V*.sql`로 추가한다.**
기존 행은 `activities`의 마지막 `STATUS_CHANGED` `created_at`으로 backfill하고, 없으면 `updated_at`으로 대체한다.
이미 배포된 `V*.sql`은 CI(`migration-guard`)가 수정을 차단하므로 반드시 새 파일로 만든다.

### 7.2 계획선 계산용 시작일·마감일

게이지의 계획선(`오늘 있어야 할 위치`)에는 프로젝트 시작일·마감일이 필요하다. 로드맵 기능에 마일스톤 데이터가 있으므로 가능할 것으로 보이나 **미확인**. 착수 시 확인 필요.

### 7.3 업무 간 선후 관계 없음

L·O안을 기각한 이유. 이번 범위에서 의존성 모델을 새로 만들지 않는다(YAGNI). 필요해지면 별도 스펙으로.
