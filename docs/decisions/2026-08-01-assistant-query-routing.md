# 어시스턴트 검색: 하이브리드 융합 대신 질의 라우팅

- 날짜: 2026-08-01
- 대상 브랜치: `feature/assistant-query-routing`
- 선행 조치: [2026-08-01-ivfflat-index-returns-fewer-rows.md](../trouble-shooting/2026-08-01-ivfflat-index-returns-fewer-rows.md) —
  이 결정의 근거 수치는 해당 인덱스 제거 **이후** 값이다.
- 근거 실험: `02_hybrid_rag_evalset.ipynb` ~ `02-2_hybrid_rag_analysis.ipynb` (전체 설계 문서는
  `docs/superpowers/specs/2026-08-01-assistant-query-routing-design.md`, `.gitignore` 대상이라 로컬 전용)

## 맥락

어시스턴트 질문 경로는 임베딩 유사도 하나로만 검색한다. 업무 코드 정확 검색
함수(`find_task_chunks_by_code`)는 이미 있지만 부르는 곳이 `graph/task_resolver`
하나뿐이라, 같은 코드를 말해도 처리가 갈린다.

| 사용자 입력 | 경로 | 코드 정확 검색 |
| --- | --- | --- |
| "WF-195 상태 바꿔줘" | 명령 | 돈다 |
| "WF-195 어떻게 돼가?" | 질문 | **안 돈다** |

운영 데이터(378청크) 30문항 평가에서 코드가 든 질문의 Hit@5가 **0.400**이다.

## 선택

**질의 라우팅.** 질문에 `[A-Za-z]{2,}-\d+`가 있으면 코드 정확 일치 결과를 앞에 놓고
남는 칸을 임베딩으로 채운다. 코드가 없으면 현행 그대로 간다.

| 방식 | Hit@5 | identifier | semantic | 악화 문항 |
| --- | --- | --- | --- | --- |
| dense (현행) | 0.733 | 0.400 | 0.800 | — |
| RRF K=60 | 0.833 | 0.600 | 0.900 | 0 |
| RRF K=1 | 0.900 | 1.000 | 0.700 | 1 |
| **라우팅** | **0.933** | **1.000** | **0.800** | **0** |

### 구현 완료 후 실측 정정 (2026-08-01)

위 표는 노트북 시뮬레이션 값이다. 구현 후 **실제 함수를 운영 DB에 붙여 30문항을 다시
재봤다.** 라우팅은 0.933으로 정확히 재현됐지만 dense 기준선이 달랐다.

| | 노트북 | 실제 구현 |
| --- | --- | --- |
| 라우팅 Hit@5 | 0.933 | **0.933** (일치) |
| dense Hit@5 | 0.733 | **0.667** |
| dense identifier | 0.400 | **0.200** |

노트북의 dense 기준선이 `search_similar_chunks`의 회의록 최소 슬롯 예약
(`MEETING_MIN_RESERVED = 2`)을 반영하지 않았다. 운영에서는 상위 5칸 중 2칸이 회의록에
예약되므로 코드 질문의 실제 성적이 더 나쁘다. **즉 개선 폭은 위 표보다 크다 —
0.667 → 0.933.**

점수만이 이유는 아니다. 스키마 변경이 없고(인덱스 하나 때문에 데인 직후다),
코드 없는 질문의 순위를 아예 건드리지 않아 **구조적으로 악화가 불가능하다.**

### 세부 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 개인화 질문(`assignee_id`) | 라우팅 미적용 | 코드 검색 SQL에 담당자 필터가 없어 남의 업무가 개인화 답변에 섞인다. 평가에서 측정된 적 없는 경로다 |
| 코드 히트 상한 | 3건 (임베딩 2칸 보장) | 실측상 코드 101종 중 100종이 청크 1건에만 매칭된다. 상한은 "코드가 여러 개일 때"를 정하는 값 |
| 여러 코드 배분 | 코드마다 한 건씩 돌아가며 채움 | 아래 "리뷰로 드러난 결함" |
| 없는 코드 | 임베딩으로 폴백 | 명령 경로와 **반대**. 잘못된 답변은 무시하면 되지만 잘못된 업무 수정은 못 되돌린다 |
| 정규식 | `task_resolver`의 `_CODE_PATTERN`을 `retrieval_service`로 이동해 공유 | 복제하면 명령과 질문이 서로 다른 코드를 인식하는 버그로 자란다 |
| 캐시 | `_ANSWER_CACHE_SCHEMA_VERSION` v13 → v14 (필수) | 안 올리면 30분 TTL 동안 옛 답변이 그대로 나간다 |
| 관측 | 라우팅 발동 시에만 info 로그 1줄 (개수만) | 질의 로그 테이블이 없어 코드 질문의 실사용 비중을 모른다 |

## 버린 대안

- **RRF 융합** — 식별자는 확률적 유사도와 다른 축의 정보다. 순위 점수로 환산해 평균 내면
  확실한 정보가 희석된다. 교과서 기본값 K=60은 현행보다 낫지만(0.833) 라우팅보다 나쁘고,
  한쪽만 확신하는 1위(`1/61`)가 양쪽의 미지근한 동의(`1/64+1/65`)에 지는 구조다.
  후보 풀이 작으면 K는 1~5가 맞다.
- **Postgres 내장 FTS (`to_tsvector('simple')`)** — 한국어 조사 때문에 현행보다 나쁘다
  (0.567 < 0.733). 채택하지 않는다.
- **pg_trgm 하이브리드** — `mixed` 카테고리가 이미 1.000으로 포화라 이득을 측정할 수 없다.
  새 인덱스도 필요하다. 보류하고, 위 관측 로그로 재검토 시점을 잡는다.

## 구현 시 놓치기 쉬운 두 지점 (테스트로 잠근다)

1. **코드 히트를 유사도로 재정렬하지 않는다.** 정확 일치 청크의 유사도가 임베딩 1등보다
   낮을 수 있다. 재정렬하면 라우팅이 무력화된다.
2. **임베딩은 잔여 칸이 아니라 항상 `top_k` 전체로 요청한다.** "코드가 3칸 썼으니 2건만"
   이라며 `top_k=2`로 부르면 `MEETING_MIN_RESERVED=2`에 걸려 남은 2칸이 통째로 회의록으로
   대체되고 의미 검색 결과가 사라진다.

## 리뷰로 드러난 결함 — 한 코드가 슬롯을 독점 (2026-08-01 수정)

최초 구현은 코드 정확 일치를 **유사도 순으로 앞에서 3건** 잘랐다. 그러면 한 코드가
슬롯을 독점해 사용자가 명시한 다른 코드가 통째로 빠진다. 운영 DB에서 재현됐다.

```
"FS-4 와 WF-174 와 WF-175 비교해줘"
  수정 전  [FS-4, FS-4, WF-175]   -> WF-174 누락
  수정 후  [FS-4, WF-174, WF-175] -> 셋 다 포함
```

FS-4는 청크가 2건이라 혼자 두 칸을 먹었다. 사용자가 코드 셋을 나열했으면 셋 다 근거에
있어야 한다.

**고친 방법**: 후보를 넉넉히 받아(`len(codes) * limit`, 상한 30) **코드마다 한 건씩
돌아가며** 채운다. 444행 순차 스캔이 1ms 미만이라 넉넉히 받아 파이썬에서 고르는 편이 싸다.

**왜 못 잡았나**: 평가셋 30문항이 전부 코드 0개(20문항) 또는 1개(10문항)였다.
**다중 코드는 측정된 적이 없다.** 코드 1개일 때는 코드당 청크가 1건이라(101종 중 100종)
어떤 배분 방식을 써도 결과가 같아 결함이 드러나지 않았다.

**남는 한계**: 코드가 4개 이상이면 상한 3에 걸려 일부는 여전히 빠진다. 다만 이제
질문에서 **뒤에 말한 코드부터** 예측 가능하게 밀린다(이전에는 임베딩 거리로 임의 결정).
로그의 `코드 N개, 정확 일치 M건`에서 N > M 이면 잘렸다는 뜻이다.

## 되돌리는 법

`revert` 커밋 하나. 스키마도 데이터도 건드리지 않는다.

캐시 버전은 `v13`으로 되돌리는 것이 맞다. 살아남은 `v13` 항목은 전부 옛 코드가 만든
것이므로 되돌린 코드에게 정확히 올바른 캐시다.

## 한계

평가는 `project_id=1` 하나에서 쟀고, 이 프로젝트는 테스트 주입 데이터가 섞인 데모다.
코드 질문의 실사용 비중을 모르므로 **체감 개선 폭은 예측할 수 없다.** 다만 악화 문항이
0이라 효과가 작을 수는 있어도 나빠지지는 않는다.
