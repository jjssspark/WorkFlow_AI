# 세션 폐기는 사용자 행 잠금으로 원자적으로 만든다

- 날짜: 2026-08-16
- 대상 브랜치: `feature/password-change` (PR #605 → `dev`)
- 상태: **적용 완료**

## 맥락

리프레시 토큰은 서버에 저장하지 않는 stateless 토큰이다. 그래서 비밀번호를 바꿔도 자동으로 무효화되지
않고, 대신 `users.password_changed_at`보다 이전에 발급된(`iat` 기준) 토큰을 거부하는 **시각 비교**로
폐기를 흉내낸다. "비밀번호를 바꾸면 다른 기기 세션이 끊긴다"는 약속이 이 비교 하나에 걸려 있다.

문제는 이 방식이 원자적이지 않다는 것이다. 기준 시각을 기록한 순간과 트랜잭션이 커밋되는 순간 사이에
도착한 재발급 요청은 READ COMMITTED에서 **아직 옛 `password_changed_at`을 읽는다.** 그래서 통과하고,
그렇게 발급된 토큰은 `iat`이 기준 시각보다 **뒤**라서 비밀번호 변경이 끝난 뒤에도 계속 유효하다.

```
T0  변경 트랜잭션: changedAt = now() 기록
T1  재발급 요청 도착 → 옛 password_changed_at 읽음 → 통과 → iat=T1 토큰 발급
T2  변경 트랜잭션 커밋 (bcrypt ~100ms + flush 만큼 T0보다 늦다)
    → T0 < T1 이므로 이 토큰은 폐기를 통과해 살아남는다
```

탈취한 리프레시 토큰을 반복 호출하는 공격자에게는 이 창이 폐기를 통째로 무력화하는 구멍이 된다.
비밀번호를 바꿔도 공격자 세션이 끊기지 않는다.

`changePassword`와 `confirmReset` 양쪽에 있었다. 후자가 더 나쁘다 — 계정이 털린 것 같아서 재설정하는
흐름인데, 바로 그 순간에 공격자가 살아남을 수 있다.

### 시각을 언제 찍든 창은 닫히지 않는다

`changedAt`을 bcrypt 앞이 아니라 뒤에서 찍으면 창이 좁아질 뿐 사라지지 않는다. 커밋은 어차피 그보다
뒤이고, 그 사이에 읽는 쪽은 여전히 옛 값을 본다. 시각을 미래로 밀면 창은 닫히지만, 그 사이에 정상
로그인한 사용자의 토큰까지 거부된다.

`iat`이 JWT 스펙상 초 단위라는 점이 창을 좁혀주기는 한다. 경계 규칙이 "이하(`<=`)"라 같은 초에 발급된
토큰은 이미 거부되므로, **커밋이 초 경계를 넘길 때만** 뚫린다. 그래서 확률적이지만, 반복 호출하면
언젠가는 걸린다. 방어를 확률에 맡길 수는 없다.

## 선택

읽는 쪽과 쓰는 쪽을 **행 잠금으로 직렬화한다.**

| 흐름 | 잠금 | 이유 |
|---|---|---|
| `AuthService.changePassword` | `findByIdForUpdate` (FOR UPDATE) | 변경 중에는 아무도 옛 값을 못 읽게 한다 |
| `PasswordResetService.confirmReset` | `findByIdForUpdate` (FOR UPDATE) | 위와 같음 |
| `AuthService.refresh` | `findByIdForShare` (FOR SHARE) | 변경이 진행 중이면 커밋까지 기다렸다 갱신된 값을 읽는다 |

두 인터리빙 모두 안전해진다.

- **재발급이 먼저 잠그면**: 토큰을 발급하고 커밋한 뒤 잠금을 놓는다. 변경 쪽은 그 후에 잠금을 얻고
  `changedAt`을 찍으므로 `changedAt`이 그 토큰의 `iat`보다 뒤다 → 이후 거부된다.
- **변경이 먼저 잠그면**: 재발급은 커밋까지 블록됐다가 갱신된 `password_changed_at`을 읽는다 → 거부된다.

공유 잠금을 쓴 이유는 재발급끼리는 서로 막을 이유가 없기 때문이다. FOR SHARE는 FOR UPDATE와만 충돌한다.
`refresh`에 `@Transactional`을 붙인 것은 잠금에 트랜잭션이 필요해서다.

### 잠금 순서는 사용자 → 토큰으로 통일한다

`confirmReset`은 원래 `consumeIfUnused`(토큰 행 갱신)를 먼저 하고 사용자를 읽었다. 여기에 사용자 잠금을
그대로 붙이면 `changePassword`(사용자 → `invalidateAllUnusedByUserId`)와 **반대 순서**가 되어 교착이 난다.
그래서 사용자 잠금을 토큰 소모보다 앞으로 옮겼다. "정책 위반은 토큰을 소모하기 전에 막는다"는 기존
약속도 그대로 유지된다.

## 버린 대안

- **세션 버전 카운터** (`users.token_version`을 증가시키고 토큰 클레임에 실어 비교) — 구조적으로 더 깨끗하다.
  시각 비교가 사라지므로 이 경쟁 조건이 원천적으로 없어지고, 변경 직후 발급 토큰의 `iat`을 1초 밀어내는
  꼼수도 함께 없앨 수 있다. 커밋 전에 읽은 재발급은 옛 버전을 실으므로 자동으로 거부된다.
  **컬럼 추가와 마이그레이션이 필요해 이번 범위에서 뺐다.** 다음에 이 영역을 손댈 때 우선 후보다.
- **리프레시 토큰을 DB에 저장(stateful)** — 폐기가 명시적이 되지만 재발급마다 쓰기가 생기고 토큰 테이블
  수명 관리가 따라붙는다. 지금 문제에 비해 과하다.
- **낙관적 잠금(@Version)** — 충돌한 쪽이 예외를 받으므로 재시도 로직이 필요하고, 재발급이 실패로 끝나면
  정상 사용자가 튕긴다. 여기서는 "기다렸다가 최신 값을 읽는" 동작이 맞다.

## 검증

`PasswordChangeConcurrencyTest`가 두 흐름 모두를 재현한다. 테스트가 직접 트랜잭션을 열고 그 안에서
서비스를 호출해(REQUIRED로 합류) 커밋 시점을 쥔 채 "커밋 전에 도착한 재발급"을 만든다. 대기 시간에
기대지 않으며, `iat` 초 경계를 넘기기 위한 1.1초 대기 하나만 남겼다.

잠금을 되돌리면 두 테스트가 다시 실패하는 것을 확인했다(변경 도중 발급된 토큰이 변경 후에도 거부되지
않음). 실제 앱에서도 확인했다 — 변경 후 현재 기기 재발급 200, 다른 기기 토큰 401 `INVALID_TOKEN`.

## 되돌리는 법

`findByIdForUpdate`/`findByIdForShare` 호출을 `findById`로 되돌리고 `refresh`의 `@Transactional`을 떼면
된다. 단, 그 순간 위 경쟁 조건이 그대로 돌아온다 — `PasswordChangeConcurrencyTest`가 빨개져서 알려준다.

잠금 경합이 문제가 되면(같은 사용자에 대해서만 생긴다) 잠금을 푸는 대신 위 "버린 대안"의 세션 버전
카운터로 옮기는 것이 맞다. 잠금 없이 시각 비교만 남기는 선택지는 없다.
