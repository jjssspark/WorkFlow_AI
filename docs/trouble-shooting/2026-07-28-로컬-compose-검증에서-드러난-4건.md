## 1. AI 어시스턴트가 첫 질문마다 "일시적으로 처리할 수 없습니다"

### 증상

어시스턴트에 질문하면 45초쯤 뒤 실패 문구가 뜬다. 그런데 FastAPI 로그에는 **200이 찍혀
있다.** 답은 만들어졌는데 버려진 것이다.

### 원인

두 가지가 겹쳤다.

**(a) Spring 읽기 타임아웃이 실측값과 사실상 같았다.**
`FastApiAssistantClient`가 `READ_TIMEOUT = 45s`를 상수로 갖고 있었다. 같은 스택에서 잰 값은

| 상태 | 소요 |
|---|---|
| 캐시 히트 | 0.03초 |
| 웜(모델 적재됨) | 33.2초 |
| 콜드(모델 내려감) | **44.6초** |

45초는 여유가 아니라 경계선이었다. 옆 클래스 `FastApiMeetingClient`는 이미
`workflow.ai.read-timeout-seconds` 프로퍼티를 읽고 있었는데 어시스턴트만 빠져 있었다.

**(b) ollama가 5분마다 모델을 내렸다.**
`ollama ps`가 비어 있었다. `_generate_with_ollama`가 `keep_alive`를 안 넘겨서 기본 5분이
적용됐고, 콜드 로드에만 약 10.9초가 붙는다. 회의 중 띄엄띄엄 쓰는 화면이라 5분 간격을
넘기기 쉬워 **사실상 매번 콜드**였다. 회의록 분석(`app/main.py`)과
체크리스트(`checklist_pipeline.py`)는 이미 `keep_alive`를 넘기고 있었다.

### 수정

- `assistant-read-timeout-seconds`(기본 120초) 프로퍼티 신설 + 생성자 주입.
  회의록 분석과 걸리는 시간이 달라 `read-timeout-seconds`를 재사용하지 않고 분리했다 —
  공유하면 한쪽을 늘릴 때 다른 쪽이 조용히 끌려간다.
- `keep_alive=settings.rag_ollama_keep_alive`(기본 `30m`) 추가.

타임아웃은 "끊기지 않게", keep_alive는 "느려지지 않게" 한다. 서로 대체재가 아니다.
운영은 huggingface를 쓰므로(`docker-compose.prod.yml`) 타임아웃만 공통이고
keep_alive는 로컬 전용 효과다.

### 되돌리는 법

`WORKFLOW_AI_ASSISTANT_READ_TIMEOUT_SECONDS` / `RAG_OLLAMA_KEEP_ALIVE` 환경변수만
바꾸면 된다. 재빌드 불필요 — 그게 이번 수정의 요지다.

## 2. backend-fastapi 빌드가 네트워크 한 번 흔들리면 통째로 실패

### 증상

```
ERROR: Could not find a version that satisfies the requirement numpy==2.2.6
       (from versions: none)
```

같은 `python:3.12-slim`에서 numpy 2.2.6은 정상 설치된다. **재시도만으로 성공했다.**
패키지 문제가 아니라 PyPI 접속이 순간 흔들린 것이다.

`requirements.txt`가 2026-07-27(`929b4d1`, testcontainers 추가)에 바뀌어 pip 레이어
캐시가 무효화된 상태였고, 그 레이어는 약 700초짜리다.

### 원인

진짜 비용은 실패 자체가 아니라 **재시도가 다시 0부터 700초**라는 점이다.
`--no-cache-dir`라 그때까지 받은 휠이 전부 버려진다.

### 수정

BuildKit 캐시 마운트로 pip 다운로드 캐시를 빌더에 남긴다. 이미지 레이어 밖이라 크기
영향은 없다(확인: 이미지 2.79GB 유지, 캐시 마운트 925.4MB 별도).

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --retries 10 --timeout 60 -r requirements.txt
```

`--retries/--timeout`(기본 5회/15초)은 짧은 흔들림이 애초에 실패로 번지지 않게 하는
보조 장치다.

**한계**: 네트워크 장애를 없애는 게 아니라 장애가 빌드 실패로 번지는 창을 좁힌다.

## 3. frontend compose 잔재 — 하루 전 화면을 현재 코드로 착각

### 증상

프론트 코드에서 주석 처리된 "AI 추천 액션" 배너가 브라우저에는 그대로 보였다.
컨테이너는 멀쩡히 떠 있었다.

### 원인

`43c8a50`에서 Dockerfile을 nginx 멀티스테이지(`pnpm build` → `dist`)로 바꿨는데
compose를 안 고쳐 `./frontend:/app` 볼륨과 `API_PROXY_TARGET`이 남아 있었다.
nginx는 `/usr/share/nginx/html`을 서빙하므로 **둘 다 무의미한데, 주석은 "HMR"이라고
말한다.** 그래서 "마운트가 있으니 반영됐겠지"라고 믿고 옛 이미지를 검증하게 된다.

허영주님이 [2026-07-17 OCI 런북](../../document_허영주/2026-07-17-oci-deployment-runbook.md)에
이미 지적해 둔 항목이다. 이번에 실제로 밟았다.

### 수정

죽은 볼륨·환경변수 제거, 주석을 사실대로 교체. `DOCKER.md`의
"db/redis/kafka를 앱이 안 쓴다"는 서술도 정정했다 — db/redis는 이제 실제로 쓰고
(JPA·Redis 의존성 존재) kafka만 여전히 미사용이다.

프론트 화면을 바꿨으면 반드시:

```bash
docker compose up -d --build frontend
```

## 4. 스토리지 미설정 환경에서 정상 요청마다 ERROR 스택트레이스

### 증상

`.env`의 `STORAGE_ACCESS_KEY`/`STORAGE_SECRET_KEY`가 비어 있으면 `/me` 요청마다

```
NullPointerException: Access key ID cannot be blank
```

가 ERROR 레벨로 쌓인다. 화면은 멀쩡하다(아바타만 안 보임).

### 원인

`S3StorageClient`는 앱이 뜨는 것 자체는 막지 않으려고 자격증명 검증을 요청 시점으로
미뤄뒀다. 의도는 맞다. 다만 아바타 서명 URL은 **`/me` 응답마다** 발급되므로,
"설정 안 함"이 요청 건당 예외로 번역된다.

### 수정

판단을 클라이언트 자신에게 뒀다. 자격증명 미설정은 장애가 아니라 그 환경의 **상태**다.

```java
public String createSignedUrl(...) {
    if (!configured) {
        return null;
    }
```

- 읽기(서명)만 완화. `upload`/`delete`는 그대로 던진다 — 쓰기 실패는 사용자가 알아야 한다.
- `TaskResultController.getFileUrl`은 그 null을 200에 실어 보내면 프론트가 null을 URL로
  받게 되므로 `503 STORAGE_NOT_CONFIGURED`로 명시했다.

가드를 `MeController`에 두는 안은 버렸다. `@MockitoBean S3StorageClient`가 기본 false를
돌려줘 기존 테스트 3개가 깨지고, 무엇보다 설정 판단이 컨트롤러로 새어나간다.
