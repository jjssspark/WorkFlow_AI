# 같은 내용이 여러 벌 색인돼 근거 칸을 잡아먹던 문제

- 발견: 2026-08-01 (하이브리드 RAG 마무리 중 남은 한계 점검)
- 조치: 검색 단계에서 내용이 같은 청크를 한 건으로 접고, 접힌 칸을 다른 근거로 채운다
- 상태: 운영 30문항 기준 낭비 슬롯 12칸 → 0칸, Hit@5 회귀 없음

## 증상

운영(OCI) `project_id=1`의 378청크 중 **잉여가 109건(28.8%)** 이었다.

```
고유 content 269종 / 중복 그룹 54개
중복에 걸린 행 163건, 이 중 잉여 109건
```

사용자에게 보이는 결과: 상위 5칸이 같은 문장으로 채워져 근거가 줄어든다.

```
상위 5칸에 중복이 낀 문항: 10/30 (33%)
낭비된 슬롯: 12칸

B05  5칸 반환 → 고유 3개    근거 40% 손실
C08  5칸 반환 → 고유 3개
```

mixed 카테고리는 10문항 중 7문항이 걸렸다.

## 원인은 코드가 아니다

중복이 어느 축에서 생기는지부터 나눠 봤다. 축이 다르면 고칠 곳도 다르기 때문이다.

```
A. 같은 source 안에서 content 반복        0개    <- 청킹 결함이면 여기 잡힌다
B. 서로 다른 source 가 같은 content      54개
C. 재색인이 겹쳐 쌓인 것                  0개    <- 삭제 누락이면 A 로 잡힌다
```

**A가 0개다.** 청킹·인제스트·삭제 로직에는 결함이 없다. B의 실체를 추적했다.

```
content 이 같은 action_item 5건
  id 375 → meeting 61    (7/26)
  id 422 → meeting 62    (7/27)
  id 506 → meeting 77    (7/27)
  id 574 → meeting None  (7/27)
  id 695 → meeting 112   (7/30)

회의별 분석 실행 수: 전부 1회
```

**같은 회의를 여러 번 분석한 게 아니라, 같은 회의록을 서로 다른 회의로 반복 업로드한 것이다.**
각 회의는 정확히 한 번씩만 분석됐고 RAG 는 시킨 대로 색인했다. 데모 데이터를 만들면서
같은 대본을 여러 번 올린 흔적이다.

즉 **상류에 고칠 코드가 없다.** 그리고 이 입력은 막을 수도 없다 - 같은 정기회의를 매주
올리면 운영에서도 정상적으로 같은 일이 생긴다.

## 조치 — 검색이 방어한다

원인이 코드 밖에 있어도, 사용자에게는 근거 5개를 줘야 한다. `search_similar_chunks` 가
넉넉히 받아(`top_k × 4`, 상한 40) 내용이 같은 청크를 접고 상위 `top_k` 를 돌려준다.

접는 기준은 **content** 다. 중복이 서로 다른 `source_id` 로 들어와 있어
`(source_type, source_id)` 로는 하나도 안 걸린다. 반대로 긴 업무 설명이 여러 청크로
쪼개진 경우는 content 가 서로 달라 잘못 합쳐지지 않는다.

남길 대표는 `(source_type, source_id)` 최솟값으로 고정했다. 내용이 같으면 임베딩도 같아
유사도가 완전 동률이라, 정해두지 않으면 DB 가 돌려주는 순서에 따라 매번 다른 행이 남는다
- 출처 목록이 흔들리고 답변 캐시와 평가 재현이 어긋난다.

회의록 최소 슬롯 예약(`MEETING_MIN_RESERVED`)은 **접은 뒤에** 판단한다. 접기 전에 보면
같은 회의록이 여러 벌 들어온 것을 "회의록은 이미 있다"로 읽어 예약을 건너뛴다.

SQL `DISTINCT ON` 대신 파이썬에서 고른 이유: 444행 순차 스캔이 1ms 미만이고,
`DISTINCT ON (content)` 는 content 우선 정렬을 강제해 유사도 순서를 깨뜨린다.

## 결과

| | 전 | 후 |
| --- | --- | --- |
| 중복이 낀 문항 | 10/30 | **0/30** |
| 낭비 슬롯 | 12칸 | **0칸** |
| Hit@5 | 0.933 | **0.933** |
| identifier / mixed / semantic | 10/10, 10/10, 8/10 | **동일** |

**Hit@5 가 그대로인 것이 정상이다.** 이 지표는 "정답이 상위 5칸에 하나라도 있나"만 보므로
근거가 3개든 5개든 같은 점수가 나온다. 실제로 좋아진 것은 LLM 에 들어가는 근거의
다양성이고, **지금 평가셋으로는 그걸 측정할 수 없다.** 회귀가 없다는 것만 확인된 상태다.

측정하려면 "정답을 몇 개나 회수했는가"(recall@5)를 재는 평가셋이 필요하다. 지금 평가셋은
문항당 gold 가 최대 25청크라 그 지표가 의미를 갖지 못한다.

캐시 스키마 버전을 v14 → v15 로 올렸다. 안 올리면 30분 TTL 동안 같은 문장이 여러 번
실린 옛 답변이 계속 나간다.

## 되돌리는 법

`revert` 커밋 하나. 스키마도 데이터도 건드리지 않는다. 캐시 버전은 `v14` 로 되돌리는 것이
맞다 - 살아남은 `v14` 항목은 전부 옛 코드가 만든 것이다.

## 남는 것

- 운영 데이터의 중복 자체는 그대로 있다. 검색이 가릴 뿐이다. 데모 데이터를 정리하려면
  별도 판단이 필요하다(운영 행 삭제라 사용자 확인 대상).
- `meeting_action_items` 에 `meeting_id` 가 NULL 인 행이 116건 있다. 이번 문제와는 별개이고
  원인을 확인하지 않았다.
