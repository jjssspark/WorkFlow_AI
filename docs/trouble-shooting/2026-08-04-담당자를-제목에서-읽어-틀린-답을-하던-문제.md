# 어시스턴트가 담당자를 제목에서 읽어 틀린 답을 하던 문제

- 발견: 2026-08-04 (DB 초기화 후 `3번 업무 담당자 알려줘` 확인 중)
- 증상: 담당자가 박지수로 배정된 업무에 대해 어시스턴트가 "담당자는 미정입니다"라고 답한다
- 상태: 해결. 어시스턴트(01:47 배포)와 회의록 파서(02:52 배포) 양쪽을 고치고 운영에서 확인함

## 증상

같은 업무를 물었는데 항목에 따라 답이 갈렸다.

```
"3번 업무의 우선순위는 뭐야"   ->  "- MEDIUM"              정답
"3번 업무의 담당자는 누구야"   ->  "담당자는 미정입니다."     오답 (실제: 박지수)
"3번 업무 담당자 알려줘"       ->  "근거 없음: 관련 자료를 찾지 못했습니다"
```

같은 원인인데 문구에 따라 오답과 근거 없음으로 갈린다. **근거 없음보다 오답이 나쁘다.**
사용자는 틀린 줄 모른다.

## 검색은 정상이었다

API 응답 원문을 잡아 확인했다(브라우저에서 `fetch` 를 후킹, 확인 후 원복).

```json
{
  "message": "담당자는 미정입니다.",
  "sources": [
    { "source_type": "task", "source_id": 3, "similarity": 0.4026,
      "content_snippet": "담당 미정 · 삭제된 심사자 계정 3개를 다시 만들지 결정 · 심사 일정 전까지" }
  ]
}
```

`3번` -> `task#3` 라우팅은 1순위로 정확히 걸린다. 구조화 조회도 살아 있다(우선순위 MEDIUM 정답).
**고장난 건 검색이 아니라 컨텍스트에 담당자가 없다는 것이었다.**

## 원인 1 — 담당자가 어디에도 실리지 않는다

색인 본문을 만드는 두 곳 모두 제목과 설명만 넣는다.

```java
// TaskController.buildRagContent, MeetingAnalysisService.buildTaskIngestContent
return task.getTitle() + " - " + task.getDescription();
```

검색 후 사실값을 붙이는 `task_facts_service` 도 담당자를 빼먹었다.

```python
SELECT id, due_date, status, priority FROM tasks    # 담당자 없음
```

이 서비스는 **정확히 이 문제를 위해** 만들어졌다. 파일 주석에 "마감일·상태·우선순위는
테이블에만 있어 붙여주지 않으면 근거 없음으로 답한다"고 적혀 있다. 담당자만 빠졌다.

## 원인 2 — 제목에 "담당 미정"이 박혀 있다

여기가 진짜 뿌리다. 배포되는 회의록 양식의 실행항목 표 헤더가 이렇다.

```
우선순위                      | 내용 (누가 · 무엇을 · 언제까지)
[ ] 긴급 [v] 보통 [ ] 낮음     | 고무서 · 관리자와 구글 계정으로 로그인되는지 확인 · 배포 당일
[ ] 긴급 [v] 보통 [ ] 낮음     | 담당 미정 · 삭제된 심사자 계정 3개를 다시 만들지 결정 · 심사 일정 전까지
```

`·` 로 세 칸을 나눠 쓰라는 것은 **우리가 정한 규격**이다. 그런데 파서는 그 칸을 통문장으로 받았다.

```python
# app/main.py  build_todos_from_action_items
title = shorten(clean_todo_title(sentence) or sentence, 44)   # 셀 전체가 제목이 된다
```

여기서 세 가지가 동시에 깨졌다.

| 깨진 것 | 실제 화면 |
|---|---|
| 제목에 담당자가 박제됨 | `담당 미정 · ...`, `고무서 · ...` |
| 담당자 추출 실패 | 회의록엔 `고무서`라고 적혀 있는데 4건 전부 미배정 |
| 마감일 전부 미정 | `배포 당일`, `심사 일정 전까지` 가 제목 안에 묻혀 파싱 안 됨 |

`extract_assignee_candidate`(main.py)는 `OO가 ~한다` 와 `담당: OO` 패턴만 본다.
`고무서 · 관리자와...` 는 안 걸린다.

**미배정의 원인은 이름 필터가 아니라 추출 실패 하나였다.** 조사 중 "참석자 미지정 시
`resolve_participants` 의 `팀장/팀원` 기본값 때문에 이름이 지워진다"고 판단했으나 틀렸다.
이 경로는 `request.participants` 를 그대로 넘기고, 비어 있으면 `_allowed_assignee_names`
가 `None` 을 돌려줘 필터 자체가 걸리지 않는다.

## 왜 배정해도 안 바뀌는가

제목은 **문자열**이고 배정은 **별개 필드**다. 역할분배 화면에서 박지수를 배정해도
제목의 "담당 미정"은 그대로 남는다. 둘은 영원히 어긋난다.

어시스턴트는 제목만 읽으므로 배정 결과가 아니라 회의록 작성 시점의 문구를 답한다.

## 조치 1 — 어시스턴트 (2026-08-04 01:47 배포)

`task_facts_service` 에 담당자 이름을 붙인다. `users` 를 조인해 `assignee_name` 을 가져오고,
출처 줄 끝에 `담당자: 박지수` 로 적는다. 액션아이템은 `final_assignee_id` 를 쓴다 —
`recommended_assignee_id` 는 AI가 뽑은 후보라 사람이 확정한 값과 어긋날 수 있다.

**재임베딩은 필요 없다.** 담당자를 임베딩에 굽지 않고 검색 후 조회로 붙이기 때문이다.
마감일을 그렇게 만든 이유와 같다. 배정이 바뀌어도 항상 최신값이 나온다.

마감일·상태와 달리 담당자는 값이 없어도 출처 줄에서 빼지 않고 `미배정` 으로 적는다.
조용히 빼면 모델이 다시 제목에서 담당자를 주워 와 같은 버그가 재발한다. 배정이 없다는 것
자체가 답할 근거다.

같은 배포에 출처 머리말 표시도 넣었다. 지목된 업무는 검색 결과 맨 앞에 놓이지만 같은 모양의
줄이 다섯 개 나열되면 모델이 순서를 근거로 삼지 않는다.

```
[출처 1 - task#3 ← 질문이 지목한 업무] ... (담당자: 박지수, 상태: todo)
[출처 2 - task#4] ... (담당자: 고무서, 상태: todo)
```

표시는 시스템이 대괄호 안에만 넣고, 대괄호 밖 본문의 같은 문구는 표시로 취급하지 말라고
시스템 프롬프트에 못 박았다. 안 그러면 표시 자체가 주입 경로가 된다.

## 조치 2 — 회의록 파서 (2026-08-04 02:52 배포)

`split_todo_cell` 이 실행항목 칸을 `(누가, 무엇을, 언제까지)` 로 한 번에 나눈다. 제목·담당자·
마감일 세 소비처가 각자 나누면, 한쪽만 고쳤을 때 제목에서는 뗀 칸을 담당자 쪽은 그대로 읽는
식으로 조용히 어긋난다.

**누가** — 세 가지를 구분한다. 뭉개면 작성자 의도를 뒤집는다.

| 값 | 뜻 |
|---|---|
| 이름 | 작성자가 지목한 사람 |
| `""` | "담당 미정"이라고 명시했다. 여기서 끝이고 문장을 더 뒤지지 않는다 |
| `None` | 이름 자리가 없다(양식 미준수). 기존 문장 추출로 넘어간다 |

**무엇을** — 제목으로 쓴다.

**언제까지** — 이 칸의 날짜는 문맥 검사 없이 마감일로 받는다. `sanitize_due_date` 는
마감·완료·까지 같은 문맥 키워드가 곁에 있어야 날짜를 인정하는데, 그 방어막은 회의 일자
헤더를 마감일로 오인하지 않으려는 **자유 서술용**이다. 지정된 칸 안의 날짜는 추측이 아니라
선언이므로 문맥을 요구할 이유가 없다. 칸 밖의 날짜는 기존 방어막을 그대로 받는다.

떼어내는 조건은 좁게 잡았다. 첫 칸은 미배정 표기이거나 2~4자 한글 이름일 때만, 마지막 칸은
담당자 칸이 확인됐거나(양식을 지킨 문서) 날짜·기한 표현일 때만 뗀다. 양식을 안 지키고 `·` 로
문장을 이어 적은 경우 잘라내면 업무 내용이 소리 없이 사라진다. 떼고 남는 게 없으면 원문을
지킨다 — 제목이 빈 문자열이 되느니 지저분한 편이 낫다.

`description` 과 `evidence_text` 는 원문을 지킨다. 회의록에 뭐라고 적혔는지 되짚을 수
없게 되면 안 된다.

LLM 경로에도 같이 넣었다. 프롬프트가 원문 복사를 금지하지만 모델은 자주 어기고, 베낀 경우
같은 증상이 그대로 재현된다.

## 운영 확인 결과

배포된 서버에 같은 문서를 새로 올려 확인했다.

```
고무서    | 마감 08.10 | 관리자와 구글 계정으로 로그인되는지 확인
고무서    | 마감 08.10 | 초대 화면에서 링크 복사 버튼이 사라졌는지 …
(미배정)  | 마감 08.12 | 삭제된 심사자 계정 3개를 다시 만들지 결정
```

어시스턴트도 같은 데이터로 확인했다.

```
"7번 업무의 담당자는 누구야"        -> 박지수        정답
"TASK-6 담당자와 우선순위 알려줘"   -> 고무서 / MEDIUM  정답
```

7번이 결정적이다. 업무 4건 중 3건이 고무서 담당이고 출처에 그 업무들이 같이 실렸는데도
소수 쪽인 박지수를 골랐다.

## 판단이 틀렸던 지점

조치 1 배포 직후 `3번 업무의 담당자는 누구야` 가 여전히 옆줄 담당자("고무서")를 집어왔다.
이를 보고 **출처 머리말 표시가 효과 없다고 판단해 "지목된 업무를 단독 블록으로 분리"하는
추가 작업을 제안했으나, 성급했다.**

표시가 안 먹힌 게 아니라 제목에 박힌 `담당 미정`·`고무서 ·` 글자가 더 셌던 것이다.
당시 컨텍스트에는 `고무서` 가 제목 2건·인사말·출처 담당자에 반복 노출돼 있었다.
조치 2로 제목 오염을 걷어내자 추가 작업 없이 해결됐다. 단독 블록 분리는 하지 않았다.

**증상이 남았다고 직전 수정이 무효인 것은 아니다.** 오염원이 둘일 때 하나만 걷으면
증상은 그대로다.

## 되돌리는 법

어시스턴트 조치는 `task_facts_service._TASK_FACTS_SQL` 의 조인과
`generation_service._FACT_LABELS`·`_reference_mark` 를 빼면 원래대로 돌아간다.
파서 조치는 `split_todo_cell` 호출부를 원문 그대로 넘기도록 되돌리면 된다.
스키마도 색인도 건드리지 않으므로 양쪽 다 되돌림 비용이 없다.

이미 등록된 업무의 제목은 바뀌지 않는다. 새로 분석하는 회의록부터 적용된다.

## 남은 함정

**운영 서버 로그를 못 봤다.** SSH 실행이 차단돼 브라우저에서 응답을 가로채는 방식으로
확인했다. `ids_referenced` / `id_miss` 카운터 검증은 아직 못 했다.

**LLM 경로 테스트가 처음에 거짓 초록불이었다.** 회의록 원문에 없는 To-Do 는 지어낸 것으로
보고 통째로 대체되는데, 테스트에 원문을 넣지 않아 제목이 고쳐진 게 아니라 다른 업무로 갈려서
통과했다. 원문 To-Do 가 유지됐는지 먼저 단언하도록 고쳤다. 이 경로를 테스트할 때는
`source_text` 에 대상 문장이 있어야 한다.
