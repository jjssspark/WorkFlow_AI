# 요약 안전성 문항이 원문에 따라 답을 뒤집은 문제

- 발견: 2026-08-17 (요약 지표의 반반 평균 허점을 고치고 재측정하던 중)
- 증상: 지어낼 것이 없는 규칙 기반 요약까지 "환각 안 했는가" 문항에서 떨어진다
- 상태: 해결(해당 축을 LLM 심사에서 문자열 검사로 옮김)

## 증상

요약 점수를 충실도 × 안전성으로 나눠 4개 provider 를 재측정했더니 안전성이 전부 낮았다.

```
provider         충실도     안전성      종합
huggingface    1.000   0.417   0.417
ollama         0.833   0.500   0.333
rule_based     0.917   0.417   0.333
auto           1.000   0.417   0.417
```

**규칙 기반이 0.417 인 것이 앞뒤가 안 맞는다.** 규칙 기반 요약은 날짜도 사람 이름도
쓰지 않는다. 지어낼 재료가 없는데 "지어내지 않았는가"에서 절반 넘게 떨어진다.

떨어진 요약들은 하나같이 이런 모양이었다. 날짜도 이름도 하나 없다.

```
nosep-01     알림 중복 제거에 대한 회의
halluc-01    RAG 재색인 진행 상황 공유
formal-01    임베딩 모델 교체 후 검색 정확도 감소와 재색인 필요성 논의
```

## 가설을 두 번 틀렸다

### 1차: "공허참(vacuous truth) 함정이다"

요약에 날짜가 하나도 없으면 "요약에 적힌 날짜가 모두 원문에 나오는가"는 논리적으로
참이지만 모델이 "요약에 날짜가 없으니 아니오"로 답한다는 해석이었다.

예외를 명시한 문구를 붙여 반증을 시도했다.

```
요약에 날짜나 사람 이름이 나온다면 그것이 모두 회의록 원문에 있는 것인가?
요약에 날짜와 사람 이름이 전혀 없으면 예로 답하세요.
```

여전히 아니오였다. **여기서 "공허참이 아니다"라고 결론 냈는데, 이것도 성급했다.**
그 문구 하나가 나빴을 뿐일 수 있는데 가설 전체를 버렸다.

### 2차: "문구를 바꾸면 된다"

대조 입력 세 개(날짜·이름 없음 / 원문과 일치 / 지어냄)로 문구 후보를 재봤다.
원문은 짧은 합성 문장 하나로 고정했다.

| 문항 | 날짜·이름 없음 | 원문과 일치 | 지어냄 |
|---|---|---|---|
| `요약에 적힌 날짜와 사람 이름이 모두 회의록 원문에 나오는가` | 아니오 | 아니오 | — |
| `요약에 나오는 날짜와 사람 이름을 회의록 원문에서 모두 찾을 수 있는가` | **예** | **예** | **아니오** |

`나오는가` → `찾을 수 있는가` 차이로 세 경우를 다 맞혔다. 이걸 정답으로 보고
픽스처 41건에 적용하고 재측정했다.

```
ollama       0.500 -> 0.833
rule_based   0.417 -> 0.583
huggingface  0.417 -> 0.417   <- 그대로
```

**HF 는 꿈쩍도 안 했다.** 그 5건은 여전히 요약에 날짜도 이름도 없는데 안전성 0 이었다.

## 원인

같은 요약 문장에 원문만 바꿔 넣어봤다.

| 요약 (날짜·이름 없음) | 원문 | 답 |
|---|---|---|
| `알림 중복 발송 원인을 파악하고 중복 제거 로직을 적용하기로 했다` | 짧은 합성 원문 | 예 |
| `알림 중복 발송 원인을 파악하고 중복 제거 로직을 적용하기로 했다` | 실제 `nosep-01` 원문 | **아니오** |

결정사항 유무, 원문 유무를 따로 떼어 세 조합을 돌려도 실제 원문에서는 전부 아니오였다.

`nosep-01` 원문에는 날짜와 이름이 잔뜩 들어 있다.

```
박지수: 최근 사용자들이 같은 알림을 여러 번 받는다는 문의가 늘고 있습니다.
유소은: 알림 발송 큐에서 중복 삽입이 일어나는 것 같습니다.
박지수가 알림 중복 원인을 8월 14일까지 파악하기로 했다
유소은은 중복 제거 쿼리를 검토한다
```

**원문에 날짜·이름이 많으면 심사기가 대조 방향을 뒤집어 읽는다** — "원문엔 있는데
요약엔 없네" 로 판단해 아니오를 낸다. 요약→원문 방향으로 물었는데 원문→요약으로 답한다.

문구를 아무리 다듬어도 원문 구성에 따라 뒤집히므로, 이 축을 LLM 문답으로 재는 한
재현되지 않는다.

## 해결

안전성 축을 LLM 심사에서 떼어내 문자열 검사로 옮겼다(`meeting_eval/safety_check.py`).

- 요약과 원문에서 날짜를 정규식으로 뽑아 `(월, 일)`로 정규화한 뒤 집합 차를 본다
- 표기가 갈려도(`8월 10일` vs `8/10` vs `2026-08-10`) 같은 날이면 같은 값이다
- 지어낸 날짜가 하나라도 있으면 0, 없으면 1

체크리스트에는 판단이 필요한 문항만 남겼다. `'다음 주쯤'이 특정 날짜로 바뀌지 않고
남아 있는가` 같은 케이스별 제약은 앞선 측정에서 정확히 작동했으므로 그대로 둔다.
최종 안전성 = 문자열 검사 × 남은 안전성 문항 통과율.

### 사람 이름은 재지 않기로 했다

이름도 같이 검사하려 했다. 성씨 목록으로 요약에서 세 글자 이름을 뽑았더니 이렇게 나왔다.

```
요약: "알림 중복 원인을 정리해 문서로 남기기로 했다."
잡힌 이름 후보: ['정리해', '문서로', '남기기']
```

형태소 분석 없이 한국어에서 미지의 이름을 가려낼 방법이 없다. 담당자 환각이라는 실제
위험은 구조화된 필드를 대조하는 `todo_scorer` 의 `assignee_accuracy` 가 이미 정확히
재고 있어, 여기서 못 미더운 값을 하나 더 만들지 않기로 했다. **재는 척하는 것이
안 재는 것보다 나쁘다.**

## 검증

`tests/meeting_eval/test_safety_check.py` 7건. 날짜 없음 / 원문에 있는 날짜 /
원문에 없는 날짜 / 표기가 다른 같은 날 / ISO 표기 / 막연한 시점 표현 / 다건 환각.
LLM 호출이 없어 매번 같은 값이 나온다.

## 되돌리는 법

`safety_check.py` 를 지우고 `summary_judge.judge_summary` 에서 곱하는 항을 빼면
체크리스트 문항만으로 안전성이 계산된다. 픽스처에서 뺀 문항은 해당 커밋을 되돌리면
돌아온다.

## 남은 함정

**충실도 축의 변별력이 약하다.** 12건 중 11건이 모든 provider 에서 1.00 이다.
규칙 기반 요약("OCI 배포 리허설 회의")까지 충실도 0.917 을 받는다. 안전성을 고쳤으니
다음은 이쪽인데, 이 축은 판단 문제라 문자열 검사로 옮길 수 없다.

**날짜 표기 `8.10` 은 인식하지 않는다.** 버전 번호·소수와 구분되지 않아 뺐다.
회의록에 그 표기가 쓰이기 시작하면 환각을 놓친다.

## 배운 점

**대조군을 실제 데이터로 만들어야 한다.** 짧은 합성 원문에서 세 경우를 다 맞힌 문항이
실제 케이스에서 전부 무너졌다. 계측기를 고칠 때 계측 대상과 다른 데이터로 검증하면
고쳤다는 착각만 얻는다.

**가설을 반증할 때도 한 번의 실험으로 끝내면 안 된다.** 공허참 가설을 문구 하나로
기각했는데, 결과적으로 방향은 절반쯤 맞았다. 기각의 근거가 "이 문구도 실패했다"였는데
그건 문구가 나쁠 가능성과 구분되지 않았다.

**LLM 심사기는 판단에만 쓴다.** 문자열 대조로 답할 수 있는 것을 모델에게 물으면
정확도를 잃고 재현성도 잃는다. 이 작업에서 계측기 결함이 다섯 번 나왔는데
(심사기에 원문 미전달, 출력 상한 잘림, 정답 0건 채점 불능, 폴백 혼입, 이번 건)
그중 둘이 "모델에게 묻지 말았어야 할 것을 물어서" 생겼다.
