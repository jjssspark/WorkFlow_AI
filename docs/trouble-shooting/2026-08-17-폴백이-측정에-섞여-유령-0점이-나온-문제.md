# provider 폴백이 측정에 섞여 유령 0점이 나온 문제

- 발견: 2026-08-17 (문서형 회의록 To-Do 누락을 고치기 전, 베이스라인 재현 측정 중)
- 증상: 정답 4건짜리 평가 케이스가 F1 0.000 으로 찍히는데, 같은 입력을 모델에 직접 넣으면 4건을 정확히 뽑는다
- 상태: 측정 쪽만 해결(평가 스크립트가 폴백을 표시하게 함). 프로덕션의 조용한 폴백은 그대로 남아 있음

## 증상

`doc-multi-01`(문서형 회의록, 정답 To-Do 4건)의 점수가 이렇게 나왔다.

```
doc-multi-01         golden=4 pred=1 f1=0.000 recall=0.000
    회의내용 - 재설정 메일이 스팸함으로 분류되…[-/-]
```

문서형 8건 평균도 F1 0.625 로, 하루 전 실험 기록의 0.750 과 어긋났다.
아직 프롬프트를 한 글자도 안 고친 상태였다.

예측 제목에 `회의내용 - ` 이라는 **섹션 라벨**이 붙어 있는 것이 유일한 단서였다.
LLM 은 저런 제목을 만들지 않는다.

## 첫 가설은 틀렸다

"문서형 다건 회의록에서 모델이 To-Do 를 못 뽑는다"고 봤다. 그날 고치려던 것이 문서형
누락이었으니 자연스러운 해석이었고, **틀렸다.**

같은 케이스를 HF 에 직접 던져 원 응답을 봤다.

```json
"todos": [
 {"title": "메일 템플릿 정리하기", "assignee_candidate": "박지수", "due_date": "2026-08-18", ...},
 {"title": "발신 도메인 인증 확인하기", "assignee_candidate": "유소은", "due_date": "2026-08-19", ...},
 {"title": "재설정 토큰 정책 검토하기", "assignee_candidate": "허영주", "due_date": "2026-08-20", ...},
 {"title": "재발송 제한 로직 추가하기", "assignee_candidate": "이은주", "due_date": "2026-08-21", ...}
]
```

4건 전부 정확했다. 전체 파이프라인(`_analyze_json_uncached`)으로 2회 더 돌려도 4건이 나왔다.
즉 **모델도 파서도 멀쩡했고, 그 순간의 호출만 실패했던 것이다.**

## 원인

`_analyze_by_provider` 는 HF -> Ollama -> 규칙 기반 순으로 폴백한다.
폴백이 걸려도 반환 타입은 같은 `MeetingAnalysisResult` 라, 호출한 쪽에서는
**AI 가 분석한 결과인지 규칙 기반이 만든 결과인지 구분할 수 없다.**

흔적은 로그에만 남는다. 후속 측정에서 실제로 다시 잡힌 원문은 이렇다.

```
2026-08-17 11:46:34,309 WARNING app.main Hugging Face 회의록 분석 실패, Ollama/규칙 기반 분석으로 대체합니다. errorType=RemoteProtocolError httpStatus=N/A
2026-08-17 11:46:54,460 WARNING app.main Ollama 회의록 분석 실패, 규칙 기반 분석으로 대체합니다. errorType=ReadTimeout
```

```
2026-08-17 11:47:30,602 WARNING app.main Hugging Face 회의록 분석 실패, Ollama/규칙 기반 분석으로 대체합니다. errorType=ConnectTimeout httpStatus=N/A
2026-08-17 11:47:50,653 WARNING app.main Ollama 회의록 분석 실패, 규칙 기반 분석으로 대체합니다. errorType=ReadTimeout
```

평가 스크립트는 이 경고를 보지 않고 점수만 집계했다. 그래서 **그날의 네트워크 사정이
그대로 "품질 개선/악화"로 읽히는 구조**였다. 재시도도 없어서 한 번 끊기면 그 케이스는
규칙 기반 점수로 확정된다.

간헐적으로만 재현되는 것도 이 때문이다. 같은 스크립트를 세 번 돌리면 폴백에 걸리는
케이스가 매번 달랐다(1회차 `doc-multi-01`, 2회차 `ext-noassign-01`·`ext-none-01`·`ext-rejected-01`,
3회차 0건).

## 해결

평가 스크립트에 로깅 핸들러를 붙여 `대체합니다` 경고를 케이스 단위로 잡고,
CSV 열(`provider_fallback`)과 콘솔에 표시하게 했다.

```python
class FallbackWatcher(logging.Handler):
    def emit(self, record):
        if "대체합니다" in record.getMessage():
            self.hit = True
```

케이스마다 `hit` 를 초기화하고, 실행 끝에 폴백이 걸린 케이스 목록을 찍는다.

```
provider 폴백(측정 무효 의심) 3건 ['ext-noassign-01', 'ext-none-01', 'ext-rejected-01']
```

**저장소 코드는 건드리지 않았다.** 문제는 측정 하네스가 실패를 못 본 것이지
프로덕션 폴백 자체가 잘못 동작한 것은 아니다.

## 검증

폴백 0건으로 잡힌 실행에서만 수치를 채택했고, 그 상태로 2회 측정해 같은 값이 나왔다.

```
문서형   n= 8  F1=0.875  재현율=0.875
구어체   n=10  F1=0.900  재현율=0.975
provider 폴백(측정 무효 의심) 0건 []
```

`doc-multi-01` 은 두 번 다 F1 1.000 이었다.

## 되돌리는 법

평가 스크립트가 세션 스크래치패드에 있고 저장소에 커밋되지 않았으므로 되돌릴 것이 없다.
핸들러를 떼면 원래대로 돌아간다.

## 남은 함정 (근본 해결 아님)

**프로덕션에서도 같은 폴백이 조용히 일어난다.** 사용자가 회의록을 올렸을 때 HF 가 끊기면
규칙 기반 결과를 받는데, 화면에는 그 사실이 표시되지 않는다. 응답에 어느 경로로 분석했는지
남기지 않기 때문에 나중에 "AI 분석이 이상하다"는 제보가 와도 그때 폴백이었는지 알 수 없다.

**재시도가 없다.** `RemoteProtocolError` / `ConnectTimeout` 은 재시도 한 번이면 대부분
넘어가는 종류인데, 첫 실패에서 바로 다음 티어로 내려간다.

둘 다 이번 범위에서 고치지 않았다. 고친다면 응답에 `analysis_provider` 를 실어
보내는 쪽이 먼저다 — 관측이 없으면 재시도 정책도 근거 없이 정하게 된다.

## 배운 점

**폴백은 실패를 숨기는 장치다.** 운영에서는 그게 목적이지만, 측정 하네스에서는 정반대로
실패를 반드시 표면화해야 한다. 안 그러면 인프라 상태가 품질 수치로 둔갑한다.

**수치가 기대와 다르면 대상보다 계측기를 먼저 의심한다.** 이 회의록 분석 개선 작업에서
계측기 결함이 이번까지 네 번 나왔다(요약 심사기에 원문 미전달, 출력 상한 잘림,
정답 0건 케이스 채점 불능, 이번 폴백 혼입). 매번 "모델이 나쁘다"가 첫 가설이었고
매번 틀렸다.

**타입이 같으면 구분할 수 없다.** 성공 결과와 폴백 결과가 같은 `MeetingAnalysisResult` 로
나오는 한, 호출부는 둘을 영원히 구분하지 못한다. 로그는 호출부가 읽지 않는다.
