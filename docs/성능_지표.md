# 성능 · 품질 지표

숫자가 있어야 설계 판단에 근거가 생긴다. 여기 적힌 값은 전부 실제로 잰 것이고, 재현 방법을
같이 남긴다. **재지 못한 것은 재지 못했다고 적는다.**

측정일: 2026-08-13

## 1. 프론트엔드 번들

`App/frontend`에서 `pnpm build`. Vite 7, 모듈 4,030개, 빌드 8.14초.

| 자산 | 원본 | gzip |
| --- | --- | --- |
| `index-*.js` (메인 청크) | 2,254.84 kB | **645.85 kB** |
| `index.es-*.js` | 158.79 kB | 53.01 kB |
| `index-*.css` | 143.69 kB | 22.69 kB |
| `purify.es-*.js` | 27.95 kB | 10.57 kB |
| `MyPage-*.js` | 26.14 kB | 7.36 kB |

### 예산 대비 — 초과다

앱 페이지 JS 예산은 gzip 300 kB인데 메인 청크 하나가 **645.85 kB로 2.15배**다. Vite도
빌드 때 500 kB 초과 경고를 낸다. CSS는 22.69 kB로 예산(50 kB) 안이다.

원인은 코드 스플리팅이 없다는 것이다.

```
라우트 30개 중 React.lazy()로 감싼 것: 0개
```

`router.tsx`가 30개 라우트 컴포넌트를 전부 정적 import한다. 그래서 로그인 화면만 보는
사용자도 심사자 화면과 대시보드 차트 코드를 같이 받는다. 분리된 청크는 `MyPage` 하나뿐이고
나머지 둘은 vendor다.

**고치는 방법은 정해져 있다.** 라우트 단위 `React.lazy()` + `Suspense`. 30개 라우트 중
로그인·온보딩을 뺀 대부분이 첫 화면에 필요 없다.

지금까지 안 한 이유는 단순하다 — **재본 적이 없어서 몰랐다.** Vite가 빌드마다 500 kB 초과
경고를 찍고 있었는데 그냥 지나쳤다. 이 건은 [회고](../document_박지수/회고.md)에도 적어 뒀다.

## 2. 배포본이 실제로 내려주는 양 — 압축이 꺼져 있다

빌드 산출물 크기보다 **사용자가 실제로 받는 바이트**가 중요하다. 배포된 사이트를 직접 쟀다.

```bash
curl -s -I -H "Accept-Encoding: gzip, br" https://t3-workflow-ai.site/assets/index-CT6CN-uR.js
```

```
server: nginx/1.27.5
content-type: application/javascript
content-length: 2290185
```

**`content-encoding` 헤더가 없다.** `Accept-Encoding: gzip, br`을 보냈는데도 응답에 압축
표시가 없고, `content-length`가 빌드 원본과 같다. 즉 **gzip이 걸려 있지 않다.**

| 자산 | 실제 전송 | gzip 적용 시 |
| --- | --- | --- |
| 메인 JS | 2,290,185 B | 약 646 kB |
| CSS | 143,202 B | 약 23 kB |
| HTML | 791 B | 약 0.5 kB |
| **합계** | **약 2.43 MB** | **약 670 kB** |

원인도 확인했다. `App/frontend/nginx.conf`와 `nginx.prod.conf` **둘 다 `gzip` 지시어가
없다.** nginx 기본값은 `gzip off`이므로 설정하지 않으면 압축은 일어나지 않는다.

설정 한 줄이면 **전송량이 3.6배 줄어든다.** 코드 스플리팅보다 먼저 해야 할 일이다 —
코드를 한 줄도 안 고치고 얻을 수 있는 이득이 더 크다.

> 이 문서를 쓰면서 발견한 것이라 아직 고치지 않았다. 운영 nginx 설정 변경이라 팀과
> 합의가 필요하다.

## 3. 응답 시간

같은 배포본에 대한 실측(3회, 서울에서 OCI).

| 대상 | TTFB | 총 시간 |
| --- | --- | --- |
| `/` (HTML 791 B) | 0.127 / 0.135 / 0.178 s | 동일 |
| 메인 JS (2.29 MB) | — | 0.432 / 0.453 s |

TTFB 130~180ms는 정적 서빙으로 정상 범위다. **병목은 서버 응답이 아니라 전송량**이라는 게
숫자로 보인다. 위 2번을 고치면 메인 JS 시간이 그대로 줄어든다.

재현:

```bash
curl -s -o /dev/null -w "TTFB %{time_starttransfer}s  총 %{time_total}s\n" https://t3-workflow-ai.site/
```

## 4. 타임아웃 값의 근거 — 다 재고 정한 것이다

설정 파일의 숫자들은 감으로 넣은 게 아니다. 실측이 주석으로 같이 남아 있다.

### 어시스턴트 read timeout: 45초 → 120초

```yaml
read-timeout-seconds: ${WORKFLOW_AI_READ_TIMEOUT_SECONDS:45}
# 어시스턴트는 회의록 분석과 걸리는 시간이 다르다(생성 LLM 한 번이 통째로 들어간다).
# 45초는 로컬 ollama 콜드 44.6초와 사실상 같은 값이라 첫 질문이 상시 실패했다.
assistant-read-timeout-seconds: ${WORKFLOW_AI_ASSISTANT_READ_TIMEOUT_SECONDS:120}
```

**로컬 ollama 콜드 스타트 실측 44.6초**, 타임아웃 45초. 0.4초 차이라 첫 질문이 사실상 항상
실패했다. "느려서 늘렸다"가 아니라 **44.6초를 재고 나서 45초가 왜 실패하는지 알고 늘린 것**이다.

### ollama keep_alive: 5분 → 30분

```python
# ollama가 답변 후 모델을 메모리에 붙들고 있을 시간. 기본값(5분)이면 잠깐만 안 물어봐도
# 모델이 내려가서, 다음 질문에 로드 시간(로컬 실측 약 11초)이 통째로 붙는다.
rag_ollama_keep_alive: str = "30m"
```

**모델 로드 실측 약 11초.** 어시스턴트는 회의 중 띄엄띄엄 쓰는 화면이라 5분 간격을 넘기기
쉽고, 그때마다 11초가 그대로 붙는다.

### Redis 소켓 타임아웃: 2초 / 무제한 분리

```python
REDIS_SOCKET_TIMEOUT_SECONDS = 2.0
# 큐 전용 클라이언트는 LLM 응답이 끝날 때까지 소켓을 열어둔다
QUEUE_SOCKET_TIMEOUT_SECONDS = None
```

일반 조회는 2초로 조이고, 큐 소비(`XREADGROUP BLOCK`)만 무제한으로 뺐다. 하나로 뒀으면
응답 생성 도중 소켓이 끊긴다.

## 5. 벡터 검색 — 인덱스를 지운 근거

`document_chunks`의 ivfflat 인덱스를 제거했다. 판단 근거가 전부 실측이다.

| 항목 | 값 |
| --- | --- |
| 대상 행 수 | 444행 |
| ivfflat 설정 | `lists=100` (권장값은 행수/1000 ≈ 1) |
| 실질 후보 수 | `probes=1` × 목록당 4.4건 ≈ **4건** |
| `pg_stat_user_indexes` | `idx_scan=33`, `idx_tup_read=119` → **스캔당 3.6건** |
| 인덱스 없는 순차 스캔 | **2ms** (다른 측정 3.2ms) |

`LIMIT 5`를 요청해도 2~3건만 돌아오고 있었다. 순차 스캔이 2ms면 **이 규모에서 인덱스가 주는
속도 이득은 없고 정확도만 깎인다.** 그래서 지웠다.

재도입 기준도 숫자로 박아 뒀다 — `document_chunks`가 **1만 건**을 넘어 순차 스캔 지연이
체감되면 HNSW + `iterative_scan`으로 재검토한다. 자세한 내용은
[DB 스키마 문서](DB_스키마.md)에 있다.

## 6. 테스트 규모

재집계일: 2026-08-22 (이 절만 다시 셈. 08-13 이후 테스트가 추가돼 이전 값과 다르다)

| 계층 | 건수 | 성격 |
| --- | --- | --- |
| Spring | 874 | 소스의 `@Test` 871 + `@ParameterizedTest` 3 |
| FastAPI | 762 | **CI가 실행 건수로 강제하는 하한** (정의는 `def test_` 717개, parametrize로 실행 시 늘어남) |
| Frontend | 634 | 소스의 `it()`/`test()` 집계 |
| **합계** | **2,225** | 세 계층 |

Spring 값을 셀 때 `@Test`만 문자열로 찾으면 `@Testcontainers`(6) · `@TestPropertySource`(13)까지
같이 잡혀 890으로 부풀려진다. 뒤에 문자가 붙지 않는 `@Test`만 세야 871이다.

FastAPI만 CI가 실제 실행 건수를 검증한다. pytest는 파일이 통째로 수집되지 않아도 통과로
끝나기 때문이다. 자세한 건 [README 테스트 절](../README.md#테스트) 참고.

## 7. 재지 못한 것

정직하게 남긴다. 아래는 **측정하지 않았고, 따라서 이 문서에 숫자가 없다.**

| 항목 | 왜 못 쟀나 |
| --- | --- |
| 회의록 분석 종단 소요 시간 | 전체 스택 + LLM 제공자가 살아 있어야 한다. 로컬에서 재면 제공자·하드웨어가 달라 운영 값과 무관한 숫자가 나온다 |
| Lighthouse / Core Web Vitals | 로그인 뒤 화면이 대부분이라 공개 URL 하나로는 실제 사용 화면을 못 잰다 |
| API 엔드포인트별 응답 분포 | 운영 DB에 부하를 주지 않고 잴 방법이 없다. APM이 붙어 있지 않다 |
| DB 쿼리 실행 계획 | 운영 데이터 규모가 있어야 의미가 있는데 로컬은 비어 있다 |

이 중 **회의록 분석 종단 시간이 가장 아쉽다.** 비동기 큐로 옮긴 판단의 근거가 "수십 초
걸린다"인데, 실제 분포(중앙값·p95)가 있으면 그 결정이 훨씬 단단해진다. 운영에 APM이나
구조화 로그 타이밍을 붙이는 게 다음 순서다.
