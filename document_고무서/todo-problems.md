## 1. 배포할 때마다 20~40초 다운타임 (우선순위: 높음)

### 문제

`docker compose up -d --build`가 컨테이너를 교체하는 구조라, 컨테이너가 뜬 시점과
Spring이 요청을 받기 시작하는 시점 사이에 공백이 생긴다. 그 사이 모든 API가 502다.

### 근거

2026-07-23 PR #246 배포 중 실제 사용자 2명이 로그인 실패를 겪었다. nginx 로그:

```text
11:22:01  컨테이너 재생성
11:22:44  컨테이너 start (JVM 부팅 시작)
11:22:44~50  connect() failed (111: Connection refused) → 502 5건
          client: 221.153.94.253 (Windows), 1.220.247.75 (Mac)
11:23:05  Spring 기동 완료 (18.9초)
```

Spring 기동에만 19초가 걸리므로 이 공백은 구조적이다. 배포마다 반복된다.

### 선택지

| 안 | 내용 | 규모 | 상태 |
|---|---|---|---|
| A | 502/503/504에 "일시적, 재시도" 문구 부여 | 작음 | **완료** (`fix/api-unavailable-message`) |
| B | 로그인 등 핵심 요청에 자동 1회 재시도 | 중간 | 미정 |
| C | nginx가 백엔드 미기동 시 점검 안내 페이지 반환 | 중간 | 미정 |
| D | 무중단 배포 — 새 컨테이너가 health OK가 된 뒤 트래픽 전환 | 큼 | 미정 |

A는 오인을 없앨 뿐 다운타임 자체는 그대로다. **D가 근본 해결이다.**

### 권고

D를 하되 **단독 작업으로 분리한다.** 배포·롤백 경로는 2026-07-23에 이미 여러 번
고쳤고(3번 항목 참조) 종단 간 검증이 안 된 구간이 남아 있다. 같은 경로를 연달아
바꾸면 검증 부담이 겹친다. D 착수 전에 3번(스테이징)을 먼저 해결하는 편이 안전하다.

C는 D의 대체재가 아니라 보완재다. D를 하더라도 백엔드가 완전히 죽은 상황은 남는다.

## 2. 프론트엔드 CI가 없다 (우선순위: 높음)

### 문제

테스트 162개(28파일)가 레포에 있는데 **CI에서 아무도 실행하지 않는다.** 백엔드는
2026-07-23에 `backend-tests.yml`을 만들고 배포 게이트까지 연결했지만 프론트는 그대로다.

### 근거

```console

backend-tests.yml
deploy-oci.yml
lint-workflows.yml

$ ls App/frontend/tsconfig*
(없음)
```

백엔드에서 정확히 이 공백 때문에 운영 장애가 났다(컨텍스트 기동 실패, `@Autowired`
누락). 프론트는 같은 공백이 그대로 남아 있다.

### 선택지

| 안 | 내용 | 규모 |
|---|---|---|
| A | `frontend-tests.yml` 추가 — PR/push에서 `vitest run` + `vite build` | 작음 |
| B | A + `tsconfig.json` 도입 후 `tsc --noEmit` 추가 | 중간 |
| C | B + `deploy-oci.yml`의 `test` 잡에 프론트 포함(배포 게이트) | 중간 |

### 권고

**A를 먼저 하고, B는 별도.** tsconfig 도입은 기존 코드에서 타입 오류가 대량으로
나올 가능성이 있어 규모를 예측하기 어렵다. 먼저 A로 회귀를 막고, B는 오류 개수를
확인한 뒤 결정한다. C는 B가 안정된 다음.

## 3. 롤백의 변경 구간이 검증된 적 없다 (우선순위: 높음)

### 문제

자동 롤백 스크립트에서 **판정부는 실측했지만 실제로 시스템을 바꾸는 구간은 한 번도
실행된 적이 없다.**

```text
검증됨   : 메트릭 수집(queue/outbox), 안전 가드, 롤백 대상 태그 선택
미검증   : docker stop → git reset --hard → docker compose up -d --build
```

### 근거

2026-07-23 조사에서 롤백 스텝이 **도입 이후 한 번도 동작한 적이 없었다**는 것이
드러났다(러너에서 bash 인용 오류로 exit 2, SSH 접속 전에 사망). 문법과 Go 템플릿
변수 문제를 고쳤고 판정부는 서버에서 읽기 전용으로 실측해 BLOCKED → PROCEED로
뒤집히는 것을 확인했다. 그러나 변경 구간은 운영에서 강제 실패를 유도할 수 없어
실행해 보지 못했다.

> 참고: `deploy-last-good` 태그 부재 문제는 PR #246 배포로 해소됐다.
> 현재 `deploy-last-good = de729d7`(정상 확인된 커밋)을 가리킨다.

### 선택지

| 안 | 내용 | 규모 |
|---|---|---|
| A | 스테이징 환경 구축 후 강제 실패를 유도해 종단 간 검증 | 큼 |
| B | 운영에서 저트래픽 시간대에 의도적 실패 배포로 1회 검증 | 중간 · 위험 |
| C | 롤백 스크립트를 dry-run 플래그로 분리해 변경 구간만 시뮬레이션 | 중간 |

### 권고

**A.** B는 실제 사용자에게 다운타임을 주고, 롤백이 실패하면 복구가 더 어려워진다.
C는 시뮬레이션일 뿐 실제 `git reset --hard`와 재빌드의 부작용을 재현하지 못한다.

스테이징은 1번(무중단 배포)에도 필요하므로 두 문제가 같은 선행 조건을 공유한다.

## 6. 테스트 계정 동시 접속 제한이 시연 중 사고를 낼 수 있다 (우선순위: 중간)

### 문제

테스트 계정은 같은 계정으로 동시 로그인을 막는다. 해제는 두 경로뿐이다.

1. 로그아웃 버튼을 눌러 `/auth/test-logout` 호출
2. heartbeat가 끊긴 뒤 **TTL 40초** 경과

**브라우저 탭을 그냥 닫거나 새로고침하면 1번이 호출되지 않는다.** 그러면 40초 동안
그 계정으로 로그인할 수 없고, 사용자는 "다른 곳에서 로그인 중입니다"를 본다.

### 근거

`PresenceService.java:23` — `private static final Duration TTL = Duration.ofSeconds(40);`

2026-07-23 조사 중 이 상황을 여러 번 실제로 겪었다(`leader`, `member4`, `reviewer`).
중간보고·시연에서 발표자가 탭을 닫고 다시 열면 40초 대기가 발생한다.

### 선택지

| 안 | 내용 | 규모 |
|---|---|---|
| A | `beforeunload`/`pagehide`에서 `sendBeacon`으로 test-logout 전송 | 작음 |
| B | TTL을 10~15초로 단축 | 작음 |
| C | 같은 계정 재로그인은 기존 세션을 밀어내고 허용 | 중간 |

### 권고

**A + B.** A는 정상 종료 경로를 넓히고, B는 비정상 종료 시 대기 시간을 줄인다.
단 B만 하면 heartbeat 주기(20초)와 간격이 좁아져 오탐이 늘 수 있으므로 heartbeat
주기도 함께 조정해야 한다. C는 "동시 접속 제한"이라는 원래 의도를 없앤다 —
시연 중 두 사람이 같은 계정을 쓰는 상황을 막으려는 기능이므로 신중해야 한다.

**B를 먼저.** 벤더 청크를 분리하면 배포 시 앱 코드만 무효화되어 재방문 로딩이

우선순위는 낮다 — 현재 체감 문제로 보고된 적은 없다.

## 8. 운영에서 dev-login이 인증 없이 열려 있다 (우선순위: 높음)

### 문제

`WORKFLOW_DEMO_DEV_LOGIN_ENABLED=true`가 운영 컨테이너에 그대로 들어가 있다.
그 결과 **인증 절차 없이 누구나 유효한 JWT를 받아갈 수 있다.** 공개 도메인이므로
링크를 아는 사람이면 브라우저 주소창만으로 팀장 계정에 로그인된다.

### 근거

2026-07-25 배포(`5978597`) 직후 외부 네트워크에서 확인:

```console
$ curl -sI https://t3-workflow-ai.site/api/v1/auth/dev-login/1
HTTP/2 302
location: https://t3-workflow-ai.site/auth/callback#accessToken=<유효>&refreshToken=<유효>&expiresIn=1800

$ curl -s -o /dev/null -w '%{http_code}\n' https://t3-workflow-ai.site/api/v1/auth/dev-login-token/1
200
```

로컬 리허설에서 이 플래그를 끄면 같은 엔드포인트가 404를 반환하는 것도 확인했다.
즉 코드는 정상이고 **환경변수 하나가 게이트를 열어둔 상태**다.

로그인 화면이 테스트 계정 목록과 비밀번호(`1111`)를 공개 표시하는 것도 같은 맥락이다.
이쪽은 의도된 시연 기능이지만, dev-login과 겹치면 "계정을 아는 사람"이 아니라
"URL을 아는 사람"까지 범위가 넓어진다.

### 선택지

| 안 | 내용 | 규모 |
|---|---|---|
| A | 시연 종료 후 서버 `.env`에서 `false`로 내리고 재기동 | 작음 |
| B | 지금 즉시 끄고, 시연 시엔 test-login(계정+비밀번호) 경로만 사용 | 작음 |
| C | nginx에서 `/api/v1/auth/dev-login*` 경로를 외부에 대해 차단 | 작음 |
| D | prod 프로파일에서 이 플래그를 무시하도록 코드에서 강제 | 중간 |

### 권고

**B 또는 C를 지금, D를 다음에.** dev-login은 test-login이 있는 이상 시연에 꼭
필요하지 않다. C는 앱을 건드리지 않고 즉시 막을 수 있어 시연 일정과 무관하게 적용
가능하다. D는 "운영에서는 플래그 값과 무관하게 닫힌다"를 코드로 못박는 것이라
같은 사고의 재발을 막지만, 지금 당장의 노출을 멈추지는 못한다.

**공유 인프라 설정이라 임의로 바꾸지 않았다.** 시연 일정이 남았는지 팀 확인이 먼저다.

## 9. 어시스턴트가 집계형 질문에 "근거 없음"을 낸다 (우선순위: 중간)

### 문제

"몇 건이냐" 같은 **수를 세는 질문**에 답하지 못한다. 그런데 출처 칩은 함께 표시되어
"자료를 찾았는데 근거가 없다"는 모순된 화면이 나온다.

### 근거

2026-07-25 운영 화면 실측. 같은 세션, 같은 프로젝트에서:

```text
질문: "지금 블로커 상태인 업무가 몇 건이고 누구한테 몰려 있어?"
답변: "근거 없음: 관련 자료를 찾지 못했습니다."
출처: 5건 표시됨
(같은 화면 대시보드에는 블로커 12건이 표시 중)

질문: "마감 임박한 업무 뭐야?"  (프리셋)
답변: WF-240 업무 편중 피처 설계 및 데이터 준비, 마감 2026-07-20, inprogress …
출처: 5건
```

**검색은 되는데 집계가 안 된다.** RAG가 문서 조각을 유사도로 가져오는 구조라
"전체에서 조건에 맞는 것을 모두 세라"는 질의는 원리상 맞출 수 없다. 상위 k개만
보고 있으므로 "12건"이라는 값 자체가 컨텍스트에 들어오지 않는다.

### 선택지

| 안 | 내용 | 규모 |
|---|---|---|
| A | 집계 질의를 감지해 RAG 대신 업무 통계 API를 호출(툴 라우팅) | 중간 |
| B | 프로젝트 요약 통계(상태별 건수·담당자별 분포)를 매 질의 컨텍스트에 상시 주입 | 작음 |
| C | 근거 부족 시 출처 칩을 숨겨 모순된 화면만 없앤다 | 작음 |

### 권고

**B를 먼저, A는 이후.** B는 툴 라우팅 없이도 "블로커 12건" 같은 값이 항상 컨텍스트에
있게 만들어 흔한 집계 질문을 대부분 커버한다. 통계는 이미 대시보드가 쓰는 값이라
새로 만들 것이 없다. A는 정확하지만 라우팅 판정 로직과 오분류 처리가 붙는다.

C는 단독으로 하면 안 된다 — 화면만 정리되고 답을 못 하는 것은 그대로다.
다만 B/A와 함께 하면 "근거 없음인데 출처 5건" 같은 신뢰도 손상은 없앨 수 있다.

## 10. 같은 사용자의 역할이 화면마다 다르게 보인다 (우선순위: 중간)

### 문제

마이페이지 상단 배지는 `팀원`인데, 같은 화면의 브레드크럼과 사이드바는 `팀장`이다.
같은 로그인 세션, 같은 사용자다.

### 근거

2026-07-25 운영 화면, `leader` 계정(허영주)으로 로그인한 상태에서 육안 확인.

두 값의 출처가 다른 것으로 보인다 — 하나는 사용자 프로필의 역할, 다른 하나는
프로젝트 멤버십의 역할일 가능성이 높다. 최근 두 건의 변경이 이 근처를 건드렸다.

- 심사자(REVIEWER)를 팀원 수/목록에서 제외 (`d0454c9`)
- 회의 AI 역할 권한/알림 (PR #310)
- 마이페이지 프로필 항목 추가 (PR #317)

**어느 쪽이 맞는 값인지 아직 확인하지 않았다.** 표시 버그인지 데이터 불일치인지
가려야 한다. 데이터 쪽이면 권한 판정에도 영향이 있어 성격이 달라진다.

### 선택지

| 안 | 내용 | 규모 |
|---|---|---|
| A | 두 값의 출처를 먼저 추적해 표시 버그/데이터 불일치를 판별 | 작음 |
| B | 역할 표기를 한 곳(프로젝트 멤버십)에서만 읽도록 통일 | 중간 |

### 권고

**A 먼저.** 원인을 모르는 채 B로 통일하면 잘못된 쪽 값으로 맞출 수 있다.
권한 판정이 같은 값을 쓰고 있는지도 A에서 함께 확인한다.

## 부록: 되돌리자는 말이 나올 결정들

아래 둘은 **이미 결정됐고 선택지가 없다.** 다만 겉보기에 "그냥 하나 더 넣으면 되는데"
처럼 보여서 다시 제안될 가능성이 높다. 그때 꺼낼 근거를 적어둔다.

### A. `deploy-last-good`에 폴백을 두지 않는 이유

**나올 말:** "롤백이 태그 없다고 막혔네요. `deploy-previous`를 폴백으로 넣으면
적어도 뭐라도 되돌아가잖아요."

**답:** 두 태그는 이름이 비슷하지만 **의미가 반대다.**

| 태그 | 의미 | 정상 동작 보장 |
|---|---|---|
| `deploy-previous` | 직전에 **배포한** 커밋 | 없음 |
| `deploy-last-good` | 직전에 **헬스체크를 통과한** 커밋 | 있음 |

지금 롤백이 필요하다는 건 **방금 배포가 실패했다**는 뜻이다. 그 직전 배포도
실패했다면 `deploy-previous`는 **장애 커밋을 가리킨다.** 폴백은 이때 발동한다 —
하필 가장 위험한 순간에, 깨진 커밋으로 되돌리고, 헬스체크를 통과하지 못해
다시 롤백을 시도하는 구조다.

2026-07-23이 정확히 그 상황이었다. `deploy-previous`는 크래시 루프 중인
커밋을 가리키고 있었다. 폴백이 살아 있었다면 롤백은 "복구"가 아니라
**장애의 연장**이 됐다.

**핵심:** 롤백이 막히는 건 버그가 아니라 설계다. 되돌아갈 안전한 지점이
없다는 사실을 사람에게 알리는 것이, 안전하지 않은 지점으로 자동으로
되돌아가는 것보다 낫다. 자동 복구의 가치는 "복구된다"가 아니라
"복구된 상태가 정상임을 안다"에 있다.

폴백이 필요하다고 느껴진다면 진짜 문제는 태그가 아니라 **검증된 정상본이
없다는 것**이고, 그건 3번 항목(스테이징)으로 풀 문제다.

### B. 500을 게이트웨이 계열(502/503/504)에 넣지 않는 이유

**나올 말:** "500도 서버 오류인데 같이 묶어서 '잠시 후 다시 시도' 띄우면 안 되나요?"

**답:** 그러면 사용자에게 **두 가지 거짓말**을 하게 된다.

1. **"기다리면 해결된다"** — 500은 요청이 백엔드에 **도달했고**, 코드가 실행되다
   터졌다는 뜻이다. NPE, 제약조건 위반, 외부 API 실패 같은 것들이다. 이건
   시간이 지난다고 낫지 않는다. 같은 요청을 다시 보내면 같은 곳에서 또 터진다.
2. **"당신 잘못이 아니다"** — 500 중에는 특정 입력에서만 터지는 것이 있다.
   "일시적"이라고 말하면 사용자는 같은 입력으로 무한 재시도하게 되고, 정작
   다른 방법을 시도하거나 문의할 기회를 잃는다.

502/503/504가 다른 이유는 **요청이 애플리케이션에 닿지도 못했기** 때문이다.
백엔드 컨테이너가 교체되는 20초 동안 nginx가 붙을 곳이 없어서 나는 것이고,
이건 **기다리면 실제로 해결된다.** 재시도 안내가 참인 유일한 구간이다.

부수 효과도 있다. 500을 "일시적"으로 표시하면 **운영자도 속는다.**
사용자 문의가 "가끔 안 돼요"로 들어오고, 재현 안 되는 버그로 분류되어
실제 예외가 로그에 묻힌다.

**정리:** 재시도 안내는 재시도가 실제로 통할 때만 참이다. 범위를 넓히는 순간
그 문구는 정보가 아니라 소음이 된다.
