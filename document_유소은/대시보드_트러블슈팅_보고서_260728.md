### 0.1 중요도 Top 5

전체 45건 중 중요도가 가장 높은 5건이다. **No는 아래 상세 목록의 순번**이며, 표는 중요도 순으로 정렬했다.

| No | 문제 상황 | 발생 원인 | 해결 방안 |
|---:|---|---|---|
| 15 | 대시보드 조회 API 4개(`/summary`, `/tasks`, `/activities`, `/progress`)가 JWT 로그인만 요구해, URL의 `projectId`만 바꾸면 **소속되지 않은 프로젝트의 업무·팀원·활동을 조회**할 수 있다. | 전역 `SecurityConfig`가 JWT 인증을 강제하므로 "인증됨 = 접근 가능"으로 간주하고 프로젝트 단위 인가를 걸지 않았다. 일부 엔드포인트에는 `isMember`가 있어 **엔드포인트별 기준이 달랐던 것**이 문제를 가렸다. | 조회 계열 전 엔드포인트에 `@PreAuthorize("@projectAccess.isMember(#projectId)")` 적용. **재분석 계열 5개는 적용 완료, 조회 4개는 미적용 — 잔여 1순위.** |

선정 근거는 아래와 같다.

- **15·13번** — 유일한 두 건의 **보안(인가 누락)** 이슈다. 특히 15번은 아직 미해결이라 실 위험이 남아 있다.
- **25번** — 지연 위험도 모델 **전체의 신뢰도**를 좌우한다. 놓쳤다면 성능이 과대평가된 모델이 그대로 배포됐다.
- **19번** — 모델 결과가 **사람에 대한 평가**로 표시되는 지점이라, 오탐의 실질 피해가 가장 크다.
- **2번** — 화면에 **다른 프로젝트의 데이터**가 뜨는 정합성 문제로, 사용자가 오류로 인지하기도 어렵다.

### 0.2 작성 기준

대시보드 개발 과정에서 실제로 **발견되고 대응한 문제**만 기록한다. 단순 기능 추가·시안 반영은 제외하고, 아래 중 하나에 해당하는 건을 대상으로 한다.

- 잘못된 값이 화면에 표시되거나 데이터가 누락된 건
- 권한·알림이 의도와 다르게 동작한 건
- 빌드·테스트·배포가 실패한 건
- 모델 학습·추론에서 신뢰할 수 없는 결과가 나온 건
- 성능·안정성 문제로 구조를 바꾼 건

총 **45건**이며, 상태별로 해결 완료 39건 / 부분 해결 2건 / 미해결 4건이다.

PR봇 리뷰가 **전체의 3분의 1**을 차지한다. 특히 **권한 우회(13·14번)와 무음 폴백(22번)처럼 화면상으로는 정상으로 보이는 문제**를 사람이 아닌 봇이 먼저 잡아낸 비중이 높다.

**커밋 표기 규칙** — 각 항목의 `이슈 출처`에는 발견 경로와 함께 **관련 커밋 해시**를 "· 관련 커밋 `xxxxxxx`" 형태로 병기했다. 해시가 여러 개면 수정이 나뉜 것이고, `A → B`는 **1차 수정 후 재발·보완**된 2단계 이력이다(9·16번). 아래 요약표의 `출처` 열에는 지면상 대표 커밋 1건만 적었으므로 전체 목록은 상세 항목에서 확인한다. 미해결·부분 해결 항목은 수정 커밋이 없으므로 `관련 커밋 없음`으로 표기하고, 대신 **문제를 유발한 원인 커밋**을 참고로 덧붙였다.

## 4. ML — 업무 편중 점수 (ml_workload_score)

### 19. 업무를 다 끝낸 팀원이 "저활동 의심"으로 오탐

- **중요도** — ★★★★★ (5/5) — 모델 결과가 **사람에 대한 평가**로 표시되는 지점이고, 판정 기준 자체의 구조적 결함
- **이슈 출처** — 실사용 중 발견 (2026-07-24) · 관련 커밋 `aee8aad`
- **문제 상황** — 배정받은 업무 **12건을 전부 완료**한 팀원이 "저활동 의심"으로 표시됐다. 가장 성실한 팀원이 태만한 것으로 보이는 심각한 오탐.
- **발생 원인** — 저활동 판정 기준이 `task_count_active_rel`(팀 평균 대비 **진행 중** 업무 비율)이었다. 배정받은 일을 전부 끝내면 진행 중 업무가 0이 되므로 **완주한 사람은 구조적으로 무조건 걸리는** 설계 결함이었다.
- **해결 방안** — 판정 기준을 `task_count_total_rel`(팀 평균 대비 **전체 배정량** 비율)로 변경. "애초에 배정량 자체가 팀 평균보다 적은가"를 봐야 완료 여부와 무관하게 정확히 판정된다. 라벨도 **"저활동 의심"(태만을 단정하는 뉘앙스) → "배정량 불균형"(중립적 관찰 사실만 전달)** 으로 변경.
- **상태** — 해결 완료 — 단, 대시보드 반영은 20번 참조
- **기타** — FastAPI(`workload_model`/`workload_service`/`contribution_service`) → Spring(`ContributionMemberScoreDto`) → 프론트(`contributorsApi`/`MemberDrilldownPanel`) **전 계층에 `task_count_total_rel` 필드를 추가**해야 했다. 회귀 테스트(`test_workload_model_anomaly_direction.py`)로 "배정량이 팀 평균과 같으면(rel=1.0) 진행 중 업무가 0이어도 걸리지 않음"을 고정했다. **라벨 문구도 모델 산출물의 일부**라는 관점을 이 건에서 얻었다.

### 20. 편중 라벨 계약 변경이 대시보드에 미반영

- **중요도** — ★★★★☆ (4/5) — 19번의 오탐이 대시보드에는 **아직 그대로 노출 중**일 가능성

### 25. 데이터 누수로 검증 성능 과대평가

- **문제 상황** — 초기 학습에서 **F1-Macro 0.92**라는 비현실적으로 높은 검증 성능이 나왔다. 3클래스 다중분류에 '주의' 클래스가 0.8%뿐인 데이터에서 나올 수 없는 수치였다.
- **발생 원인** — `elapsed_ratio_at_cutoff`, `blocked_ratio_at_cutoff`, `imbalance_index_at_cutoff`가 **라벨링 규칙 `classify_risk()`의 입력값 그 자체**였다. 모델이 지연 패턴을 학습한 게 아니라 **라벨 계산식을 그대로 베끼고 있었다**. `hours_until_deadline_at_cutoff`도 `proxy_deadline_hours − elapsed_hours`로 역산 가능해 사실상 동일 정보였다.

- **상태** — 해결 완료
- **기타** — 제외 후 macro F1이 **0.92 → 0.79**로 현실화됐다. **"성능이 너무 좋으면 누수를 먼저 의심한다"** — 규칙 기반 라벨링을 쓸 때 라벨 계산에 들어간 변수는 전부 누수 후보다. 최종 학습 피처는 활동 모멘텀·블로커 정체·상태 체류 신호 중심의 8개로 선정했다.

### 26. 스냅샷 그룹 누수 및 희귀 클래스 편중 분할

- **중요도** — ★★★★☆ (4/5) — 같은 이슈가 학습·검증 양쪽에 섞여 성능이 과대평가되고 희귀 클래스 평가가 무효화될 수 있음

- **문제 상황** — 하나의 이슈를 생성 후 1/3/7/14/30일 시점으로 잘라 여러 학습 행을 만드는 **다중 스냅샷** 구조라, 단순 랜덤 분할하면 **같은 이슈의 스냅샷이 train과 valid에 나뉘어** 들어갔다. 또한 '주의' 클래스가 전체의 0.8%(4,633행 중 37행)뿐이라 랜덤 분할 시 **검증셋에 '주의' 표본이 아예 없을 수도** 있었다.

- **기타** — 클래스 불균형은 분할만으로 부족해 **역빈도 샘플 가중치**(`total / (클래스 수 × 해당 클래스 표본 수)`)를 `lgb.Dataset(weight=...)`로 함께 적용했다. 평가도 accuracy·weighted avg가 아닌 **macro F1과 F2를 동시 기준**으로 본다 — 위험/주의를 놓치는 비용이 큰 도메인이라 recall에 가중을 둔 F2를 병행한다.
