## A. 아키텍처 · 기술 선택

### A-1. 왜 백엔드를 Spring과 FastAPI 두 개로 나눴나요?

**①** 역할이 다릅니다. Spring은 DB 집계·권한 검증·트랜잭션을 담당하고, ML 추론은 Python 생태계(LightGBM·scikit-learn·pandas)가 필요해서 FastAPI로 분리했습니다.

**②** Spring에서 ML을 하려면 모델을 ONNX 등으로 변환해야 하는데, 학습 노트북과 서빙 코드가 갈라지면 재현성이 깨집니다. 지금은 학습(`train.py`)과 서빙(`delay_service.py`)이 **같은 `build_feature_row()`를 호출**해서 train/serve skew가 구조적으로 생길 수 없습니다.

**③** 대가는 네트워크 홉 1개와 장애 지점 1개 추가입니다. 그래서 실패 정책을 명시적으로 설계했습니다(A-2).

### A-2. FastAPI가 죽으면 대시보드는 어떻게 되나요?

**①** 대시보드는 계속 뜹니다. 다만 두 모델의 실패 정책이 다릅니다 — 지연 위험도는 마지막 예측으로 계속 서비스하고, 편중 점수는 캐시가 없으면 503으로 명시합니다.

**②** 기준은 **되돌아갈 마지막 값이 있는지**입니다.
- 지연 위험도: 결과가 `ml_predictions`에 **남으므로**, 재분석 호출 실패는 예외를 삼키고 저장된 최신 예측으로 응답합니다.
- 편중 점수: 원래 라이브 계산이라 캐시가 없었고, 그래서 `503 WORKLOAD_SCORE_UNAVAILABLE`로 드러냈습니다. 지금은 Redis 캐시(TTL 30일)를 앞에 둬서 **캐시 히트면 FastAPI가 죽어 있어도 서비스되고**, 캐시조차 없는 최초 1회만 503이 납니다.

**③** 프론트도 실패를 숨기지 않습니다. 편중 조회가 실패하면 "과부하 0명"이 아니라 **"…명"** 으로 표시합니다 — 예전에 휴리스틱으로 조용히 대체했더니 "N명 과부하"라는 숫자는 뜨는데 팀원 이름은 "데이터 없음"이 나오는 모순이 실제로 발생했습니다(TS-7).

### A-3. 정책이 서로 다르면 일관성이 없는 것 아닌가요?

**①** 일관된 기준을 적용한 결과가 다르게 나온 겁니다. 기준은 "사용자에게 보여줄 수 있는 마지막 유효값이 존재하는가" 하나입니다.

**②** 값이 있으면 그것으로 서비스하고(가용성 우선), 없으면 실패를 명시합니다(정직성 우선). 없는데도 그럴듯한 값을 만들어 보여주는 것이 가장 나쁜 선택이라고 판단했습니다.

### A-4. 왜 Redis Streams인가요? Kafka나 RabbitMQ, Celery가 아니고?

**①** 이미 알림(SSE)과 회의록 분석 워커에 Redis를 쓰고 있어서 인프라를 추가하지 않았고, 필요한 기능(consumer group · at-least-once · 정체 메시지 회수)이 Redis Streams로 충분했습니다.

**②** 팀 단위 서비스 규모(프로젝트당 수십~수백 업무)에 Kafka는 운영 비용이 과합니다. Celery는 Python 전용이라 **Spring이 producer**인 구조에 맞지 않습니다.

**③** 회의록 분석 워커와 **동일한 consumer-group 패턴**을 재사용해서 코드 리뷰·운영 노하우를 공유합니다(`DashboardAiQueueWorker`의 주석에도 명시).

### A-5. 대시보드에 AI(LLM) 기능이 있나요?

**①** 없습니다. 대시보드는 어떤 화면에서도 RAG/LLM을 직접 호출하지 않습니다.

**②** 커밋 `cd777a81`·`6e4843b`에서 **LLM 의존성을 전면 제거**했습니다. 빠른 액션의 "AI Assistant" 버튼은 전역 AI 패널을 여는 진입점일 뿐이고, 전체 업무 관리의 "회의록 AI" 표기는 **회의록 AI가 생성한 업무**를 가리키는 라벨입니다.

**③** 대시보드가 쓰는 두 ML은 LLM이 아니라 **지도학습 분류기(LightGBM)와 통계적 이상치 탐지(MAD)** 입니다. 외부 API 호출도, 토큰 비용도 없습니다.

## B. 성능 · 확장성

### B-1. N+1을 왜 JPA fetch join이나 `@EntityGraph`로 해결하지 않았나요?

**①** 담당자가 연관 엔티티로 매핑돼 있지 않아서 fetch join 대상이 아닙니다. `Task`는 `@ManyToOne User`가 아니라 `@Column(name = "assignee_id") private Long assigneeId`로 **id 값만** 들고 있습니다.

**②** 그래서 조인이 아니라 **id 수집 → distinct → `findAllById` 1회**로 해결했습니다. `Activity`의 `actorId`, `ProjectMember`의 `userId`도 같은 구조입니다.

**③** 연관 매핑으로 바꾸면 fetch join을 쓸 수 있지만, 프로젝트 전체가 id 참조 스타일로 통일돼 있어 대시보드만 바꾸면 오히려 일관성이 깨집니다. 지금 방식도 쿼리 수는 동일하게 2회입니다.

### B-2. 1분 이상에서 10초로 줄였다지만 10초도 느린데요?

**①** 맞습니다. 남은 비용은 N+1이 아니라 **프로젝트 전체 업무를 한 번에 읽어 메모리에서 집계**하는 구조 자체입니다.

**②** `getSummary()`는 `findByProjectIdOrderByCreatedAtDesc()`로 전체 업무를 읽고 `tasks.stream()`으로 상태별 카운트·마감 임박·팀원별 업무량을 모두 만듭니다. 업무 수에 선형 비례합니다.

**③** 다음 단계는 세 가지입니다 — (1) 카운트성 지표는 DB 집계 쿼리(`COUNT ... GROUP BY`)로 내리기, (2) 요약 응답을 Redis에 짧게 캐싱, (3) 목록은 페이지네이션. 현재 규모(프로젝트당 수십 건)에서는 10초가 첫 로딩 1회뿐이라 우선순위를 뒤로 뒀습니다.

### B-3. 동시 사용자가 늘면 버틸까요?

**①** 무거운 작업은 이미 요청 경로에서 빠져 있습니다. ML 재분석은 큐로, 편중 점수는 캐시로 분리했습니다.

**②** 조회 API는 모두 `@Transactional(readOnly = true)`이고, 재분석은 같은 (projectId, jobType)이면 **in-flight 마커로 병합**돼서 팀원 5명이 동시에 버튼을 눌러도 FastAPI 호출은 1회입니다.

**③** 병목은 워커 수입니다. 현재 인스턴스당 워커 스레드 1개인데, consumer group이라 **인스턴스를 늘리면 그대로 수평 확장**됩니다.

### B-4. 15초마다 폴링하면 서버 부하가 크지 않나요?

**①** 화면 리렌더는 실제 변경이 있을 때만 일어납니다. 다만 **요청 자체는 계속 나가는 것이 맞고**, 이건 개선 여지로 남아 있습니다.

**②** `AllTasksPage`는 15초마다 조용히 목록을 가져와 `id:status:updatedAt` 시그니처를 만들고, **이전 시그니처와 다를 때만** `refetch()`를 호출합니다. 그래서 스크롤·선택 상태가 흔들리지 않습니다.

**③** 근본 해결은 이미 있는 SSE 알림 채널에 "업무 변경" 이벤트를 태워 **푸시로 바꾸는 것**입니다. 폴링은 그 전 단계의 단순한 구현입니다.

## C. ML ① 지연 위험도 — 가장 날카로운 질문들

### C-1. macro F1 0.74는 낮지 않나요?

**①** 절대 수치보다 **왜 0.74에서 멈추는지**가 중요합니다. 라벨을 정하는 지표 3개를 피처에서 의도적으로 제외했기 때문에 생긴 상한입니다.

**②** 라벨은 `elapsed_ratio(경과 시간)`, `blocked_ratio(블로킹 시간)`, `imbalance_index(불균형 지수)`로 결정되는데, 이 세 개를 피처에 넣으면 모델이 정답 규칙을 그대로 외웁니다. 실제로 초기에 F1-Macro가 비현실적으로 높게 나와서 **누수 피처 4개를 제거하고 재학습**했습니다(트러블슈팅 3번). 지금 모델은 대리 신호만 보고 판단합니다.

**③** 특히 '주의'와 '위험'을 가르는 건 `blocked_ratio`가 0.12~0.28이냐 0.35~0.7이냐인데, **그 분모(마감까지의 총 기간)가 누수 컬럼이라 빠져 있습니다.** 모델은 분자만 보고 판단해야 하므로 원리적으로 완전 구분이 불가능합니다. 혼동 행렬에서 오류 141건 중 대부분이 이 두 클래스 사이에 있습니다.

### C-2. (핵심) 그럼 그냥 규칙 기반으로 하면 되지 않나요? ML이 왜 필요합니까?

**①** 지금 합성 데이터 기준으로는 **규칙이 사실상 상한이라는 지적이 맞습니다.** 현재 단계의 가치는 파이프라인 검증이고, 모델의 실익은 운영 데이터가 쌓인 뒤에 나옵니다.

**②** 상위 2개 피처(`status_at_cutoff`, `blocked_hours_before_cutoff`)가 설명력의 **87.3%** 라, 실질적으로 "블로커 상태와 그 체류시간"으로 판정합니다. 이건 규칙으로도 쓸 수 있습니다. 정직하게 이게 현재 한계입니다.

**③** 그래도 ML로 둔 이유는 세 가지입니다.
1. **임계값을 사람이 정하지 않아도 됩니다.** 규칙으로 하면 "블로커 며칠이 위험인가"를 팀마다 다시 튜닝해야 하는데, 모델은 데이터에서 경계를 잡습니다.
2. **확률을 함께 저장합니다.** 정상/주의/위험 라벨만이 아니라 클래스별 확률을 `ml_predictions`에 남겨서, 나중에 "주의 확률 0.45 이상은 미리 알림" 같은 정책을 코드 수정 없이 조정할 수 있습니다.
3. **피처를 늘리는 통로가 열려 있습니다.** 활동 로그·댓글·체크리스트 진행률처럼 규칙으로 조합하기 어려운 신호를 이미 피처 계약(52컬럼)에 넣어뒀고, 운영 데이터에서 신호가 생기면 재학습만으로 반영됩니다.

### C-3. 왜 실제 데이터가 아니라 합성(mock) 데이터로 학습했나요?

**①** 서비스가 아직 운영 데이터를 충분히 쌓지 못했고, 원래 쓰던 Jira 공개 데이터셋은 **스키마가 우리 DB와 달라 train/serve skew가 구조적으로 존재**했습니다. 그래서 학습 데이터를 서빙 스키마에 맞춰 합성하는 쪽으로 방향을 바꿨습니다.

**②** 핵심 설계는 **학습도 서빙과 같은 `build_feature_row()`를 호출**하는 것입니다. 학습 전용 피처 코드가 없으면 skew가 생길 수 없습니다. 4,500행(정상·주의·위험 각 1,500) × 52컬럼, 프로젝트 12개, 기준 시각 고정(재현성).

**③** 현실감 장치도 넣었습니다 — 마감일 없음 17.2%, 담당자 미배정 5.4%, 체크리스트 0개 10.6%, **댓글 0건 86.2%**. 특히 카테고리는 라벨 버킷 안에서 독립 샘플링해서 "카테고리=AI/ML → 위험" 같은 얕은 상관을 학습하지 못하게 했습니다(실제로 카테고리 R² 비중이 0.48%로 낮은 게 의도한 결과입니다).

### C-4. 합성 데이터 성능이면 실제 성능은 모르는 거 아닌가요?

**①** 맞습니다. 0.74는 "합성 규칙을 모델이 얼마나 되짚어내는가"이고 **실제 팀의 지연 패턴 적중률이 아닙니다.** 발표자료에도 한계로 명시했습니다.

**②** 그래서 검증 대상을 성능 수치가 아니라 **파이프라인**으로 잡았습니다 — 피처 생성 → 예측 → `ml_predictions` 적재 → Spring 최신값 추출 → 화면 표시가 실제 Supabase 데이터로 동작하는 것까지 확인했습니다.

**③** 운영 데이터가 쌓이면 반드시 재검증해야 합니다. 그때는 클래스가 '정상'에 크게 쏠릴 것이므로 accuracy가 아니라 **macro 지표를 봐야** 합니다.

### C-5. 왜 LightGBM인가요? 모델 비교는 했나요?

**①** 4개 모델 × 3구성 = **12 trial을 MLflow로 비교**했고 LightGBM이 최적이었습니다(macro F1 0.7399).

**②** 베이스라인에서 LightGBM 0.7335 / XGBoost 0.7334 / CatBoost 0.7324로 **사실상 동률**이고 RandomForest만 0.6972로 약 0.036 낮았습니다. 튜닝 개선폭이 +0.0064에 불과한 것도 "성능 상한이 하이퍼파라미터가 아니라 피처에 남은 신호량에 걸려 있다"는 뜻입니다.

**③** 동률 중 LightGBM을 고른 실무적 이유는 (1) **결측을 대치 없이 네이티브 분기**로 처리(체크리스트 0개 → `progress_ratio` NaN을 그대로 넘김), (2) 범주형(`status_at_cutoff`)을 `category` dtype으로 native 처리, (3) 학습·추론 속도입니다.

### C-6. 피처 선정을 왜 모델 중요도가 아니라 상관계수로 했나요?

**①** 4개 모델을 **공정하게 비교하려면 피처가 같아야** 하기 때문입니다.

**②** 각 모델이 자기 방식으로 중요도를 재서 피처를 고르면, "어떤 모델이 유리한 피처를 골랐는가"가 알고리즘 비교에 섞입니다. 그래서 **모델에 의존하지 않는 상관계수 R²로 한 번만** 선정해 4개 모델이 동일한 피처를 쓰게 했습니다.

**③** 명목형은 원-핫으로 펼쳐 더미별 R²를 구한 뒤 원본 컬럼 단위로 합산했습니다. 정수 코드로 바로 상관을 내면 코드 순서에 따라 값이 왜곡되기 때문입니다.

### C-7. 댓글 피처가 왜 탈락했나요? 성능이 0.79에서 0.74로 떨어진 건 회귀 아닌가요?

**①** 회귀가 아니라 **의도된 현실화**입니다. 데이터 생성에서 댓글 사용률을 15%로 낮추자(86.2%가 댓글 0건) 댓글 기반 피처 3개가 라벨과의 상관을 잃었습니다.

**②** 댓글이 없는 업무는 `hours_since_last_comment`가 `elapsed_hours`로 폴백되므로, 대부분이 댓글 0건이 되면 이 피처는 사실상 경과시간의 복사본이 됩니다. R² 비중이 15.0%(3위) → **0.05%(탈락)** 로 떨어졌습니다.

**③** 판단 근거는 "우리 팀이 업무 댓글을 거의 쓰지 않는다"는 관찰입니다. 그게 맞다면 0.79는 **서빙 시점에 존재하지 않을 신호에 기댄 낙관적 수치**였고 0.74가 실제에 가깝습니다. 활동 로그 기반인 `activity_count_recent_window`는 살아남아 5위를 지키고 있습니다.

### C-8. '정상' recall은 0.97인데 '위험' recall이 0.60입니다. 위험을 놓치면 안 되는 거 아닌가요?

**①** 정확히 그게 가장 비싼 오류라고 보고 있습니다. **'위험'을 '정상'으로 놓친 35건(11.7%)** 이 운영상 최악입니다.

**②** 대부분은 '위험-마감초과형'(블로커 없이 마감만 넘긴 케이스)으로 추정합니다. 이 분기의 유일한 구분 신호가 `elapsed_ratio`인데 그게 누수 컬럼이라 빠져 있습니다.

**③** 그래서 F1만 보지 않고 **recall에 가중을 둔 F2를 함께** 평가 지표로 넣었습니다(0.7425). 개선 방향은 마감일 정보를 누수가 아닌 형태(예: 마감까지 남은 기간을 구간화한 범주형)로 재설계하는 것입니다.

### C-9. 모델 파일이 없거나 잘못된 게 배포되면요?

**①** 잘못된 예측을 내는 대신 **503으로 명시적으로 실패**합니다.

**②** `delay_router.py`가 `load_artifact()` 실패를 잡아 `HTTPException(503)`으로 변환합니다. Hugging Face에서 모델을 받을 때는 **SHA256 체크섬을 검증**하고, 불일치면 파일을 폐기해 "모델 없음" 경로(503)를 타게 합니다.

**③** 운영 추론 코드를 `delay_model.py`로 분리해서 **노트북 실행 의존을 제거**했습니다. 노트북을 수정해도 서버가 깨지지 않습니다.

## D. ML ② 업무 편중 점수

### D-1. 왜 Isolation Forest가 아니라 MAD인가요?

**①** 팀 규모가 5~9명이라 표본이 너무 적습니다. Isolation Forest가 트리 분할 불안정으로 **극단값을 오히려 놓치는 사례**가 실제로 확인됐습니다.

**②** 그래서 `detect_overload_anomalies_auto()`가 팀원 수로 자동 분기합니다 — **15명 미만은 MAD 기반 Modified Z-score**, 15명 이상은 Isolation Forest. 캡스톤 팀 규모에서는 항상 MAD 경로를 탑니다.

**③** MAD는 평균·표준편차 대신 중앙값을 쓰므로 **극단값 자체가 기준을 흔들지 않습니다.** 과부하 팀원 1명 때문에 팀 평균이 올라가 그 사람이 정상으로 보이는 문제가 없습니다.

### D-2. 임계값 3.5는 어디서 나온 숫자인가요?

**①** Iglewicz & Hoaglin(1993)이 Modified Z-score에 권장한 기준값입니다. 임의로 정한 값이 아닙니다.

**②** 피처 4개의 modified z-score를 유클리드 거리로 결합한 `combined_distance`가 3.5를 넘으면 이상치로 봅니다.

**③** 점수도 **같은 3.5를 기준**으로 스케일링합니다 — `min(100, 100 × combined_distance / 3.5)`. 판정과 점수가 기준을 공유해야 모순이 없습니다(D-4).

### D-3. MAD가 0이면 어떻게 되나요?

**①** 표준편차로 폴백하고, 표준편차마저 0이면 그 피처를 판단에서 제외합니다.

**②** 값들이 중앙값에 몰려 있으면 MAD가 0이 되고, 그대로 나누면 아주 작은 차이도 z-score가 발산합니다. `denom = np.where(mad > 0, mad / 0.6745, np.where(std > 0, std, np.inf))` — 분모를 `inf`로 두면 해당 피처의 z가 0이 되어 자연스럽게 가중치 0이 됩니다.

**③** 완전히 동일한 값만 있는 피처는 변별력이 없으므로 제외하는 것이 맞습니다.

### D-4. 전원이 정상인데 한 명이 100점이 나왔다고 들었습니다.

**①** 스케일링 기준이 잘못돼 있었습니다. 점수를 **팀 내 최댓값 기준 상대 스케일링**으로 계산해서, 분포와 무관하게 최고값이 항상 100이 됐습니다(TS-15).

**②** 이상치 판정은 절대 임계값(3.5)을 쓰는데 점수만 상대 기준이라, `anomaly_type`은 "정상"인데 점수는 100점인 모순이 생겼습니다.

**③** `100 × combined_distance / 3.5`(상한 100)의 **절대 스케일링**으로 바꿔 두 값이 같은 기준을 공유하게 했습니다. 검증 테스트는 `test_workload_model_score_scale.py`입니다.

### D-5. "저활동 의심"을 "배정량 불균형"으로 바꾼 이유는?

**①** 판정 로직이 틀렸고, 라벨 표현도 부적절했습니다. 둘 다 고쳤습니다.

**②** 로직 문제 — 저활동을 **진행 중 업무 비율**(`task_count_active_rel`)로 판단해서, 배정된 12건을 **전부 완료한** 팀원도 진행 중 업무가 0이 되어 무조건 걸렸습니다. 기준을 **`task_count_total_rel`(전체 배정량 비율)** 로 바꿔야 "애초에 배정량이 적은 사람"과 "일을 다 끝낸 사람"이 구분됩니다.

**③** 표현 문제 — "저활동 의심"은 태만을 단정합니다. 시스템이 관찰할 수 있는 건 배정량 분포뿐이므로, **중립적 관찰 사실만 전달하는 "배정량 불균형"** 으로 바꿨습니다. 회귀 테스트(`test_workload_model_anomaly_direction.py`)로 배정량이 팀 평균과 같으면(rel=1.0) 진행 중 업무가 0이어도 걸리지 않음을 검증합니다.

### D-6. 팀원을 점수로 평가하는 게 윤리적으로 괜찮습니까?

**①** 평가가 아니라 **업무 배분 상태의 관찰**로 설계했습니다. 그래서 라벨도 중립적 표현으로 바꿨습니다(D-5).

**②** 점수는 "이 사람이 게으르다"가 아니라 "이 사람에게 배정된 업무 분포가 팀 평균에서 벗어나 있다"는 뜻입니다. 판정 근거로 쓰는 피처 4개는 모두 **업무 수·완료율·마감 초과 비율**이고, 근무 시간이나 개인 활동량은 보지 않습니다.

**③** 남은 개선점은 **판정 근거를 화면에 노출**해서 사용자가 결과를 해석하고 이의를 제기할 수 있게 하는 것입니다(개발총정리 트러블슈팅 4번의 향후 개선 사항).

## E. 비동기 큐 · 정합성

### E-1. 같은 재분석 요청이 동시에 여러 번 오면요?

**①** in-flight 마커로 병합해서 **기존 jobId를 반환**합니다. FastAPI는 1회만 호출됩니다.

**②** `enqueue()`가 `SETNX`로 `dashboard-ai-inflight:{projectId}:{jobType}` 키를 선점합니다. 선점 성공한 요청만 큐에 넣고, 실패한 요청은 그 키에 저장된 jobId를 그대로 돌려줍니다.

**③** 경합도 처리했습니다 — `setIfAbsent` 실패와 `get` 사이에 마커가 사라지면(TTL 만료 등) 큐에 아무것도 안 들어간 상태이므로, **새 jobId로 폴백하지 않고 재시도**합니다(`MAX_ENQUEUE_ATTEMPTS = 2`). 이걸 안 하면 큐에 넣지도 않은 jobId를 반환해 영원히 완료되지 않는 작업을 폴링하게 됩니다.

### E-2. 워커가 처리 중에 죽으면 작업이 사라지나요?

**①** 아닙니다. Redis Streams consumer group의 pending 목록에 남고, **10분 이상 정체되면 다른 워커가 `XCLAIM`으로 회수**합니다.

**②** 실행 중에는 1분마다 (1) 스트림 pending 리스와 (2) in-flight 마커를 **함께 갱신**합니다. 예전에는 리스만 갱신해서, 5분(in-flight TTL)을 넘기는 재분석이 아직 돌고 있는데도 마커가 사라져 중복 실행되고 상태 조회가 FAILED로 나왔습니다.

**③** TTL은 "워커가 죽었다"를 판정하는 시계이지 작업 시간 상한이 아닙니다. 그래서 살아 있는 동안 계속 연장합니다.

### E-3. at-least-once면 중복 실행될 수 있는데 괜찮나요?

**①** 재분석은 멱등(idempotent)이라 안전합니다. 같은 예측을 다시 계산해 `ml_predictions`에 행을 추가할 뿐입니다.

**②** `ml_predictions`는 이력 테이블이고, 화면은 항상 **`target_id`별 최신 1건만** 사용합니다(`target_id` ASC + `created_at` DESC로 읽어 `putIfAbsent`로 첫 행만 남김). 중복 실행이 화면에 영향을 주지 않습니다.

**③** 그래서 ACK 순서도 안전한 쪽으로 잡았습니다 — **완료 마커를 먼저 남기고 ACK/삭제**합니다. 순서가 반대면 그 사이 Redis 오류 시 레코드는 사라졌는데 마커가 없어 성공한 재분석이 영구히 FAILED로 보고됩니다(재시도할 레코드도 없음).

### E-4. 작업 상태를 왜 3값으로 나눴나요? 성공/실패면 되지 않나요?

**①** 2값으로 하면서 "in-flight 마커가 없으면 완료"로 간주한 게 버그였습니다(TS-14).

**②** 마커가 없는 경우에는 **성공 외에도 TTL 만료, 재시도 대기, 존재한 적 없는 jobId**가 전부 섞여 있습니다. 그래서 실패했는데 프론트가 `DONE`을 받아 갱신되지 않은 데이터를 최신인 것처럼 다시 조회했습니다.

**③** 워커가 남기는 **완료 마커를 도입**하고, `DONE`은 그 마커가 확인될 때만 반환합니다. 나머지는 `FAILED`로 내려 프론트가 즉시 에러 처리합니다. 검증은 `DashboardAiJobPublisherTest`(markDone/isJobDone), `DashboardServiceTest`(DONE/FAILED 판정 분리)입니다.

### E-5. 큐가 무한히 쌓이면요?

**①** 상한 1,000건을 두고, 초과하면 적재를 거부합니다.

**②** Lua 스크립트로 `XLEN` 확인과 `XADD`를 **원자적으로** 실행합니다. 두 명령을 따로 보내면 그 사이에 다른 요청이 끼어들어 상한을 넘길 수 있습니다. 상한 초과 시 `QUEUE_FULL` 센티넬을 반환해 `enqueue()`가 예외를 던집니다.

**③** 실제로 상한에 닿기 어렵습니다 — 중복 병합 때문에 (projectId, jobType) 조합당 최대 1건이므로, 1,000건이 차려면 프로젝트가 500개 동시에 재분석을 걸어야 합니다.

### E-6. 재분석 중에 사용자는 뭘 보나요?

**①** 요청 즉시 `jobId`와 `PROCESSING`을 받고, 프론트가 **2초 간격으로 최대 2분** 폴링합니다. `DONE`이 오면 진행률을 다시 조회합니다.

**②** `pollDashboardAiJobUntilDone()`이 담당하고, 2분(60회)을 넘기면 타임아웃 처리합니다. 완료 마커 TTL을 5분으로 잡아 폴링이 놓치지 않게 했습니다.

**③** 요청자 외 팀원에게는 워커가 **SSE 알림**을 보냅니다. 다른 사람이 재분석을 돌렸을 때도 화면을 갱신할 수 있습니다.

## F. 보안 · 권한

### F-1. URL의 projectId만 바꾸면 다른 프로젝트 데이터를 볼 수 있었다고요?

**①** 초기에 일부 조회 API가 로그인 여부만 확인하고 요청자의 프로젝트 소속을 검사하지 않았습니다. **현재는 13개 엔드포인트 전부** 멤버십 검사를 통과해야 합니다.

**②** 전역 `SecurityConfig`로 JWT 인증이 필수이고, 그 위에 컨트롤러 메서드마다 `@PreAuthorize("@projectAccess.isMember(#projectId)")`를 선언했습니다. 마일스톤 생성·수정·삭제는 `hasRole(#projectId, 'LEADER')`를 추가로 요구합니다.

**③** 발견 경로는 대시보드 API 전수 점검이었습니다. 신규 API에서 재발하지 않도록 **역할별 허용·거부 회귀 테스트**를 두고 있습니다(`DashboardMilestoneSecurityTest` 3건).

### F-2. 프론트에서 버튼을 숨기면 되지 않나요?

**①** 안 됩니다. 실제로 그 문제가 있었습니다 — 일반 팀원에게 마일스톤 삭제 버튼을 숨겼지만, **API를 직접 호출하면 삭제가 됐습니다.**

**②** 그래서 화면 노출 제어와 **서버 권한 검사를 동시에** 적용하는 것으로 정책을 통일했습니다. 서버 검사가 진짜 방어선이고, 버튼 숨김은 UX입니다.

**③** 블로커 화면의 마감일 조정도 같은 이유로 팀장 전용으로 제한했습니다(`5384f52`).

### F-3. 마일스톤을 삭제하면 연결된 업무도 사라지나요?

**①** 아닙니다. 업무는 보존하고 **일정 미정으로 이동**시킵니다.

**②** 초기에는 연결 해제 처리가 없어서 마일스톤 삭제 시 업무까지 사라졌습니다. 지금은 삭제 전에 `taskRepository.clearMilestoneId()`로 연결만 끊습니다.

**③** 마일스톤은 팀 전체 공지 성격이라 **생성자를 포함한 전원**에게 알림을 보냅니다. 수정 알림은 값이 실제로 바뀐 경우에만 발송하고, 변경 전/후 값을 문구에 담습니다.

## G. 프론트엔드

### G-1. React Query나 SWR을 쓰면 되는데 왜 훅을 직접 만들었나요?

**①** 타당한 지적입니다. 라이브러리를 썼다면 generation 번호를 직접 관리할 필요가 없었습니다.

**②** 직접 만든 이유는 프로젝트 전체가 `useState` + `fetch` 스타일로 통일돼 있어서, 대시보드만 새 데이터 페칭 라이브러리를 도입하면 팀원 간 코드 스타일이 갈라지기 때문입니다. 의존성을 늘리지 않는 쪽을 택했습니다.

**③** 대신 5개 훅이 **같은 3가지 계약**을 지키도록 규칙을 명문화했습니다 — (1) 첫 로드 이후 재조회에서 `loading`을 올리지 않음, (2) generation 번호로 stale 응답 폐기, (3) `refetch`는 항상 Promise 반환. React Query로 옮긴다면 이 세 가지가 각각 `keepPreviousData`, 쿼리 키 무효화, `refetch()` 반환값에 대응됩니다.

### G-2. 프로젝트 전환 시 이전 데이터가 덮어쓰는 문제는 어떻게 잡았나요?

**①** 요청마다 **세대(generation) 번호**를 올리고, 응답이 도착했을 때 번호가 다르면 상태에 반영하지 않습니다.

**②** 먼저 보낸 요청이 늦게 도착하는 응답 순서 역전(stale response)이 원인이었습니다. `AbortController`로 취소하는 방법도 있지만, 이전 구현이 cleanup 함수를 반환해서 `await refetch()`가 실제 완료를 기다리지 못하는 별개 버그가 겹쳐 있었습니다.

**③** 그래서 **취소는 cleanup이 아니라 번호 비교로** 처리하고, `refetch`는 순수하게 Promise를 반환하도록 분리했습니다. 5개 훅에 공통 적용했고 회귀 테스트는 `useDashboardTasks.test.ts`입니다.

### G-3. 완료일이 하루씩 틀어졌다는 건 무슨 문제였나요?

**①** 타임존 문제입니다. 백엔드가 내려주는 `LocalDateTime` 문자열에 **오프셋이 없어서** 브라우저가 로컬 타임존으로 해석했습니다.

**②** 백엔드 JVM은 `Asia/Seoul`로 고정인데 `"2026-07-24T10:15:30"`처럼 오프셋 없는 문자열을 `new Date()`로 파싱하면 보는 사람 타임존이 적용됩니다. 특히 `YYYY-MM-DD` 날짜-only 값은 UTC 자정으로 해석돼 KST와 하루 어긋났습니다.

**③** `parseKstDateTime()`에서 오프셋이 없으면 **`+09:00`을 명시로 붙입니다.** 그리고 임계값 판정용 `daysSince`(실제 경과 시간 기준)와 표시용 `formatRelativeDate`(캘린더 경계 기준)를 **의도적으로 분리**했습니다. "3일 이상 미업데이트" 판정과 "3일 전"이라는 라벨은 서로 다른 계산이어야 합니다.

**③-추가** 근본적으로는 서버가 오프셋 포함 ISO-8601로 내려주는 게 맞습니다. 다지역 서비스로 확장하면 그렇게 바꿔야 합니다.

### G-4. 화면이 9개인데 진행률 관련이 3개나 겹쳐 보입니다.

**①** 역할이 다릅니다 — **진행률 분석**(`/progress`)은 팀원·카테고리·마일스톤별 **완료율 분석**, **전체 진행률**(`/dash-progress`)은 **일정 대비 계획 진행률과 마일스톤 관리**, 홈의 진행률 카드는 **요약 진입점**입니다.

**②** 특히 `/dash-progress`는 프로젝트 시작일·마감일 기반 **예상 진행률과 실제 완료율을 대비**하는 화면이고, 팀장의 마일스톤 생성·수정·삭제·일괄 처리가 여기 있습니다.

**③** 다만 사용자 입장에서 이름만으로 구분이 어려운 건 사실입니다. 네이밍 정리는 개선 과제로 봅니다.

## J. 한 문장 요약 (마무리 발언용)

대시보드는 React 화면 9개 + Spring API 13개 + FastAPI ML 2종으로 구성했고, 구현의 핵심은 네 가지입니다.

1. **집계 성능** — user id 일괄 조회로 N+1을 제거하고 읽기 트랜잭션을 분리해 첫 로딩을 1분 이상에서 10초로 줄였습니다.
2. **실패를 숨기지 않는 설계** — 되돌아갈 값이 있으면 그것으로 서비스하고(저장형), 없으면 503으로 명시합니다(라이브형). 화면도 실패를 "0명"이 아니라 "…명"으로 드러냅니다.
3. **비동기 처리와 정합성** — 무거운 ML을 Redis Queue로 분리하고, 중복 요청은 in-flight 마커로 병합하며, 완료는 워커가 남긴 마커로만 판단합니다.
4. **ML 결과의 정확한 소비** — 데이터 누수 피처를 제거해 성능을 낙관적으로 부풀리지 않았고, `isAnomaly` 대신 `anomalyType`으로 이상치 방향을 구분하며, 판정 기준을 진행 중 업무량이 아닌 전체 배정량으로 교정했습니다.

한계도 분명합니다. 지연 위험도는 합성 데이터로 학습해 실제 적중률이 검증되지 않았고, 상위 2개 피처가 설명력의 87.3%를 차지해 사실상 블로커 신호에 의존합니다. 운영 데이터가 쌓이는 시점의 재검증을 다음 과제로 두고 있습니다.
