# ADR

## 회의록 분석을 요청-응답에서 Redis Queue 비동기로 이전

회의록 분석은 STT와 LLM 호출이 붙어 수십 초가 걸린다. 업로드 HTTP 요청 안에서 동기로
처리하면 긴 녹음일수록 타임아웃 위험이 커지고, 그 시간 동안 요청 스레드가 묶인다. Redis
Queue에 Job을 넣고 워커가 소비하는 구조로 바꿨다.

워커를 어디에 둘지는 세 안을 비교했다. Spring 내부 워커는 기존 DB 저장 로직을 그대로
재사용할 수 있고 초기 구현 비용이 가장 낮지만 API 서버에 분석 부하가 섞인다. FastAPI
워커는 AI 책임이 Python 쪽에 모여 구조적으로는 맞지만, DB 상태 저장과 프로젝트 권한 검증을
위해 Spring과 다시 연동해야 해서 권한 경계가 복잡해진다. 별도 워커 컨테이너는 확장성이
가장 좋지만 지금 규모에 운영 비용이 과하다. **Spring 내부 워커를 초기안으로 채택**했다 —
권한 검증이 이미 Spring에 있어 경계를 새로 만들지 않아도 되는 점이 결정적이었다.

큐 자체는 Kafka가 아니라 Redis Stream을 썼다. 이 규모에서 Kafka는 운영할 것만 늘어난다
(compose에 구성만 남아 있고 코드에서 호출하지 않는다).

결과: 이후 PR 리뷰에서 오디오 업로드 경로에 **동기 STT가 남아 있는 것**이 발견돼 같은 큐로
마저 옮겼다. 비동기로 바꿀 때는 "느린 작업"을 하나 옮기는 게 아니라 그 작업이 붙어 있는
경로 전체를 훑어야 한다는 걸 이때 배웠다.

## 알림의 소속 프로젝트를 파생 계산에서 컬럼으로 전환

여러 프로젝트에 참여하는 사용자에게 모든 프로젝트의 알림이 섞여 전달되고 있었다. 알림을
프로젝트 단위로 나눠야 했는데, 소속 프로젝트를 어떻게 알아낼지에서 결정이 한 번 바뀌었다.

처음에는 **컬럼을 넣지 않고 파생값으로 계산**하는 쪽을 택했다. 서버가 targetType/targetId로
원본을 되짚어 projectId를 내려주면 마이그레이션 없이 기존 알림까지 곧바로 분류된다는 게
이유였다. 스키마를 안 건드리고 끝낼 수 있으니 싸 보였다.

이 판단은 틀렸다. 파생 계산은 읽을 때마다 원본 테이블을 조인해야 해서 조회 경로마다 같은
역추적이 반복되고, 무엇보다 **자동 정리 쿼터를 프로젝트 단위로 좁힐 수가 없었다.** 쿼터가
사용자 단위로 남으면 알림이 활발한 프로젝트가 사용자 전체 쿼터를 독점해, 다른 프로젝트의
안 읽은 알림이 사용자가 보기도 전에 삭제된다. 저장 시점에 값이 없으면 저장 경로를 프로젝트
단위로 만들 수 없다는 게 핵심이었다.

그래서 `notifications.project_id` 컬럼을 추가하고(V20260728_1) 기존 행은 백필했다. 알림 생성
메서드에는 projectId 없는 오버로드를 **일부러 남기지 않았다** — 남겨두면 이후에 추가되는 알림이
다시 프로젝트 없이 저장되는 경로가 생긴다.

결과: 백필이 두 경우(원본이 이미 삭제된 알림, target_id가 애초에 NULL인 알림)를 복원하지 못해
project_id가 NULL인 행이 남았고, 이 행들이 조회에서도 정리에서도 빠지는 누수가 됐다. 별도
마이그레이션(V20260728_3)으로 삭제했다. 파생 계산을 버린 판단 자체는 옳았지만, 백필의 사각지대를
미리 설계에 넣지 못한 건 놓친 부분이다.

## 부수 작업이 본 작업의 트랜잭션을 무너뜨리지 않게 하는 방식

심사자 활동 로그처럼 본 작업에 곁다리로 붙는 기록은, 실패해도 본 작업을 되돌려선 안 된다.
그런데 활동 기록 저장이 실패하면 평가 확정·점수 저장 API 전체가 500으로 죽고 있었다.

세 가지를 검토했다. try/catch로 감싸기만 하는 것은 통하지 않는다 — JPA save()가 자체 트랜잭션
경계를 갖고 있어 예외가 그 경계를 빠져나가는 순간 참여 중인 트랜잭션이 rollback-only로
마킹되고, 그 뒤에 잡아봐야 호출자의 커밋은 이미 실패가 예정돼 있다. `REQUIRES_NEW`로 트랜잭션을
분리하는 것도 부족했다. 새 트랜잭션 역시 같은 이유로 rollback-only가 되는데, 커밋은 메서드
바디가 반환된 뒤 AOP 프록시에서 일어나므로 메서드 안 try/catch의 사정권 밖이다.

**TransactionTemplate을 채택**했다. `executeWithoutResult()` 안에서 커밋이 동기적으로 일어나므로
커밋 실패까지 같은 메서드의 try/catch로 잡을 수 있다. 선언적 트랜잭션(@Transactional)이 읽기는
깔끔하지만, 커밋 시점을 내 코드 안으로 가져와야 하는 자리에서는 프로그래매틱 방식이 맞다.

## 회의록 분석 정확도를 프롬프트가 아니라 입력 구조로 개선

회의록 To-Do 추출 정확도가 낮았다. LLM 프롬프트를 다듬는 방향과 입력 자체를 구조화하는
방향이 있었는데, **서비스가 회의록 서식(.docx)을 제공하고 그 양식으로 쓴 문서는 섹션 구조를
인식해 분석 범위를 좁히는** 쪽을 택했다. 프롬프트 튜닝은 모델이나 제공자가 바뀌면 다시
해야 하지만, 입력 구조화는 그 아래에서 계속 유효하다.

같은 원칙으로 두 가지를 바꿨다. 우선순위를 목록 순서로 추정하던 것(`index < 2면 HIGH`)을
작성자가 직접 체크하게 했다. 순서는 우선순위와 아무 상관이 없는데 그렇게 읽고 있었다.
그리고 실행항목 칸에 적힌 줄은 업무 키워드 필터 없이 전부 To-Do로 만든다 — 작성자가 그
칸에 적었다는 것 자체가 할 일이라는 선언이라, 거기에 키워드 필터를 또 거는 건 사용자의
명시적 입력을 시스템이 뒤집는 셈이다.

양식을 쓰지 않은 문서와 음성 업로드는 기존 경로 그대로 동작한다. 양식은 정확도를 높이는
선택지이지 전제 조건이 아니어야 한다.

## OAuth 쿠키 Secure 판정 방식

리버스 프록시 뒤에서는 백엔드가 "지금 요청이 진짜 TLS를 거쳐 왔는가"를 혼자 알 수 없다.
URL 문자열 추측(frontend.base-url이 https인지)은 배포 토폴로지와 무관해 폐기하고,
HttpServletRequest.isSecure() + 프록시 헤더 신뢰를 기본 판정 방식으로 채택했다. 다만
프록시가 사설 대역 밖(퍼블릭 IP 로드밸런서 등)에 있으면 이 방식도 항상 실패로 판정되므로,
운영자가 "이 배포는 어차피 HTTPS 전용"임을 명시적으로 선언할 수 있는 강제 플래그를 오버라이드로
병행했다. 자동 판정을 기본으로 두고 안 되면 명시적으로 강제할 수 있는 탈출구를 같이 두는
편이, 어느 한쪽만 쓰는 것보다 커버하는 배포 구성이 넓다.

## 아바타 업로드 검증 전략

포맷 판정은 클라이언트 Content-Type 헤더나 파일 확장자 대신 파일의 실제 매직 바이트로
한다. 둘 다 클라이언트가 자유롭게 조작할 수 있어 검증으로서 의미가 없기 때문이다. 디코딩
비용은 업로드 크기만으로 제한하지 않고, 헤더(메타데이터)만 먼저 읽어 해상도가 안전 범위인지
확인한 뒤에만 전체 픽셀을 디코딩하는 2단계 구조로 나눴다. 위험 판단을 실제 디코딩 이전
단계로 옮겨야, 크기는 작지만 해상도가 비정상적으로 큰 압축 폭탄 파일을 막을 수 있다.

## 이용약관·개인정보처리방침 동의 분리

두 동의를 하나의 필드에 매핑해 처리하던 방식을 버리고, 프론트 상태와 DB 컬럼 양쪽에서
완전히 독립된 값으로 관리하기로 했다. 서버에서는 둘 중 하나라도 없으면 예외 없이 가입을
거부한다. 구버전 클라이언트라 필드가 빠진 것인지 의도적으로 우회한 것인지 서버가 구분할
방법이 없으므로, 예외를 두지 않는 쪽을 택했다. 법적 동의 기록은 각각 독립적인 시각과 값으로
남아야 하고, 클라이언트 검증만으로는 devtools로 우회할 수 있어 최종 검증은 서버가 책임져야
실효성이 있다고 판단했다. 같은 원칙으로 비밀번호를 sessionStorage에 임시 저장하지 않도록
범위도 함께 좁혔다.

## 팀원 참여 방식 이원화 — 이메일 코드 + 공유 링크

프로젝트별 고정 초대 코드 하나만 쓰던 방식에, 클릭 한 번으로 처리되는 공유 링크 초대를
없애지 않고 병행 추가했다. 고정 코드는 구두로 불러주거나 문서에 남길 수 있는 짧고 재사용
가능한 값이 필요한 상황에 맞고, 링크는 메신저처럼 클릭 한 번으로 끝나야 하는 채널에 맞아
두 채널의 쓰임과 위협 모델이 다르기 때문에 하나로 합치지 않았다. 링크 초대는 역할을 항상
팀원으로 고정해 링크가 유출돼도 팀장 권한까지 넘어가지는 않도록 범위를 좁혔고, 아직 아무도
쓰지 않은 유효한 링크가 있으면 재사용해 반복 발급으로 링크가 계속 늘어나지 않게 했다. 수락
화면은 입력값이 토큰이든 코드든 먼저 토큰 수락을 시도하고 실패할 때만 코드 참여로 넘어가게
해서, 사용자가 두 방식의 차이를 몰라도 되게 만들었다.
