# 트러블슈팅

추적 과정이 드러나는 순서로 배치했다. 앞쪽일수록 처음 세운 가설이 틀렸거나, 에러 메시지와
실제 원인이 이어지지 않았거나, 간헐적으로만 재현된 건이다.

## 녹음 복구 경로가 실제 브라우저에서는 한 번도 동작한 적 없음

문제: 녹음 중 오류가 나면 그때까지의 원본을 살려내는 복구 경로를 넣어뒀는데, 실제 브라우저에서는
항상 빈 결과가 나왔다. 테스트는 통과하고 있었다.

원인: MediaRecorder를 timeslice 없이 시작해서 dataavailable 이벤트가 stop() 시점에만 발생했다.
그 전에 오류가 나면 살릴 청크가 애초에 하나도 없었다. 테스트가 통과한 건 목이 청크를 직접
밀어넣고 있었기 때문이다. 복구 로직 자체는 맞았지만, 그 로직에 도달할 데이터가 실제 환경에는
존재하지 않았다.

해결: MediaRecorder를 5초 timeslice로 시작해 주기적으로 청크를 받도록 했다. 같이 발견한 것으로,
recorder.stop()이 동기적으로 예외를 던지면 스트림과 busy 가드가 정리되지 않아 마이크가 켜진 채
남고 세션이 잠겨 다시 녹음할 수 없었다. 오류 경로와 동일하게 정리하도록 맞추고, requestStop()에
catch를 달아 미처리 rejection도 막았다.

교훈: 목이 만들어주는 입력으로만 검증하면 "로직은 맞지만 그 로직에 데이터가 도달하지 않는"
실패를 못 잡는다. 브라우저 API처럼 이벤트 발생 조건이 설정값에 달려 있는 것은 목을 통과했다고
끝내지 말고 실제 환경에서 한 번은 확인해야 한다.

## 활동 기록 실패가 평가 확정·점수 저장 API를 500으로 만듦

문제: 심사자가 평가를 확정하거나 점수를 저장하면 API가 500으로 실패했다. 정작 점수 저장
자체에는 문제가 없어 보였고, 올라오는 예외는 UnexpectedRollbackException이었다.

원인: 진짜 원인은 본 작업이 아니라 곁다리로 붙어 있던 활동 기록이었다. 호출자인
EvaluationScoreController.upsert()가 @Transactional이라, ReviewerActivityService.record()의
@Transactional(REQUIRED)이 호출자와 같은 물리 트랜잭션에 합류한다. Spring Data JPA의
save()도 자체 트랜잭션 경계를 가지고 있어서, save()가 던진 예외가 그 경계를 빠져나가는
순간 참여 중인 트랜잭션 전체가 rollback-only로 마킹된다. record() 안에서 예외를 잡아도
이미 늦어, 호출자의 최종 커밋이 UnexpectedRollbackException으로 실패했다.

해결: 첫 수정안이었던 REQUIRES_NEW로는 부족했다. 같은 이유로 record() 자신의 새 트랜잭션도
save() 실패로 rollback-only가 되는데, 커밋은 메서드 바디가 반환된 뒤 AOP 프록시에서
일어나기 때문에 메서드 안의 try/catch가 거기까지 닿지 않는다. TransactionTemplate으로 바꿔
커밋을 executeWithoutResult() 호출 안에서 동기적으로 일으키자 같은 메서드의 try/catch로
커밋 실패까지 잡을 수 있었다. 트랜잭션 격리를 검증하는 통합 테스트를 따로 붙였다.

교훈: 예외를 잡았다고 트랜잭션이 살아나지 않는다. @Transactional의 커밋은 메서드가 끝난 뒤
프록시에서 일어나므로 애초에 메서드 안 try/catch의 사정권 밖이다. 부수 작업이 본 작업을
무너뜨리면 안 되는 자리에서는 전파 속성을 바꾸는 것으로 끝내지 말고, 커밋 시점이 내 코드
안으로 들어오는지를 확인해야 한다.

## 실시간 알림이 13곳에서 통째로 발송되지 않고 있었음

문제: 업무 배정·댓글·완료 승인 등 대부분의 알림이 실시간으로 뜨지 않았다. DB에는 알림이
쌓이고 있어서 목록을 새로고침하면 보였기 때문에, 한동안 아무도 문제로 인식하지 않았다.

원인: NotificationService에 이름이 비슷한 메서드가 둘 있었다. notify()는 DB 저장만 하고 SSE
브로드캐스트를 하지 않고, notifyAfterCommit()이 실시간 발송까지 담당한다. 그런데
TaskController·TaskCommentController·MeetingAnalysisPersistence의 알림 트리거 13곳이 전부
notify()를 쓰고 있었다. 실시간 발송 경로를 쓰는 곳이 사실상 없었다.

해결: 13곳을 전부 notifyAfterCommit()으로 교체했다. 고치는 과정에서 별개 문제가 하나 더
나왔다. JwtAuthenticationFilter가 OncePerRequestFilter를 상속하는데, SseEmitter의 비동기
재처리(ASYNC dispatch) 때는 이 필터가 기본적으로 건너뛰어져 SecurityContext가 비어 있었다.
shouldNotFilterAsyncDispatch()를 false로 바꿔 해결했다.

교훈: 이름이 비슷한 메서드가 둘 있고 한쪽만 부수 효과를 가지면 호출부가 조용히 잘못된 쪽으로
몰린다. "DB에는 남는데 실시간만 안 온다"처럼 절반만 동작하는 증상은 저장과 발송이 한 메서드에
묶여 있는지부터 확인해야 한다.

## 백필이 놓친 알림 행이 보이지도 지워지지도 않은 채 무한히 쌓임

문제: 알림을 프로젝트 단위로 분리하면서 기존 행에 project_id를 채우는 백필 마이그레이션을
돌렸는데, 백필 후에도 project_id가 NULL로 남는 행이 있었다.

원인: 백필이 target_type별로 원본 테이블을 역추적하는 JOIN 기반 UPDATE라 두 경우를 복원하지
못했다. target_id가 애초에 NULL인 진행률 보고서 알림(target_type='project'), 그리고 백필
시점에 이미 삭제된 task/meeting/milestone을 가리키던 과거 알림이다. notifications.target_id는
폴리모픽이라 FK 제약이 없어 원본이 지워져도 알림 쪽에 반영되지 않는다.

더 큰 문제는 이 행들의 처지였다. project_id가 NULL이면 모든 조회 경로(project_id = :projectId
조건, countUnreadGroupedByProject의 IS NOT NULL 필터)에서 걸러져 어떤 화면에도 나타나지 않고,
정리 쿼리(deleteExcessByUserIdAndProjectId)도 project_id = :projectId 비교라 NULL에는 매칭되지
않아 정리 대상에서도 빠진다. 보이지도 않고 지워지지도 않는 채로 쌓이기만 하는 누수였다.

해결: 해당 행들을 삭제했다. 삭제 전에 tasks/meetings/milestones/evaluation_scores의 project_id가
DB 제약(NOT NULL FK)과 코드 양쪽에서 보장된다는 것을 확인해, 앞으로 새로 생기는 알림은 같은
경로로 NULL이 되지 않는다는 전제를 코드로 검증하고 진행했다.

교훈: 백필은 "채워지지 않은 행은 어떻게 되는가"까지 설계에 포함해야 한다. 조회에서도 빠지고
정리에서도 빠지는 값은 아무도 눈치채지 못한 채 무한히 쌓인다. 폴리모픽 참조는 FK가 없어 원본
삭제가 전파되지 않으므로 역추적 백필의 사각지대가 된다.

## 프로젝트 전환 시 이전 프로젝트 알림이 최신 화면을 덮어씀

문제: 프로젝트를 전환하면 방금 전환한 화면에 이전 프로젝트의 알림이 나타났다. 알림을
프로젝트 단위로 분리하는 작업을 끝낸 뒤였는데도 같은 증상이 다시 보였다.

원인: 경쟁 조건이었다. Header.handleToggleNotifications와 useNotifications의
refreshUnreadCount·showPendingNotifications가 fetch 직후 곧바로 setState하는 구조라, 요청이
나간 뒤 프로젝트를 전환하면 이전 프로젝트로 나갔던 응답이 전환 이후에 도착해 방금 전환한
프로젝트의 상태를 덮어썼다. 60초 폴링(FALLBACK_POLL_INTERVAL_MS)이 계속 요청을 내보내고
있어서, 빠르게 두 번 전환하는 특수한 조작이 아니라 평상시 사용 중에도 재현됐다. 분리 작업으로
고쳤다고 생각한 버그가 이 경로로 그대로 재발하고 있었다.

해결: 각 호출부에서 요청 시점의 projectId를 캡처해두고, 응답이 도착했을 때 useRef로 추적하는
"현재" projectId와 비교해 어긋나면 상태 반영과 토스트를 모두 버리는 가드를 넣었다. 고치기
전에 useNotifications.test.tsx에 회귀 테스트를 먼저 붙여, 수정 전에는 실패(이전 응답이 최신
상태를 덮어씀)하고 수정 후에는 통과하는 것을 확인했다.

교훈: 비동기 응답을 그대로 상태에 반영하는 코드는 화면 컨텍스트가 바뀌는 순간 전부 경쟁 조건
후보다. 기능을 프로젝트 단위로 분리했다고 끝이 아니라, 분리 이전에 이미 나가 있던 요청이
남아 있는지까지 봐야 한다. 간헐적으로만 보이는 버그는 재현을 테스트로 고정해두지 않으면
고쳤는지 확인할 방법이 없다.

## 콜드 로드에서 딥링크가 스스로 URL을 지워 영구히 깨짐

문제: 알림에서 개인 코멘트로 가는 딥링크가, 새로고침하거나 새 탭으로 열면 "찾을 수 없다"
토스트를 띄우고 그 뒤로는 아예 열리지 않았다. 앱 안에서 이동할 때는 정상이었다.

원인: MemberMyPage의 ?commentId= 딥링크 effect가 목록 로드 완료 여부를 projectId == null
하나로만 판단했다. useAuth()가 currentProjectId를 아직 확정하지 못한 콜드 로드 첫 렌더에서도
"로드 완료"로 오판해, 빈 목록에서 못 찾았다고 결론 내리고 토스트를 띄운 뒤 commentId를 URL에서
지워버렸다. URL에서 지워지니 이후 재시도할 방법도 사라졌다.

해결: useAuth()의 projectContextReady를 gate에 반영해, 컨텍스트가 확정되기 전에는 목록 로드
완료로 취급하지 않도록 했다.

교훈: "값이 없다"와 "아직 모른다"는 다르다. 비동기로 채워지는 컨텍스트를 null 체크 하나로
판단하면 초기 렌더에서 두 상태가 뭉개진다. 특히 그 판단의 결과로 URL 파라미터처럼 되돌릴 수
없는 것을 지워버리면 일시적 오판이 영구 실패가 된다.

## 녹음 원본이 조용히 사라지고 오류 뒤엔 세션이 잠김

문제: 녹음을 마친 뒤 저장 모달에서 제목·참석자를 입력하는 동안 새로고침하면 경고 없이 원본이
사라졌다. 녹음 중 오류로 중단된 경우에도 원본이 조용히 버려졌다. 별개로, 오류가 한 번 나면
그 뒤로는 다시 녹음을 시작할 수도 없었다.

원인: 유실은 세 경로였다. 새로고침 경고가 녹음 중에만 걸려 있어 아직 저장하지 않은
pendingBlob을 들고 있는 구간이 무방비였다. 녹음 중 오류로 중단되면 대기 중인 stop()이 없어
살려낸 원본을 resolve해도 받는 곳이 없었다. stop()의 조기반환 분기(기저 recorder가 스스로 멈춘
경우)도 청크를 그냥 버렸다. 세션 잠김은 원인이 달랐다. stop()이 onstop을 기다리는 사이 오류가
나면 대기 중인 Promise가 영영 resolve되지 않아 종료 가드가 잠긴 채 남았고, 마이크 권한 대기 중
언마운트되면 뒤늦게 도착한 스트림으로 recorder를 만들어 정리 주체 없이 마이크가 계속 켜져
있었다.

해결: 경고 대상을 pendingBlob 보유 구간까지 넓히고, 오류 경로에서도 대기 중인 stop()을 반드시
매듭지어 그때까지 모인 청크를 돌려주도록 했다. 조기반환 분기도 청크가 있으면 버리지 않는다.
언마운트 이후 도착한 스트림은 즉시 반납한다.

교훈: 데이터가 아직 서버로 안 간 구간은 전부 유실 구간이다. 정상 경로만 보면 "저장하면
안전하다"고 생각하기 쉬운데, 실제로는 저장 직전의 대기 시간과 오류 중단이 더 위험하다.
비동기 종료를 Promise로 감싸면 오류 경로에서 그 Promise를 매듭짓지 않는 순간 리소스가 영구히
잠긴다.

## OAuth 로그인 쿠키가 리버스 프록시 뒤에서 무효화됨

문제: Google OAuth state 쿠키의 Secure 속성을 frontend.base-url이 https로 시작하는지로
추측해서 정하고 있었다. 백엔드가 리버스 프록시 뒤에 있으면 실제 요청은 평문 HTTP로 들어올
수 있어 이 추측이 배포 토폴로지와 어긋나는 경우가 있었다.

원인: 로드밸런서가 퍼블릭 IP에 있으면 Tomcat의 프록시 헤더 신뢰 범위(사설 대역만 기본 신뢰)를
벗어나 isSecure() 판정이 항상 false로 나올 수 있고, 이 경우 쿠키가 유실돼 콜백에서 로그인이
원인불명으로 실패할 수 있었다.

해결: 문자열 추측 대신 HttpServletRequest.isSecure() + forward-headers-strategy: framework로
판정 기준을 바꾸고, 프록시가 사설 대역 밖에 있는 배포를 위해 강제 플래그
(WORKFLOW_FORCE_SECURE_COOKIES)를 명시적으로 켤 수 있게 했다. 이 설정이 잘못돼 있으면
부팅 로그에 경고를 남기도록 해서 조용히 실패하는 대신 원인이 바로 보이게 만들었다. 겸사겸사
state 값 비교도 String.equals에서 상수 시간 비교로 바꿨다.

교훈: 쿠키 보안 속성은 URL 문자열이 아니라 실제 요청 컨텍스트로 판정해야 하고, 그 판정이
프록시 설정에 의존한다는 사실 자체를 기동 로그로 드러내는 게 나중에 원인을 역추적하는 것보다
훨씬 싸다.

## 프로젝트 진행률이 항상 0%로 나오던 상태값 불일치

문제: 심사자 홈의 프로젝트 진행률이 어떤 프로젝트를 봐도 항상 0%였다. 업무는 실제로 완료돼
있었고 다른 화면의 집계는 정상이었다.

원인: ProjectService만 완료 상태를 "완료"라는 한글 라벨로 비교하고 있었다. tasks.status에
실제로 저장되는 값은 "done"이다(ReviewerService·RoadmapService·DashboardService와
TaskCreateRequest 스키마가 전부 "done"을 쓴다). 그래서 완료 건수가 늘 0으로 집계됐다.

해결: 비교값을 실제 저장값으로 교정했다. 더 문제였던 건 기존 테스트가 이 불일치를 그대로
통과시키고 있었다는 점이다. 테스트가 실제로는 저장되지 않는 "완료"/"할 일"로 픽스처를 만들어
검증하고 있어서, 구현과 테스트가 똑같이 잘못된 가정을 공유하고 있었다. 픽스처를 실측값
(done/todo)으로 바꾸고 회귀 테스트를 추가했다.

교훈: 테스트가 있다는 것과 그 테스트가 맞는 값을 쓰고 있다는 것은 다르다. 상태값처럼 문자열로
오가는 값은 DB에 실제로 저장된 값을 한 번 확인하고 픽스처를 맞춰야 한다. 같은 값을 읽는
서비스가 여러 개라면 한 곳만 다르게 쓰고 있는지 전부 훑어봐야 한다.

## 아바타 업로드 위장 파일과 압축 폭탄

문제: 프로필 아바타 업로드가 클라이언트가 보내는 Content-Type 헤더로 이미지 포맷을 판정하고,
ImageIO.read()로 바로 픽셀을 전체 디코딩해 저장하고 있었다.

원인: 헤더는 클라이언트가 자유롭게 조작할 수 있어 실제로는 이미지가 아닌 파일도 이미지로
위장해 통과시킬 수 있었고, 파일 크기는 작지만 압축을 풀면 해상도가 비정상적으로 큰
이미지(압축 폭탄)를 곧바로 전체 디코딩하면 메모리 고갈로 이어질 수 있었다.

해결: 포맷 판정을 헤더 대신 파일 실제 시그니처(매직 바이트)로 바꾸고, 디코딩도 2단계로
나눴다. ImageReader로 헤더(메타데이터)만 먼저 읽어 해상도가 안전 범위인지 확인한 뒤에만
전체 픽셀을 디코딩한다. 검증을 통과한 뒤 DB 저장이 실패하는 경우를 대비해 방금 올린 스토리지
객체를 정리하는 롤백도 추가했다. 위장 이미지 거부, Content-Type 스푸핑 방어, 손상 파일 거부를
포함한 관련 테스트 15건을 새로 붙였다. 같은 맥락에서 음성 파일 경로 검증에도 심볼릭 링크
우회를 차단하고 회귀 테스트를 붙였다.

교훈: 파일 포맷은 클라이언트 헤더가 아니라 파일 내용으로 판정해야 하고, 입력 크기와 처리
비용이 비례하지 않는 작업(이미지 디코딩)은 전체를 다 읽기 전에 위험을 판단할 수 있는 단계를
먼저 거쳐야 한다.

## 공유 Supabase DB와 로컬 마이그레이션 이력 불일치로 기동 실패

문제: 팀이 공유하는 원격 Supabase DB 하나에 여러 브랜치가 동시에 연결해 개발하고 있었는데,
한 브랜치로 backend-spring을 띄우면 기동 직후 죽었다.

원인: 원격 DB에는 이미 다른 브랜치(main) 수준의 마이그레이션이 적용돼 있는데 이 브랜치
로컬에는 해당 파일들이 없어 Flyway 검증이 실패했고, 이 브랜치 자체에서 새로 추가한
마이그레이션은 버전 번호가 이미 적용된 이력보다 낮아 순서 오류까지 겹쳐 있었다.

해결: 누락된 마이그레이션 파일들을 그대로 가져와 채워 로컬 이력을 원격과 맞추고(전부 멱등
처리돼 있어 실제 DB 변경은 없음), 이 브랜치의 신규 마이그레이션은 번호를 뒤로 재정렬해 항상
최신 버전이 되도록 했다.

교훈: 여러 브랜치가 같은 공유 DB를 바라보는 구조에서는 로컬 마이그레이션 폴더가 그 브랜치가
기준 삼는 스키마 이력과 항상 동기화돼 있어야 하고, 마이그레이션 버전 번호는 작성 시점이
아니라 실제 적용 순서를 기준으로 매겨야 한다.

## 로컬 DB 이미지에 pgvector 확장이 없어 벡터 마이그레이션 실패

문제: 로컬에서 빈 볼륨부터 DB를 새로 띄우면 벡터 검색 관련 마이그레이션이 실패했다.

원인: 로컬 compose 파일의 DB 이미지가 공식 postgres 이미지였는데, 여기엔 pgvector 확장이
포함돼 있지 않아 CREATE EXTENSION vector를 요구하는 마이그레이션이 처음부터 실패할 수밖에
없었다. 운영과 동일한 compose 파일은 이미 pgvector 포함 이미지를 쓰고 있어 이 문제가 없었다.
로컬 쪽만 갱신이 누락돼 있었다.

해결: 로컬 compose 파일의 DB 이미지를 운영과 동일하게 맞췄다.

교훈: 로컬·운영 두 compose 파일이 있는 구조에서는 한쪽 이미지를 바꾸면 다른 쪽도 함께
바꿨는지 확인해야 한다. 운영은 되는데 로컬 빈 DB에서만 실패한다면 두 환경 구성이 갈라져
있다는 신호로 먼저 의심할 것.
