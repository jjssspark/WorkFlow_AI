# 회고

- 기간: 2026-07-06 ~ 2026-08-13
- 개인 커밋: 357개
- 담당: 알림·실시간, 회의록 AI 분석 파이프라인, 심사자/기여도, 마이페이지, CI/CD

---

## 숫자 하나로 시작하면

개인 커밋 357개 중 **175개(49%)가 7월 26·27·28 사흘에 몰려 있다.** 특히 7월 27일 하루가
91개다. 이 기간은 중간보고서 마감 직전이자, 각자 따로 만든 기능을 처음 한 브랜치에 모아
붙인 통합 시점이었다.

이 회고에서 다룰 문제들의 대부분이 그 사흘 안에서 나왔다. 급하게 짜서 버그가 난 게
아니라, **붙여봐야만 드러나는 문제를 그때 처음 붙여봤기 때문**이다. 통합을 마감에 붙여둔
것 자체가 이번 프로젝트에서 가장 크게 잘못 잡은 일정이다.

## 1. 다시 만든다면 뭘 다르게 할 것인가

### "구현했다"의 기준을 코드가 아니라 실제 동작에 두겠다

같은 성격의 문제를 두 번 만났다.

- **실시간 알림**: 7월 21일에 알림 기능을 넣었다(`bd5a0ace`). 실시간 발송이 통째로 안 되고
  있다는 걸 안 건 **7월 26일**이다(`982edb83`). 닷새 동안 아무도 몰랐다. DB에는 알림이
  쌓여서 새로고침하면 보였기 때문이다. `notify()`(저장만)와 `notifyAfterCommit()`(저장 +
  SSE 발송) 중 호출부 13곳이 전부 앞쪽을 쓰고 있었다.
- **녹음 복구**: 브라우저 종료 후 복구 경로를 만들어 뒀지만, `MediaRecorder.start()`에
  `timeslice`를 주지 않아 **실제 브라우저에서는 한 번도 동작한 적이 없었다**(`173a90a0`).
  `dataavailable`이 `stop()` 때 한 번만 발생하므로 복구할 조각 자체가 생기지 않는다.

둘 다 코드는 있었고, 리뷰도 통과했고, 정상 경로 수동 테스트도 통과했다. 공통점은 **검증
경로가 정상 경로 밖에 있었다는 것**이다. 실시간 발송은 새로고침이 가려줬고, 복구는 브라우저를
실제로 죽여봐야만 밟힌다.

다시 만든다면, 부수 경로(실시간 푸시·복구·재시도)는 기능을 만든 그 커밋 안에서 **한 번이라도
실제로 밟아보는 것을 완료 조건에 넣겠다.** "코드가 있다"와 "동작한다" 사이의 간격이 닷새면,
그 닷새 동안 그 위에 쌓은 판단이 전부 틀린 전제 위에 있다.

### 알림의 소속 프로젝트를 처음부터 컬럼으로 두겠다

여러 프로젝트에 참여하는 사용자에게 알림이 섞여 나오는 문제를 풀 때, 처음엔 **컬럼을 안 넣고
`targetType`/`targetId`로 원본을 역추적해 파생 계산**하는 쪽을 택했다(`7945d7b0`). 마이그레이션
없이 기존 알림까지 곧바로 분류된다는 게 이유였다. 스키마를 안 건드리니 싸 보였다.

이 판단은 같은 날 뒤집혔다(`fd582b1e`). 파생 계산으로는 **자동 정리 쿼터를 프로젝트 단위로
좁힐 수가 없었다.** 저장 시점에 값이 없으면 저장 경로를 프로젝트 단위로 만들 수 없기 때문이다.
쿼터가 사용자 단위로 남으면 알림이 활발한 프로젝트가 전체 쿼터를 독점해, 다른 프로젝트의 안 읽은
알림이 사용자가 보기도 전에 삭제된다.

배운 건 "스키마 변경을 피하는 게 항상 싼 건 아니다"보다 조금 구체적이다. **읽을 때만 필요한
값이면 파생으로 충분하지만, 쓰기 경로가 그 값을 기준으로 동작해야 하면 파생으로는 안 된다.**
정리·쿼터·권한처럼 저장 시점에 판단이 필요한 축은 처음부터 컬럼이어야 한다.

### 부수 작업의 트랜잭션 격리를 개별 대응이 아니라 규약으로 먼저 정하겠다

심사자 활동 로그 저장이 실패하면 평가 확정·점수 저장 API 전체가 500으로 죽었다(`7aab8dd7`).
곁다리 기록이 본 작업을 되돌리면 안 되는데 되돌리고 있었다.

이건 한 곳의 버그가 아니라 **패턴의 부재**였다. 활동 로그, 알림, 통계 갱신처럼 "본 작업에 붙는
부수 기록"이 여러 군데 있는데, 각각이 어떻게 격리되는지 정해두지 않으면 매번 다르게 짜인다.
`try/catch`로 감싸는 것도 `REQUIRES_NEW`도 통하지 않고 `TransactionTemplate`이 필요하다는 걸
아는 데 시간이 걸렸고, 그 지식이 다른 부수 작업들에 자동으로 전파되지도 않았다.

다시 만든다면 "부수 작업은 이렇게 격리한다"를 컨벤션 문서에 한 줄 박아두고 시작하겠다.

### 번들 크기와 전송량을 한 번이라도 재보겠다

포트폴리오를 정리하면서 처음으로 프론트엔드 번들을 재봤다. 메인 청크가 **gzip 645.85 kB로
앱 페이지 예산 300 kB의 2.15배**였고, 라우트 30개 중 `React.lazy()`로 감싼 게 **0개**였다.

더 나쁜 건 배포본이었다. 응답 헤더에 `content-encoding`이 없다 — **nginx에 gzip이 아예 걸려
있지 않았다.** 사용자가 매번 2.43 MB를 받고 있었고, 압축만 켜면 약 670 kB로 줄어든다. nginx
설정 파일 두 개 어디에도 `gzip` 지시어가 없었고, nginx 기본값은 `off`다.

이건 앞의 항목들과 성격이 다르다. **알면서 미룬 게 아니라 재보지 않아서 몰랐다.** 기능이
동작하는지는 그렇게 확인했으면서, 얼마나 무거운지는 한 번도 묻지 않았다. 빌드 로그에 Vite가
500 kB 초과 경고를 계속 찍고 있었는데도 그냥 지나쳤다.

다시 만든다면 배포 파이프라인에 번들 크기 상한을 걸어 CI가 깨지게 하겠다. 사람이 안 보는
경고는 없는 것과 같다. 측정값은 [성능 · 품질 지표](../docs/성능_지표.md)에 있다.

### 폴리모픽 참조를 쓸 거면 백필과 정리를 같이 설계하겠다

`notifications.target_id`는 task·meeting·milestone을 함께 가리키는 폴리모픽 컬럼이라 FK 제약이
없다. 원본이 지워져도 알림에 전파되지 않는다. `project_id` 백필 때 이게 사각지대가 됐다 —
원본이 이미 삭제된 알림과 `target_id`가 애초에 NULL인 알림이 채워지지 않고 남았다(`885408a7`).

문제는 그 행들의 처지였다. `project_id`가 NULL이면 조회 쿼리에서도 걸러지고 정리 쿼리에서도
매칭되지 않는다. **보이지도 않고 지워지지도 않은 채 쌓이기만 하는 누수**다.

백필을 쓸 때 "채워진 행"만 생각했지 "안 채워진 행은 어떻게 되는가"를 설계에 넣지 않았다.
다음엔 백필 마이그레이션과 그 잔여 행 처리 마이그레이션을 한 쌍으로 쓰겠다.

## 2. 알면서도 남겨둔 기술 부채와 그 이유

README의 [미구현 · 임시처리 현황](../README.md#미구현--임시처리-현황)에 공개용으로 정리해 둔
것과 같은 내용이되, **왜 남겼는지**를 여기 적는다.

| 항목 | 상태 | 남긴 이유 |
| --- | --- | --- |
| **Kafka** | compose 구성만, 코드에서 미호출 | 회의록 분석 큐로 Redis Stream을 택했다. 이 규모에서 Kafka는 운영할 것만 늘어난다. compose 구성은 확장 대비로 남겨뒀지만, **쓰지 않는 인프라를 남긴 건 부채가 맞다.** 읽는 사람이 "Kafka를 쓰는 시스템"으로 오해할 여지가 있어 README에 미사용으로 명시했다 |
| **업무 편중 점수 ML** | 합성 데이터 학습 | 실제 라벨이 없다. 룰 기반 점수로 부트스트랩한 합성 데이터로 학습한 상태다. 운영 데이터가 쌓이기 전까지는 모델이 룰을 근사하는 것 이상을 못 한다. 그럼에도 파이프라인을 먼저 세운 건, 데이터가 생겼을 때 재학습만 하면 되도록 하기 위해서다 |
| **GitHub 연동** | 테이블·조회 경로만 | 동기화 로직이 없어 심사자 화면에 항상 0건이다. 팀 규모와 남은 기간을 보고 우선순위에서 내렸다. 프론트 화면은 라우터에 연결된 적조차 없어 포폴 정리 때 제거했다 |
| **산출물 생성** | 엔티티·리포지토리만 | P2로 분류해 범위에서 뺐다. 목업으로만 동작하던 `/deliverables` 화면을 제거했다 — **동작하지 않는 화면이 남아 있는 게 없는 것보다 나쁘다**고 판단했다 |
| **PDF 캡처 영역 하드코딩 색상 8개** | 의도적 예외 | 색상 토큰화 작업에서 이 8개만 hex로 남겼다. html2canvas 1.4.1이 `var()`를 색상 함수로 지원하지 않아(`SUPPORTED_COLOR_FUNCTIONS` 미등록 → `throw`) 토큰으로 바꾸면 PDF 내보내기가 런타임 예외로 깨진다. 해당 영역은 `left:-10000px`로 화면 밖에만 렌더되므로 사용자가 보는 색 체계와 무관하다. 근본 해결(`onclone`에서 계산값 주입)은 별건으로 남겼다 |
| **`project_id` NULL 알림 행 복구 대신 삭제** | 데이터 손실 감수 | 원본이 이미 삭제된 알림은 소속 프로젝트를 복원할 방법이 없었다. 복구를 포기하고 삭제했다. 삭제 전에 앞으로 같은 경로로 NULL이 생기지 않는지를 DB 제약과 코드 양쪽에서 확인하고 진행했다 |

공통 기준은 하나였다. **작동하지 않는 것을 작동하는 것처럼 보이게 두지 않는다.** 화면이 있으면
사용자는 동작을 기대한다. 그래서 미구현 기능의 화면은 지웠고, 지울 수 없는 것(Kafka, ML)은
문서에 상태를 적었다.

## 3. 가장 오래 붙잡은 문제와 거기서 배운 것

**알림이다.** 트러블슈팅 12건 중 4건, ADR 8건 중 1건이 알림 하나에서 나왔다. 그것도 대부분
7월 26~28일 사흘 안에 연쇄로 터졌다.

순서대로 보면 이렇다.

1. **실시간 발송이 통째로 안 되고 있었다** (7/26). 호출부 13곳이 전부 SSE를 안 타는 메서드를
   쓰고 있었다. 고치는 도중에 별개 문제가 하나 더 나왔다 — `JwtAuthenticationFilter`가
   `OncePerRequestFilter`를 상속하는데, SSE의 비동기 재처리(ASYNC dispatch) 때 이 필터가 기본
   스킵돼 `SecurityContext`가 비어 있었다.
2. **알림에 프로젝트 개념이 없었다** (7/28). 여러 프로젝트 알림이 섞여 나왔다. 파생 계산으로
   갔다가 같은 날 컬럼 추가로 뒤집었다.
3. **백필이 사각지대를 남겼다** (7/28). `project_id`가 NULL인 행이 조회에서도 정리에서도 빠져
   무한히 쌓이는 누수가 됐다.
4. **프론트에서 이전 프로젝트 알림이 최신 화면을 덮어썼다** (7/28). 프로젝트 전환 전에 나간
   요청이 뒤늦게 응답하는 경쟁 조건이었다.

### 배운 것 셋

**하나. "절반만 동작하는" 증상이 가장 오래 숨는다.**

완전히 안 되면 바로 잡힌다. 알림은 DB에 남고 새로고침하면 보였기 때문에 닷새를 버텼다.
저장과 발송이 한 메서드에 묶여 있지 않고, 이름이 비슷한 두 메서드 중 한쪽만 부수 효과를
가지면, 호출부는 조용히 잘못된 쪽으로 몰린다. **이름이 비슷한데 하는 일이 다른 메서드 쌍은
그 자체로 버그 유발 구조다.**

**둘. 한 기능의 문제는 층을 가로질러 나온다.**

알림 4건은 각각 서비스 레이어(메서드 오용), 스프링 필터(비동기 디스패치), DB 스키마(컬럼 부재),
마이그레이션(백필 사각지대), 프론트 상태(경쟁 조건)에 있었다. 어느 한 층만 잘 봐도 나머지가
안 잡힌다. 기능 단위로 **끝에서 끝까지 한 번 훑는 시간**이 층별 코드 리뷰보다 이런 문제를 잘
잡는다.

**셋. 판단을 뒤집는 건 비용이 아니라 정보다.**

파생 계산 → 컬럼 추가 전환은 같은 날 일어났다. 처음 판단이 틀렸다는 게 아니라, **정리 쿼터를
프로젝트 단위로 좁혀야 한다는 요구를 그 시점에는 몰랐다.** 요구가 드러나자 판단 근거가
무너졌고, 뒤집는 게 맞았다. 다만 뒤집은 뒤에도 백필 사각지대를 미리 못 봤다 — **뒤집는 결정을
할 때 새 방식의 실패 모드까지 같이 검토했어야 했다.** 이게 이번에 가장 아쉬운 부분이다.

## 마지막으로

이 프로젝트에서 제일 많이 한 일은 기능을 만드는 게 아니라 **"만들었다고 생각한 것이 실제로
동작하는지 확인하는" 일**이었다. 트러블슈팅 12건 중 절반 이상이 "코드는 있는데 동작하지 않던
것"이다. 없는 기능을 만드는 것보다, 있다고 믿고 있는 기능이 실은 없다는 걸 알아내는 게 더
어려웠다.
