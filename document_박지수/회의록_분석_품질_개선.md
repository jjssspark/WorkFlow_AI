# 회의록 AI 분석 품질 개선 — 측정과 수정

기간: 2026-08-15 ~ 2026-08-16
브랜치: `feat/meeting-analysis-quality`

---

## 요약 한 줄

"요약과 To-Do가 제대로 안 나온다"는 문제를 고치러 들어갔는데, **문제를 재는 자가 먼저 고장나 있었다.**
계측기를 두 군데 고치고 나서야 진짜 버그 하나가 드러났고, 그 버그가 실제 사용자 피해였다.

---

## 1. 왜 측정부터 했는가

처음 세운 개선 계획은 네 가지였다 — 파서 관대화, 양식 보강, 프롬프트 개선, 음성 분석.
전부 "이게 문제일 것이다"라는 **가설**이었고 근거가 없었다.

고치기 전에 잴 수 있는 상태를 먼저 만들었다. 회의록 12건(8개 시나리오)에 정답을 붙인
평가셋과 자동 채점기를 만들고, provider별로 점수를 냈다.

| 시나리오 | 케이스 수 | 무엇을 보는가 |
|---|---|---|
| 양식 준수 | 2 | 양식대로 적었을 때 |
| 구분자 생략 | 2 | 가운뎃점 없이 자연어로 적었을 때 |
| 우선순위 미체크 | 1 | 체크박스를 안 눌렀을 때 |
| To-Do 다수 | 1 | 실행항목이 6건일 때 |
| 담당자 미지정 | 2 | 담당자를 안 정했을 때 |
| 기한 표현 다양 | 2 | "8/10까지", "배포 당일" 등 |
| 자유 서술 | 1 | 양식을 안 쓰고 줄글로 적었을 때 |
| 환각 유도 | 1 | 막연한 표현을 날짜로 지어내는지 |

채점은 두 갈래다. To-Do는 기계적으로 잰다(정답과 예측을 **근거 문장**으로 짝지어 P/R/F1 +
담당자·기한·우선순위 정확도). 요약은 정답이 하나가 아니라 문자열 대조가 불가능하므로,
케이스마다 체크리스트를 적어두고 LLM에게 항목별 예/아니오만 받는다.

> **왜 근거 문장으로 짝짓는가**: 제목 유사도로 짝지으면, 나중에 제목 다듬는 작업을 할 때
> 채점 결과가 같이 흔들려 개선인지 착시인지 구분할 수 없다. 근거 문장은 원문에서 오므로
> 제목을 어떻게 다듬든 매칭이 흔들리지 않는다.

## 2. 측정이 계획을 세 번 뒤집었다

### 2-1. 파서 관대화 — 취소 (고칠 것이 없었다)

계획의 핵심 가설은 "사용자가 `담당 · 내용 · 기한` 형식을 안 지키면 담당자·기한이 유실된다"였다.
`split_todo_cell` 함수만 보면 맞는 말이다:

```python
split_todo_cell("박지수가 알림 중복 원인을 8월 14일까지 파악하기로 했다")
  -> (None, '박지수가 알림 중복 원인을 8월 14일까지 파악하기로 했다', None)
```

그런데 **호출부**가 이미 복원하고 있었다:

```
extract_assignee_candidate(...)                      -> '박지수'
extract_due_date_candidate(...) -> sanitize_due_date -> 2026-08-14
최종 To-Do: 담당='박지수' 기한=2026-08-14 HIGH   (정확)
```

베이스라인도 일치했다 — `구분자 생략` 시나리오의 담당자 정확도 1.00 / 기한 정확도 1.00 으로
`양식 준수`와 완전히 같았다.

**오진의 원인**: 함수 하나만 읽고 그 함수를 부르는 쪽을 읽지 않았다.
그대로 진행했다면 이미 동작하는 경로에 중복 로직을 얹고 회귀 위험만 만들었을 것이다.

### 2-2. HuggingFace 티어가 죽어 있었다

베이스라인에서 HF가 12케이스 **전부 0점**이었다. 러너를 거치지 않고 직접 호출해 예외를 받았다:

```
httpx.HTTPStatusError: Client error '401 Unauthorized'
x-error-message: Invalid username or password.
```

토큰은 `.env`에서 정상 로드됐다(길이·접두사 확인). 즉 요청은 정상이고 서버가 자격증명을 거부했다.
**코드로 고칠 수 있는 문제가 아니라 판단해 고치지 않고 보고했고**, 이후 토큰을 재발급받아 해결됐다.

이 티어는 폴백 체인의 **1순위**다. 즉 그동안 프로덕션은 항상 2순위 이하로 떨어져 돌고 있었다.
아무도 몰랐던 이유는 실패 로그에 예외 타입만 찍혀 401인지 404인지 429인지 구분할 수 없었기
때문이다. HTTP 상태 코드를 로그에 남기도록 보강했다. **응답 본문은 자격증명을 되비칠 수 있어
일부러 남기지 않는다.**

### 2-3. 요약 프롬프트 개선 — 취소 (지표가 아무것도 재고 있지 않았다)

요약 점수가 provider와 거의 무관하게 0.5 언저리에 붙어 있었다. 프롬프트를 고치려다,
그 전에 24개 체크리스트 항목의 심사기 문답을 **전부 열어봤다.**

- 긍정형 문항("~담겼는가") 12개 → **전부 `예`**
- 부재 확인 문항("원문에 없는 날짜나 이름이 요약에 없는가") 12개 → **10개 `아니오`**
- 12/24 = **정확히 0.500.** 측정된 요약 점수와 소수점까지 일치했다.

실패 12건을 원문과 대조한 결과:

| 판정 | 건수 |
|---|---|
| 사실과 다른 실패 | 10 |
| 구조적으로 답할 수 없는 문항 | 1 |
| 애매 | 1 |
| **진짜 결함** | **0** |

가장 뚜렷한 예가 환각 유도 케이스다:

```
요약: 재색인 스크립트 마무리 계획을 논의하고, 다음 주쯤 완료 예정으로 협의
결정사항: 박지수가 재색인 스크립트를 마무리할 예정이다.

Q: '다음 주쯤'이라는 막연한 표현이 특정 날짜로 단정되지 않았는가
A: 아니오  -> 실패
```

모델은 `다음 주쯤`을 **그대로 보존**했고 결정사항에 날짜를 **하나도** 넣지 않았다.
정확히 옳은 동작인데 두 항목 모두 실패로 처리됐다.

거짓 통과도 있었다 — 요약에 `8/10`이 언급조차 안 되는데 "8월 10일로 정확히 반영되는가"에 `예`.

**근본 원인**: 심사기에게 회의록 원문을 한 번도 주지 않고 있었다.

```python
def _build_prompt(summary, decisions, item):
    return (... f"[요약]\n{summary}\n\n[결정사항]\n{...}\n\n[질문]\n{item}")
```

체크리스트 절반이 "**원문에** 없는 날짜나 이름이 ..." 형태인데, 대조할 원문이 없으면
원리상 답할 수 없다. 1.5B 모델과 4B 모델이 **정확히 그 문항에서만** 반복해서 틀린 것이 증거다.
모델을 바꿔도 안 고쳐지는 종류의 문제였다.

## 3. 진짜 버그 — 출력이 잘려 분석이 통째로 실패하고 있었다

계측기를 고치는 과정에서, To-Do 6건짜리 회의가 HF·Ollama **양쪽에서** `JSONDecodeError`로
죽는 것을 발견했다. 원인을 실측으로 확정했다:

```
finish_reason: length
completion_tokens: 900          ← 상한값과 정확히 일치
응답 끝: '"keywords": [ "비밀번호 재설정", "스팸", "메일 템플'
```

완성에 **924토큰**이 필요한데 상한이 **900**이었다. 24토큰 차이로 JSON이 문자열 중간에서 끊겼다.

피해가 조용해서 더 나빴다. 잘린 JSON은 파싱에서 죽고 → 폴백이 규칙 기반까지 떨어지고 →
사용자에게는 이런 요약이 나갔다:

> "비밀번호 재설정 메일 개선 회의 내용을 분석해 핵심 결정사항 1건, 업무 후보 6건, 위험요소 1건을 추출했습니다."

내용이 아니라 **개수를 세어 읊는 기계 문구**다. To-Do 1건당 완성 길이가 대략 90토큰씩 늘어나므로,
실사용 회의는 이보다 쉽게 걸린다.

### 조치

| 항목 | 전 | 후 |
|---|---|---|
| HF 출력 상한 | 900 | 2048 |
| Ollama 출력 상한 | 650 | 2048 |
| Ollama 컨텍스트 창 | 4096 | 8192 |

컨텍스트 창을 같이 올린 이유는, 프롬프트만 1,400토큰대라 출력 상한만 올리면 이번엔
**창 쪽에서** 잘리기 때문이다. 한쪽만 고치면 증상이 자리만 옮긴다.

잘림 자체도 로그로 남긴다. 지금까지는 `Unterminated string` 예외만 남아 상한 문제인지
모델이 망가진 것인지 구분할 수 없었다.

## 4. 결과

### 4-1. 분석 실패 건수

| 측정 | HF 실패 | Ollama 실패 |
|---|---|---|
| 수정 전 | 1/12 | 1/12 |
| **수정 후** | **0/12** | **0/12** |

`To-Do 다수` 시나리오의 HF F1: **0.00 → 0.67**. 죽어서 0점이던 케이스가 살아났다.

### 4-2. provider별 평균

| provider | To-Do F1 | 요약 |
|---|---|---|
| huggingface | 0.497 | 0.708 |
| ollama | 0.258 | 0.667 |
| rule_based | 0.983 | 0.792 |
| **production** (사용자가 실제로 받는 경로) | **0.983** | **0.708** |

### 4-3. 요약 점수 before/after — **개선이 아니라 교정이다**

| 시나리오 | 전 | 후 |
|---|---|---|
| 환각 유도 | 0.00 | **1.00** |
| 자유 서술 | 0.50 | **1.00** |
| 우선순위 미체크 | 0.50 | **1.00** |
| 구분자 생략 | 0.50 | 0.75 |
| 전체 평균 (production) | 0.500 | 0.708 |

**이 숫자가 올라간 것은 요약이 좋아졌기 때문이 아니다. 채점이 정확해졌기 때문이다.**
요약 프롬프트는 한 글자도 건드리지 않았다. 환각 유도 0.00 → 1.00 은 모델이 원래부터
옳게 동작하고 있었다는 뜻이다.

점수가 오른 것보다 중요한 변화는, **케이스마다 다른 값이 나오기 시작했다**는 것이다.
이전에는 내용과 무관하게 0.5로 수렴했다.

## 5. 프로덕션 경로에 대한 이해

provider별 점수를 따로 재는 것만으로는 사용자가 받는 품질을 알 수 없다.
실제 진입점 `_analyze_json_uncached`는 한 겹을 더 씌운다 — **양식 문서면 provider의 To-Do를
버리고 규칙 기반 결과로 덮어쓴다.**

그래서 production 은 이런 합성이다:

- **To-Do**: 양식 문서면 규칙 기반 (provider 무관) → F1 0.983
- **요약·결정사항**: provider 결과 그대로 → HF 값과 일치 (0.708)

유일한 예외가 `자유 서술`이다. 액션 아이템 칸이 없어 덮어쓰기 조건이 성립하지 않고,
To-Do도 provider 결과가 그대로 나간다(production F1 0.80 = HF 0.80).

즉 **양식으로 쓴 회의록의 To-Do 품질은 LLM이 아니라 규칙 기반 로직이 책임진다.**
LLM 교체나 프롬프트 개선으로 그 부분을 올리려는 시도는 효과가 없다.

## 6. 양식 문서 보강

실행항목 칸에 `내용 (누가 · 무엇을 · 언제까지)` 헤더만 있고 **예시가 한 줄도 없었다.**
어떤 형식으로 적어야 하는지 양식이 알려주지 못했다.

| 위치 | 추가한 문구 |
|---|---|
| 실행항목 첫 입력 행 | `(예시) 박지수 · 로그인 오류 원인 파악 · 8/20` |
| 실행항목 칸 아래 | `※ 항목이 더 필요하면 표에서 행을 추가하세요.` |
| 참석자 입력 칸 | `(쉼표로 구분: 박지수, 유소은)` |

예시 행은 파서가 `(예시)` **접두사**로 거른다. 문자열 목록에 통째로 넣지 않은 이유는,
사용자가 예시를 지우지 않고 그 아래에 이어서 적는 경우가 흔한데 목록 방식은 문구가
조금만 달라져도 새어나가기 때문이다.

### 함정 하나를 미리 확인했다

예시 행의 **내용 줄만** 걸러지고 그 위 우선순위 체크 줄은 남는다. 이 고아 줄이 다음 행과
짝지어지면 우선순위가 통째로 한 칸씩 밀린다. 실측했다:

```
입력:
  [ ] 긴급  [ ] 보통  [ ] 낮음     ← 예시 행의 고아 체크줄
  [v] 긴급  [ ] 보통  [ ] 낮음
  유소은 · 세션 만료 확인 · 8/22

결과:
  [('HIGH', '유소은 · 세션 만료 확인 · 8/22'), ...]
```

밀리지 않는다. 내용 줄 없이 체크 줄이 이어지면 `pending_priority`를 덮어쓰기 때문이다.

서식은 새로 만들지 않고 기존 파일의 빈 run 에 글자만 채웠다. 사내 서식이라 격자·글꼴을
유지해야 했고, `add_run`으로 새 run 을 만들면 기본 글꼴 크기를 받아 옆 텍스트와 크기가 달라진다.

## 7. 남은 한계 — 이 측정을 믿을 때 알아야 할 것

1. **합성 데이터 12건이다.** 절대 점수에 통계적 의미를 두기 어렵다. 개선 판단은 before/after
   차이로만 한다.
2. **`"회의록 원문에 없는 날짜나 이름이 요약에 없는가"` 문항은 원문을 줘도 12건 중 6건에서 틀린다.**
   이중 부정 구조라 4B 모델도 못 읽는다. 문항을 답 가능한 형태로 다시 쓰면 해결되지만,
   골든 데이터를 손대면 되돌리기가 번거로워 이번엔 하지 않았다.
   → **25절에서 해결.** 다만 다시 쓴 문항도 안 됐다. 이 축을 LLM에게 묻는 것 자체가
   문제였고, 지금은 `safety_check` 가 문자열로 답한다.
3. **심사 모델 = HF 분석 모델이다.** huggingface·production 열의 요약 점수는 자기평가다.
   그럼에도 이 편을 택한 이유는 지금 문제가 편향이 아니라 심사기 정확도였기 때문이다
   (사람이 정답을 확인한 22개 항목 기준 1.5B 12건 → 4B 15건, 게다가 1.5B 의 12건은 전부
   긍정형 도장찍기라 실질 변별력이 0이었다).
4. **규칙 기반의 요약 점수(0.792)가 가장 높은 것은 지표의 허점이다.** 규칙 기반 요약은
   날짜와 이름을 아예 쓰지 않아서 "원문에 없는 날짜가 없는가"를 거저 통과한다.
   **아무 말도 안 하면 점수가 오르는 지표다.**
   → **25절에서 해결.** 두 축을 평균하지 않고 곱한다. 규칙 기반은 1위에서 3위로 내려갔다.
5. **평가셋이 문서→섹션 변환(Java `MeetingTemplateParser`)을 타지 않는다.** 픽스처가
   `sections`를 직접 주기 때문이다. 6절의 양식 보강 효과는 이 점수로 측정되지 않고,
   Java 단위 테스트와 수동 실측으로만 검증했다.
6. **Ollama 결과는 실행마다 흔들린다**(온도 0.1에서도 F1 0.317 / 0.267 / 0.258).
   순위는 세 번 모두 안정적이었다.

## 9. 던져진 질문

## 10. 추출 전용 평가셋을 만들었다

실행항목 칸을 비운 케이스 18건. 칸이 비면 덮어쓰기 조건(`if not action_items: return result`)에

**정답이 0건인 케이스를 6건 넣었다.** 추출에서 가장 중요한 것은 없는 할 일을 지어내지
않는 것인데, 기존 평가셋에는 그것을 재는 케이스가 하나도 없었다.

채점기도 고쳤다. 예전에는 정답 0건일 때 **아무것도 안 만든 경우와 3건을 지어낸 경우가
둘 다 f1=0.0** 이라 서로 구분되지 않았다. 즉 "환각을 안 했다"를 점수로 증명할 방법이 없었다.

## 11. 첫 측정에서 드러난 것 — 지어내고 있었다

F1 0.600. 그런데 손실의 위치가 뚜렷했다.

| | 케이스 | F1 | 재현율 |
|---|---|---|---|
| 진짜 할 일이 있는 회의 | 7건 | 0.86 | 1.00 |
| 할 일이 없는 회의 | 3건 | 0.00 | — |

**재현율이 전부 1.00 이다. 진짜 할 일은 한 번도 놓치지 않았다.** 손실은 전부 없는 것을
만들어내는 쪽이었다. 실제로 사용자에게 나가던 것들:

지표 공유 회의(배포 성공률 98% 보고, 조치 사항 없음)에서:

```
- '회의록 AI 분석 API 구현'                 HIGH
- '분석 결과 화면과 업무 보드 등록 흐름 연결'  HIGH
- '팀장 검토용 To-Do 승인 화면 점검'         MEDIUM
```

회의와 아무 관련이 없다. `app/main.py` 에 **하드코딩된 목록**이었다.

제안이 기각된 회의("이번 분기에는 안 하는 걸로 하시죠")에서:

```
- '알'                  담당=유소은  HIGH     ← '알겠습니다'가 제목으로 다듬어지다 잘린 것
- '나중에 다시 이야기'   담당=유소은  HIGH
```

## 12. 원인 세 가지와 수정

**(1) 하드코딩된 가짜 To-Do 목록.** 업무 문장을 못 찾으면 이 서비스 자체의 기능 3개를
채워 사용자 회의록에서 뽑은 것처럼 내보냈다. 제거했다.

**(2) 모델의 빈 결과를 코드가 덮어썼다.**

```python
if not explicit_candidates:
    return todos or build_todos(...)   # 빈 결과 -> 규칙 기반으로 대체
```

모델이 "할 일 없음"이라고 **옳게** 답해도 코드가 그 정답을 지웠다. 원문에 업무 선언
문장이 하나도 없으면 빈 결과가 곧 판단이므로 그대로 둔다.

**(3) "겠습니다"가 들어가면 무조건 업무 선언으로 봤다.** 그래서 "알겠습니다"가 업무가 됐다.
관측된 실패에서 나온 표현만 부정 목록에 넣었다 — 추측으로 넓히면 진짜 업무를 걸러낸다.

**결과: F1 0.600 → 0.900. 정답 0건 케이스 3건 모두 지어내지 않음.**
기존 12건은 0.983 그대로로 회귀 없음.

## 13. 문체 지적 — 두 번째 계측 오류

> "근데 문서 회의록에는 ~겠습니다 이렇게 안 적잖아. 음성본에는 그럴 수 있어도"

이것도 맞았다. 추출 케이스 10건이 전부 `"박지수: 제가 ~하겠습니다"` 구어체였다.
그건 음성 전사 문체이고, 타이핑하는 문서 회의록의 문체가 아니다.
구어체만으로 재면 **"겠습니다"에 기대는 규칙 기반 경로를 과대 대표**하게 된다.

개조식·서술형 8건을 추가해 다시 쟀다.

| 문체 | 건수 | F1 | 재현율 | 손실 방향 |
|---|---|---|---|---|
| 구어체 (음성 전사형) | 10 | 0.900 | 0.975 | **과다 생성** |
| 문서형 (개조식·서술형) | 8 | 0.750 | 0.750 | **누락** |

**실패 방식이 정반대다.** 정답 0건 케이스는 양쪽 합쳐 6건 모두 지어내지 않았다 —
환각 수정은 문체와 무관하게 작동한다.

문서형이 놓친 2건은 조건이 같다. **담당자나 기한이 없는 항목**이다.

- `doc-noassign-01`: "배포 스크립트 점검은 진행하되 담당자는 다음 회의에서 정한다" → 0건
- `doc-vague-01`: "완료 시점은 다음 주 중으로 예상되나 확정하지 못함" → 0건

이 누락은 이번 수정이 만든 회귀가 아니다. 예전 폴백도 `doc-vague-01` 은 0건이었고,
`doc-noassign-01` 은 1건 냈지만 제목이 `'회의내용 - 배포 스크립트가 간헐적으로 중단…'`
처럼 섹션 라벨까지 들어간 결과였다.

프롬프트를 보면 원인이 짐작된다. 담당자·기한 규칙은 "명시적일 때만 적어라"로 엄격한데,
**담당자나 기한 없이도 할 일은 할 일이라는 지시가 어디에도 없다.**

## 14. 그래서 답은

**양식대로 실행항목 칸을 채우면** — 그건 옮겨 적기가 맞다. AI 는 날짜 변환·이름 매칭·
분류만 한다. F1 0.983 은 그 작업의 점수다.

**칸을 비우면** — AI 가 실제로 판단한다. 문서형 0.750 / 구어체 0.900, 진짜 할 일은
거의 놓치지 않고(재현율 0.75~0.98), 할 일이 없는 회의에서는 이제 아무것도 만들지 않는다.

두 경로가 한 기능 안에 섞여 있었고, 어느 쪽이 동작 중인지 숫자만 봐서는 알 수 없었다.
그것을 나눠 잰 것이 2부의 성과다.

## 15. 2부에서 배운 것

**"AI 기능"이라고 부르는 것 안에 AI 가 없을 수 있다.** 덮어쓰기 한 줄 때문에 양식 문서의

**평가셋의 문체가 곧 측정 대상이다.** 구어체로만 짜서 규칙 기반 경로를 과대 대표했다.

폴백을 쓸 때는 **무엇을 실패로 볼 것인지**를 명시해야 한다. 빈 결과는 실패가 아닐 수 있다.

## 17. 측정 도중에 계측기 결함이 하나 더 나왔다

첫 재현 측정에서 `doc-multi-01`(정답 4건)이 갑자기 0점이 나왔다. 프롬프트를 고치기 전이라
2부 기록(0.750)과도 어긋났다. 모델에 같은 입력을 직접 넣어보니 4건을 정확히 뽑아냈다.

원인은 **HF 호출의 일시 실패**였다. 실패하면 Ollama, 그것도 실패하면 규칙 기반으로
폴백하는데, 폴백은 경고 로그만 남기고 점수에는 아무 표시 없이 섞여 들어간다.
그날의 네트워크 사정이 그대로 "품질 개선/악화"로 읽히는 구조였다.

그 값은 신뢰 구간 밖으로 두고 재측정했다.

> 1부에서 고친 계측기가 2개, 2부에서 1개, 3부에서 1개다. **측정값이 예상과 다르면
> 대상보다 계측기를 먼저 의심하는 편이 결과적으로 빨랐다.**

## 18. 프롬프트에 넣은 것

`build_ollama_prompt` 에 `todos 선정 규칙` 블록을 추가했다. 요지는 세 가지다.

1. 하기로 정해진 일은 **담당자나 기한이 없어도** todos에 넣는다. 모르는 칸은
   `assignee_candidate: ""`, `due_date: null` 로 두고 업무 자체는 남긴다.
2. 이미 시작된 일도 **남은 작업이 있고 계속하기로 했으면** 할 일이다.
3. 제외 대상을 명시한다 — 남은 작업 없이 끝난 일의 완료 보고, 조치가 결정되지 않은
   지표·현황 공유, 하지 않기로 하거나 보류한 일, 의견·질문·맞장구.

3번을 함께 넣은 이유는 1·2번만 넣으면 2부에서 잡은 환각이 되살아나기 때문이다.
"더 뽑아라"는 지시는 "없는 것도 뽑아라"로 새기 쉽다.

**예시 문장은 픽스처에서 가져오지 않았다.** 평가셋 문장을 프롬프트에 넣으면 점수는
오르지만 그건 답을 알려주고 시험을 보는 것이다. `"OO 작업은 ..."` 형태의 뼈대만 남겼다.

### 두 번째 조정

1차 수정 후 `doc-vague-01` 이 여전히 0건이었다. 이 회의의 제목이 `재색인 스크립트 진행 상황`

## 23. 양식을 4열로 바꿨다 — 추출기가 정한 제약

실행항목 표를 2열에서 4열(실행 항목 · 담당자 · 완료 기한 · 우선순위)로 바꿨다.
체크박스를 누르는 대신 값을 적고, 담당자·기한을 가운뎃점으로 이어 적지 않아도 된다.

바꾸기 전에 docx→텍스트 경로부터 확인했다. **거기서 이번 설계가 결정됐다.**

### 추출기가 표 구조를 버린다

Spring 은 POI 를 쓰지 않는다. `MeetingAnalysisService.extractDocxTextFromBytes` 가
ZIP 을 열어 `word/document.xml` 을 정규식으로 훑는다. 표를 아는 코드는 한 줄도 없고,
`<w:p>` 를 개행으로 바꾸는 부수효과로 **셀마다 한 줄**이 나온다. 그리고 결정적으로

> **빈 셀은 빈 줄조차 남기지 않고 통째로 사라진다.**

`<w:tc><w:p></w:p></w:tc>` 가 개행과 공백만 내놓고, 뒤이은 `\n{2,}` 축약이 그걸 지운다.

그래서 **열 위치로는 어느 칸인지 알 수 없다.** 4열 표에서 담당자를 비우면 그 행은
네 줄이 아니라 세 줄로 나오고, 기한이 담당자 자리로 밀린다.

구양식이 이 문제를 안 겪은 이유는 `[ ] 긴급 [ ] 보통 [ ] 낮음` 체크줄이 **정규식으로
알아볼 수 있는 행 경계 표시**였기 때문이다. 우연히 안전했던 것이지 설계된 안전은 아니었다.

### 그래서 우선순위 값이 행의 끝이다

새 양식은 빈 행마다 우선순위 칸에 **"보통"을 미리 인쇄**한다. 파서는 긴급/보통/낮음 토큰을
만나면 한 행이 끝난 것으로 보고, 그 앞에 쌓인 줄들을 이렇게 가른다.

- 첫 줄 → 실행 항목 (이 칸이 비면 행 자체를 안 쓴 것이다)
- 나머지 → 기한처럼 보이면 기한, 아니면 담당자

담당자로 잘못 읽힌 값은 참석자 대조에서 걸러지므로, 최악의 경우 기한을 놓칠 뿐
엉뚱한 사람에게 배정되지는 않는다.

양식 안내에 "그대로 두면 보통으로 처리되니 지우지 마세요"를 넣은 것은 문구가 아니라
**파싱 제약**이다. 그 값을 지우면 그 행이 다음 행과 합쳐진다.

### 빈 양식을 그대로 올리면

실제 docx 를 Spring 추출기와 같은 방식으로 텍스트화해 끝까지 태워봤다. 여기서
설계 결함이 하나 나왔다.

표 안에 예시 행을 두면 4열이라 예시가 네 칸으로 흩어지는데, 예시를 걸러내는
`(예시)` 접두사 규칙은 **첫 칸만** 잡는다. 나머지 세 칸이 살아남아 —

```
=== 보일러플레이트 제거 후 실행항목 ===
['박지수', '8/20', '긴급', '보통', '보통', '보통', '보통']
=== parse_action_items ===
  ActionItem(priority='HIGH', content='박지수', assignee='', due_date='8/20')
```

담당자 이름이 업무 제목이 된 유령 To-Do다. 예시를 표 밖 안내 줄(`※ 예: …`)로 옮겨
해결했다. ※ 로 시작하는 줄은 이미 걸러진다. 지금은 빈 양식을 그대로 올리면 To-Do 0건이다.

### 검증

| 대상 | 결과 |
|---|---|
| 사용자가 채운 신양식 (실제 추출 경로 왕복) | 3건 전부 담당자·기한·우선순위 정확 |
| 손대지 않은 빈 양식 | To-Do 0건 |
| 구양식 문서 | 계속 동작 (체크박스 경로 유지) |
| 기존 12건 평가셋 | F1 1.000 유지 |
| 테스트 | FastAPI 138 passed / Spring 회의록 184 passed |

구양식 호환을 남긴 이유는 이미 그 양식으로 쓴 회의록이 있기 때문이다. 파서가 먼저
체크줄이 있는지 보고 없으면 신양식으로 읽는다.

### 남은 것

- 평가셋에 신양식 케이스가 없다. 지금 검증은 단위 테스트와 추출 왕복 확인이고,
  품질 점수로는 재지 않았다. 신양식 픽스처를 넣으면 수치로도 볼 수 있다.
- 저장소에 docx→텍스트 구현이 **세 개**다(Spring ZIP+정규식 / FastAPI python-docx /
  프론트 미리보기). 셋의 평탄화 규칙이 다르다 — Spring 은 셀당 한 줄, FastAPI 는 행당 한 줄,
  프론트는 빈 줄을 남긴다. 한쪽에 맞춘 파서는 다른 쪽 입력을 잘못 읽는다.
  지금 분석 경로는 Spring 것이라 거기 맞췄다.

### 이걸 어떻게 읽어야 하나

**이 평가셋으로는 양식 변경의 이득을 잴 수 없다.** 구양식이 이미 만점이라 오를 자리가

회귀가 없다는 것 — 그게 이 측정이 증명한 전부다. 그것도 값은 정보다. 파서를 새로 짰고
양식 파일을 갈아엎었으니, 조용히 나빠지지 않았다는 확인이 필요했다.

양식을 바꾼 진짜 이유는 점수가 아니었다.

- 체크박스에 v 를 넣는 수고가 없어진다
- 가운뎃점 두 개로 세 칸을 나누던 규칙이 사라진다. 그 규칙은 어기기 쉽고, 어기면
  담당자가 업무 제목에 박혔다(`2026-08-04` 트러블슈팅의 뿌리가 그것이었다)
- 담당자·기한이 각자 칸을 가지므로 문장에서 유추하지 않아도 된다

셋 다 **작성자 경험**이지 모델 성능이 아니다. 지표가 그걸 보여주지 못하는 게 맞다.

### 무엇을 더 재야 이득이 보이나

구양식이 실제로 깨지는 입력이 평가셋에 없다. 예를 들면 —

- 칸 순서를 바꿔 적은 경우 (`업무 · 담당자 · 기한`)

## 25. 요약 지표를 고쳤다 — 두 번 틀리고 세 번째에

7절 한계 4번에 이렇게 적어뒀다. **"규칙 기반의 요약 점수(0.792)가 가장 높은 것은 지표의
허점이다. 아무 말도 안 하면 점수가 오르는 지표다."** 그걸 고쳤다.

### 25-1. 왜 아무 말도 안 하면 점수가 올랐나

케이스마다 문항이 딱 2개, 반반이었다.

```
[충실도] 임베딩 모델 교체와 재색인 결정이 요약에 담겼는가
[안전성] 회의록 원문에 없는 날짜나 이름이 요약에 없는가
```

이 둘을 그냥 평균했다. **두 축은 실패 방향이 반대라 평균하면 서로를 가려준다.**
날짜와 이름을 아예 안 쓰는 규칙 기반 요약은 안전성을 거저 통과하고, 충실도 한 문항만
잃는다. 바닥값이 0.5다.

**고친 방식: 두 축을 따로 세고 곱한다.**

| 충실도 | 안전성 | 종합 | 뜻 |
|---|---|---|---|
| 1.0 | 1.0 | **1.00** | 담았고 지어내지 않았다 |
| 1.0 | 0.0 | **0.00** | 지어냈으면 아무리 잘 담아도 못 쓴다 |
| 0.0 | 1.0 | **0.00** | 아무 말도 안 한 것은 안전한 게 아니다 |

기본값을 일부러 비대칭으로 뒀다. 충실도 문항이 없으면 0.0, 안전성 문항이 없으면 1.0이다.
**잰 것이 없으면 점수를 줄 근거가 없지만(충실도), 걸어둔 제약이 없으면 어긴 것도
없다(안전성).** 반대로 두면 문항을 빠뜨린 케이스가 조용히 만점을 받는다.

### 25-2. 문항을 유형별로 갈라놓고 보니 두 케이스는 충실도를 아예 안 재고 있었다

`duedate-02` 와 `halluc-01` 은 두 문항이 **모두 안전성**이었다.

```
duedate-02  '배포 당일'이라는 표현이 특정 날짜로 지어내지지 않고 미확정으로 남는가   <- 안전성
            회의록 원문에 없는 날짜나 이름이 요약에 없는가                          <- 안전성
```

문면만 보면 첫 문항은 "담겼는가"를 묻는 것처럼 읽힌다. 그래서 아무도 눈치채지 못했다.
곱셈으로 바꾸면 이 두 케이스는 **구조적으로 항상 0점**이 된다. 충실도 문항을 새로 세웠다.

이런 게 다시 생기지 않도록 픽스처 불변조건 테스트를 걸었다
(`test_summary_checklist_shape.py`). 모든 케이스가 충실도 문항을 최소 하나 가져야 한다.

### 25-3. 안전성 문항은 두 번 고쳐도 안 됐다

여기서부터가 이번 작업의 절반이다.

**1차 시도.** 이중 부정(`없는 것이 없는가`)을 긍정형으로 바꿨다. `요약에 적힌 날짜와
사람 이름이 모두 회의록 원문에 나오는가`. 재측정했더니 규칙 기반 요약이 안전성 0.417.
**지어낼 재료가 없는 요약이 환각 문항에서 떨어진다.** 앞뒤가 안 맞았다.

**2차 시도.** 대조 입력 세 개로 문구를 골랐다. `나오는가` → `찾을 수 있는가` 로 바꾸자
세 경우를 다 맞혔다. 적용 후 ollama 0.500→0.833, rule_based 0.417→0.583. 그런데
**HF는 0.417 그대로**였다.

**원인.** 같은 요약 문장에 원문만 갈아 끼워봤다.

| 요약 (날짜·이름 없음) | 원문 | 답 |
|---|---|---|
| `알림 중복 발송 원인을 파악하고…` | 짧은 합성 원문 | 예 |
| `알림 중복 발송 원인을 파악하고…` | 실제 `nosep-01` 원문 | **아니오** |

**원문에 날짜·이름이 많으면 심사기가 대조 방향을 뒤집어 읽는다.** "원문엔 있는데 요약엔
없네"로 판단한다. 요약→원문으로 물었는데 원문→요약으로 답한다. 문구를 아무리 다듬어도
원문 구성에 따라 뒤집히니, LLM 문답으로 재는 한 재현되지 않는다.

**3차 — 질문을 바꾸는 대신 질문하는 상대를 바꿨다.**

"지어낸 날짜가 있는가"는 **판단이 아니라 문자열 대조다.** LLM에게 물을 일이 아니었다.
`meeting_eval/safety_check.py` 가 정규식으로 답한다.

- 요약과 원문에서 날짜를 뽑아 `(월, 일)`로 정규화하고 집합 차를 본다
- 표기가 갈려도(`8월 10일` / `8/10` / `2026-08-10`) 같은 날이면 같은 값이다
- 지어낸 날짜가 하나라도 있으면 0

체크리스트에는 판단이 필요한 문항만 남겼다(`'다음 주쯤'이 특정 날짜로 바뀌지 않고
남아 있는가` 등). 이 문항들은 측정에서 정확히 작동했다.

**사람 이름은 재지 않기로 했다.** 성씨 목록으로 뽑아보니 `정리해`, `문서로`, `남기기`가
이름으로 잡혔다. 형태소 분석 없이는 안 된다. 담당자 환각이라는 실제 위험은
`assignee_accuracy` 가 구조화된 필드로 이미 정확히 재고 있다. **재는 척하는 것이
안 재는 것보다 나쁘다.**

## 26. 충실도 축이 관대했던 이유는 문항 수였다

`"OCI 배포 스크립트 점검 회의"` 같은 껍데기 요약이 나머지 11건에서 충실도 1.00을 받던 문제다.

### 26-1. 원인은 심사 모델이 아니라 문항 설계였다

처음에는 심사 모델을 키우는 쪽을 생각했다. 그런데 문항을 세어보니 원인이 다른 데 있었다.

```
duedate-01      coverage 1개
formal-01       coverage 1개
many-01         coverage 1개   ← 정답 To-Do 가 6건인데 문항은 1개
...
12건 중 9건이 coverage 문항 1개
```

문항이 하나면 그 하나만 통과해도 충실도가 만점이다. 게다가 그 하나가 복합문이었다.

| 종전 문항 | 문제 |
|---|---|
| `임베딩 모델 교체와 재색인 결정이 요약에 담겼는가` | 둘 중 하나만 담아도 "예" |
| `담당자 표시 버그 재현과 아바타 기능 적용이 요약에 담겼는가` | 위와 같음 |
| `6건의 실행 항목이 모두 요약이나 To-Do 목록에서 누락 없이 반영되는가` | **심사기는 To-Do 목록을 못 본다.** 요약과 결정사항만 받는다 |

마지막 건은 원리상 답할 수 없는 문항이었다. 25절에서 안전성 문항이 같은 이유로
못 미더웠던 것과 같은 결함이 충실도 쪽에도 남아 있었다.

**심사 모델을 키웠어도 이건 안 고쳐진다.** 문항이 1개면 어떤 모델이 심사해도 만점은 만점이다.

### 26-2. 담아야 할 사실을 하나씩 끊어 물었다

케이스마다 **결정 / 실행항목 / 배경** 세 축으로 나눴다.

```

  - 임베딩 모델을 교체하기로 한 결정이 요약에 담겼는가
  - 전체 문서를 재색인하기로 한 결정이 요약에 담겼는가
  - 임베딩 모델 교체 뒤 검색 정확도가 떨어졌다는 배경이 요약에 담겼는가

many-01 (종전 1문항 → 7문항)
  - 이번 스프린트에서 전부 처리하기로 한 결정 + 실행항목 6건 각각
```

충실도 문항이 12건 합계 **11개 → 39개**가 됐다. 안전성 문항은 손대지 않았다.

**배경 문항을 넣은 이유.** 결정과 실행항목만 물으면 `"~ 회의"` 형태의 껍데기 요약이
결정사항 필드를 근거로 통과할 여지가 남는다. 배경(왜 이 회의를 했나)은 요약이
실제로 원문을 읽었을 때만 담긴다.

**담당자·마감일은 요약 문항으로 재지 않았다.** `assignee_accuracy` / `due_date_accuracy` 가
구조화된 필드로 이미 정확히 재고 있어서, 요약 쪽에서 또 물으면 같은 것을 두 번 센다.

### 26-5. 같이 고친 것 둘

**원문에 없는 것을 맞히라고 요구하는 정답**이라, 담당자를 비워두는 올바른 동작이
오답 처리된다. 원문에 발화(`박지수: 재색인 스크립트 잔여 작업이 남아 있습니다`)를
넣어 근거를 만들었다. 정답을 `null` 로 바꾸는 쪽도 있었지만, 그러면 이 케이스가
`doc-noassign-01`(담당자 미정)과 목적이 겹쳐 `기한 미확정` 시나리오가 없어진다.

픽스처 41건을 전수 스캔했고 같은 결함은 이 1건뿐이었다.

**폴백이 응답에 안 보이던 문제.** FastAPI 안에서 `hf → ollama → 규칙 기반` 으로
강등돼도 로그에만 남았다. Spring 의 `analysisSource` 는 `FASTAPI` / `SPRING_FALLBACK`
만 구분해서, 사용자가 받은 요약이 HF 것인지 규칙 기반 것인지 운영에서 알 방법이 없었다.
17절에서 폴백이 표시 없이 측정에 섞여 0점이 나온 것도 같은 미관측 강등이다.

응답에 `analysis_provider` 를 실었다.

| 값 | 의미 |
|---|---|
| `huggingface` / `ollama` / `rule_based` | FastAPI 안에서 실제로 답한 티어 |
| `spring_fallback` | FastAPI 자체가 안 돼서 Spring 이 대신 분석 |
| `unknown` | 저장된 분석을 DB 에서 다시 조립한 경우 |

**저장분이 `unknown` 인 것은 한계다.** DB 에 티어 컬럼이 없어 재조회 경로에서는
출처를 모른다. 컬럼 추가는 마이그레이션이 필요해 이번엔 뺐다. 실시간 분석 응답에서는
정확한 값이 나온다.

캐시 스키마도 v2 → v3 으로 올렸다. 안 올리면 기존 캐시가 `unknown` 으로 계속 응답해서,
관측성을 붙이고도 한동안 아무것도 안 보인다.
